1Getting in, and running the firm

First boot and the two seat invites node server.js (first run) · createSeatInvites() in kernel/auth.js

Chambers ships with no accounts and no signup page. The very first time the server starts against an empty data directory it mints exactly one single-use enrolment link per named seat and prints them to the console. Those two links are the only way anyone ever gets into the system for the first time.

How to use it

Start the application with `node server.js` from /home/user/scotia/app. It listens on port 8028 unless PORT says otherwise, and binds to 127.0.0.1 only unless CHAMBERS_HOST is set, so nothing on the network can reach it without the TLS proxy in front. Its encrypted files live in /home/user/scotia/app/data unless CHAMBERS_DATA points elsewhere. On the first run the console prints a block headed 'FIRST BOOT — seat invites (single use each, 7 days):' followed by one line per seat, for example 'Dan G (admin): http://localhost:8028/invite/<code>'. Send Dan his line and Matt his line, by whatever channel you would use for a password — anyone holding a link can enrol on that seat. The seats themselves are fixed in code as 'Dan G:admin,Matt D:admin' and can only be changed by setting CHAMBERS_SEATS before the first boot.

Guarantees

Each seat link is single-use and expires seven days after it is minted. Nothing about either lawyer is pre-shared: the seat invite carries only a name and a role, and the person supplies their own email, their own password and their own authenticator secret at enrolment. There is no default account, no default password, and no public route by which a stranger can create one — every route except the front door, the login posts, /healthz, /robots.txt and the /invite/ links requires a session cookie.

Does not do

It does not re-print the links on later restarts while they are still live, and it does not email anything: the console is the only place the links appear. If you lose that console output while the links are still valid, redeem or re-issue them from the server with tools/invite.js rather than waiting.

Enrolling on a seat

Watch out

Redeem both links well inside the seven days. If they do lapse before anyone enrols, restarting Chambers mints a fresh pair and prints them again — the boot check counts only live invites, so a lapsed deployment is recoverable by a restart, and re-minting is safe because it happens only while the firm has no accounts at all. The printed URL says localhost:8028; if the firm reaches Chambers through its TLS proxy, substitute the real hostname and keep the /invite/<code> path exactly as printed.

Enrolling on a seat GET /invite/:code · POST /invite/:code · enrollPage() in kernel/html.js · redeemInvite() in kernel/auth.js

This is where a lawyer turns an invite link into an account: chooses the email address that will be their sign-in, and sets their password twice so a typo cannot become permanent.

How to use it

Open the invite link. The page is a single bare panel that reads 'Provisioned access for Dan G (admin).' and shows three boxes: 'Your email (becomes your sign-in)', 'Choose a password (12+ characters)', and 'Type it again'. Fill all three and press 'Enroll & enter'. If the two passwords differ, the page comes straight back with a red banner reading 'The two passwords do not match.' and nothing has been written. Other refusals appear the same way: 'Password must be at least 12 characters.', 'Enter a valid email — it becomes your sign-in.', and 'That email is already enrolled.' On success you are signed in immediately and land on the Account security page with the banner 'Enrolled. Next: enable two-factor authentication below — it takes thirty seconds.' Do exactly that before you do anything else.

Guarantees

The server compares the two password boxes before the password is hashed or stored, so a mistyped password can never become your live credential. Passwords are stored only as scrypt hashes (N=16384, r=8, p=1) with a random salt — the plaintext is never written anywhere. The invite is marked used at the moment it is redeemed and cannot be replayed. The email you type is checked against a real address pattern and, on a seat invite, against every other active account.

Does not do

It does not check password strength beyond the twelve-character minimum — twelve spaces would be accepted. It does not set up two-factor authentication; you arrive with password-only access and must enable 2FA yourself on the page you land on. It does not let anyone else, including the other administrator, see or later reset what you typed. And it does not verify that you own the email address you entered: there is no confirmation message, so a typo in the email means you have enrolled under an address you cannot be reached at, though you can still sign in with it exactly as typed.

Signing in

Watch out

Have your password manager open and write the password into it before you press the button. Nobody in the firm can read it back to you afterwards. The email is fixed at enrolment — there is no screen anywhere in Chambers that changes an account's email address.

Signing in GET / · POST /login · login() in kernel/auth.js

The front door. It is deliberately bare — no firm name, no logo, no hint about whether an email is known to the system.

How to use it

Go to the site root. You get a small panel with 'Email' and 'Password' and a full-width 'Sign in' button. If the credentials are good and you have no authenticator enrolled, you land straight on the Desk (/r/desk). If they are not good, you are returned to the same panel with a red banner reading exactly 'Access denied.' and nothing else.

Guarantees

An unknown email and a wrong password are indistinguishable: the server runs the full scrypt computation either way, so the two cases take the same time and return the same page. Every attempt lands in the audit chain — 'login.denied' on failure, 'login.ok' on success, 'login.await2fa' when a code is required — recording the actor and the client address only, never the password. The session cookie is HttpOnly, SameSite=Strict and Secure, lives eight hours, and slides forward with each request you make. Sessions exist only in server memory: restarting Chambers signs everybody out. A released seat cannot sign in, because the session lookup rejects any account that is not active.

Does not do

'Access denied.' is not diagnostic and is not meant to be. The same banner covers a wrong password, an unknown email, a released seat, and being rate-limited — you cannot tell which from the screen. There is no 'forgot password' link, because there is no password reset; see the recovery playbook. There is no lockout counter shown, no 'last signed in' notice, and no list of your active sessions anywhere in the application.

The authenticator step

Watch out

Sign-in attempts are rate limited to twenty requests per fifteen minutes per client address, and successful sign-ins are counted in that twenty as well. If the firm's proxy is not correctly identified to Chambers through CHAMBERS_TRUSTED_PROXY, every user shares one bucket and both seats can be shut out for fifteen minutes at once. When the limit trips you see the ordinary 'Access denied.' banner with no explanation; wait fifteen minutes rather than hammering the form.

The authenticator step POST /login/totp · verifyTotp() and consumeTotp() in kernel/auth.js · kernel/totp.js

The second factor at sign-in, shown only to an account that has enrolled an authenticator.

How to use it

After a correct email and password, the door is replaced by an identical-looking panel with one box, 'Authenticator code', which accepts exactly six digits, and a 'Continue' button. Read the current code from your authenticator app and enter it. On success you land on the Desk with a full eight-hour session.

Guarantees

This is standard TOTP: thirty-second steps, six digits, and a tolerance of one step either side, so a code that has just rolled over still works. A code that has granted access once can never grant it again — the matching time step is recorded on your account and any code from that step or earlier is refused, with 'totp.replay.denied' written to the audit chain. The half-finished login is held on the server for five minutes only, keyed by a token that is never stored in a cookie. Failed codes are audited as 'login.2fa.denied'.

Does not do

There are no backup codes, no recovery codes, no SMS fallback and no administrator override. If your authenticator is gone, this screen cannot be passed by any means, and the only route back into the firm is for the other administrator to release your seat and re-invite you. It also does not re-issue a code page on failure: a wrong or expired code drops you back to the email-and-password door with 'Access denied.', and you must type your password again before you get another chance at the code box.

Account security — the Password card

Watch out

The five-minute window between password and code is real. If you walk away mid-login you will be re-typing your password. Because the code page and the password page carry the same 'Access denied.' banner, a wrong code and a wrong password look identical on screen.

Account security — the Password card GET /account · POST /account/password · changePassword() in kernel/auth.js

The only way any password in Chambers is ever changed. It is yours alone: you change your own, and nobody changes it for you.

How to use it

Click 'account' in the top bar of any page. The middle card is headed 'Password' and has three boxes — 'Current password', 'New password (12+ characters)', and 'New password again' — and a 'Change password' button. Fill all three and press it. On success the page returns with the banner 'Password changed.' On refusal you get a red banner naming the reason: 'Current password is wrong.', 'Choose a password of at least 12 characters.', or 'The two new passwords do not match.'

Guarantees

The current password is required, so somebody who has stolen an open session on an unlocked laptop still cannot take the account over. The length is checked and the two new entries are compared before anything is hashed or stored, so a typo cannot silently become your new password. Both outcomes are audited: 'password.changed' on success and 'password.change.denied' on a wrong current password, so a run of denials against your account is visible in the chain.

Does not do

It does not sign out your other sessions. A session already open on another device keeps working for its full sliding eight hours after you change the password, and there is no 'sign out everywhere' control anywhere in Chambers. It does not check the new password against the old one, against a breach list, or for any complexity beyond the twelve-character floor. And it cannot be used by an administrator on someone else's behalf — the note on the card says so, and it is accurate: /admin has no control over anybody's credentials.

Account security — the Two-factor card

Watch out

If you believe a device has been stolen, changing your password is not enough on its own. Either have the other administrator release your seat (which kills your sessions on the next request from any device) or have the server restarted, which drops every session in the firm.

Account security — the Two-factor card POST /account/totp-start · POST /account/totp-confirm · POST /account/totp-disable

Where you attach an authenticator app to your account, and where you detach it.

How to use it

On /account the first card is headed 'Two-factor authentication' and shows either 'not enabled' or 'enabled — required at every sign-in'. To enable it, press 'Begin enrollment'. The page comes back showing a long base-32 secret in monospace and, beneath it, the full otpauth:// URI. Type or paste either into your authenticator app (Google Authenticator, 1Password and Aegis are all fine), then enter the app's current code in the 'Current 6-digit code' box and press 'Confirm & enable'. You will see 'Two-factor authentication enabled. It is now required at every sign-in.' To turn it off, use the second form on the card: enter a current code in 'Current code to disable' and press the red 'Disable 2FA' button.

Guarantees

Enrolment only completes after you have proved a working code, so you cannot lock yourself out by scanning a secret into the wrong app. Disabling also requires a live code, so an intruder with a hijacked session cannot strip the second factor off your account. Both events are audited as 'user.2fa.enabled' and 'user.2fa.disabled'. The confirming code is burned in the same way a login code is, so it cannot be replayed.

Does not do

There is no QR code — the page gives you the secret text and the otpauth URI, and you enter one of them by hand. Two-factor authentication is optional and nothing enforces it: an account with 2FA off signs in on a password alone, and no screen nags about it after the one banner at enrolment. There is no way to see or revoke enrolled devices, and no backup codes are generated at any point. Disabling requires a working code, which means a lost authenticator cannot be cleared here.

Firm administration — People and seat release

Watch out

Once you press 'Begin enrollment' there is no cancel button; the card keeps showing the pending secret and its confirm box until you confirm with a valid code. That is harmless — the secret stays visible on the page — but the only way out of the pending state is to complete enrolment. Enable 2FA on both seats: it is the single largest difference between a stolen password being an incident and being a disaster.

Firm administration — People and seat release GET /admin · POST /admin/deactivate · deactivate() in kernel/auth.js

The roster of the firm and the one control that frees a seat so a replacement can be invited.

How to use it

Go to /admin. The left card is headed 'People' and lists Name, Email, Role and Status for every account ever enrolled. An active account other than your own carries a red 'Release seat' button; your own row simply reads 'you'. Press 'Release seat' on the person whose seat is to be freed. On success the banner reads 'Seat released. You can now invite a replacement.' and their Status changes from 'active' to 'released'.

Guarantees

You cannot release your own seat: the attempt is refused with 'You cannot release your own seat — ask the other administrator.', so the firm can never be left with nobody able to invite anybody. A seat that is already released is refused with 'That seat is already released.' Releasing takes effect immediately and everywhere — the released account's sessions stop resolving on their very next request, on every device, and any calendar feed subscription they own starts answering 404. The release is written to the audit chain as 'seat.released'. Most importantly, the seat lock counts active people, so a release genuinely frees a seat for a new invite.

Does not do

It does not delete anything. The account record, its email and its name remain in the People table forever, and everything the person filed in matters stays exactly where it is. It does not restore: there is no 'reactivate' button anywhere in Chambers, so a seat released by mistake cannot simply be switched back on — the person must be invited again, and that produces a new account with a new internal identity. It does not touch ethical walls, matters, or anything else the released person was subject to.

Firm administration — Invites

Watch out

Because re-enrolment creates a genuinely new account, any ethical wall that screened the old account does NOT screen the new one. If you release and re-invite a lawyer who was screened off a matter, go to the Ethical walls card and raise the wall again against the new account before they sign in. The /admin page is invisible to non-administrators — it answers a plain 404, not an error — but both Dan and Matt hold admin, so either can do this to the other.

Firm administration — Invites POST /admin/invite · createInvite() in kernel/auth.js

Issuing an enrolment link to fill a free seat — a replacement for a departed partner, or a law clerk if the build has been configured with a seat for one.

How to use it

On /admin, below the People table, fill 'Email', optionally 'Name', pick a 'Role' from Lawyer, Law clerk or Administrator, and press 'Create invite'. On success you see 'Invite created — share the single-use link from the open invites list.' and an 'Open invites' table appears showing Email, Role and the link as /invite/<code>. Copy that path onto the front of your real site address and send it to the person. If no seat is free, the attempt is refused with 'Seat lock: this build is limited to 2 enrolled accounts.'

Guarantees

An invite is single-use and expires twenty-four hours after it is created. The role is validated against the three names in the drop-down, so a hand-crafted request cannot invent a role. Creation is audited as 'invite.created'. The seat lock is checked both when the invite is created and again when it is redeemed, so even several outstanding invites cannot together push the firm past its seat count — the first person to redeem takes the free seat and any other invite then fails with 'Seat lock: every seat in this build is already enrolled.'

Does not do

It does not send email; you deliver the link yourself. It does not let you revoke an invite — there is no delete button on the Open invites table, so a link you regret can only be waited out for its twenty-four hours. It does not show the full URL, only the path. It does not check the address you type: an invalid or already-used email is accepted at this stage, and an ordinary (non-seat) invite skips the duplicate-address check that a first-boot seat invite applies.

The two-seat lock

Watch out

An open invite link is a bearer credential to your firm's file system. Treat it exactly as you would a password, send it out of band, and tell the recipient to redeem it immediately. Note that the invite is unusable while both seats are filled, so the correct order is always: release the seat first, then create the invite.

Firm administration — Ethical walls POST /admin/wall · POST /admin/wall/remove · walls() and walledFrom() in kernel/api.js

Screening one lawyer off one matter completely, and lifting that screen when the conflict is resolved or the wall was raised in error.

How to use it

On /admin, the right-hand card is headed 'Ethical walls'. Existing walls are listed with the matter title, who is screened, the basis, and a red 'Lift' button on each row. To raise one, pick a matter from the 'Matter' drop-down, pick a person from 'Screen (deny all access)', type a short 'Basis' such as 'prior retainer at former firm', and press 'Raise wall'. You will see 'Wall raised. The screened user can no longer see or decrypt this matter.' To remove one, press 'Lift' on its row; the banner reads 'Wall lifted.'

Guarantees

The wall is enforced in the kernel before any key is unwrapped, so the screened lawyer never reaches the matter's data encryption key at all — this is not a hidden menu item, it is a refusal to decrypt. The matter vanishes from their matter list, from the quick-open palette, from firm-wide ledger totals and from ledger exports, and any attempt to name it directly is refused and audited as 'wall.denied'. The wall is invisible to the person it screens: the /admin walls table is built from a list that omits any wall screening its own viewer, so a screened lawyer does not even learn that the firm acts in the matter. That same rule protects the Lift button — a screened lawyer cannot lift the wall that screens them, and an attempt is refused with 'That wall is not yours to lift.' Screening yourself is refused outright, with 'You cannot screen yourself — you would not be able to see the wall to lift it. Ask the other administrator.' Both raising and lifting are written to the audit chain.

Does not do

It does not stop the other administrator from lifting the wall — with two seats, the unscreened one holds that power alone, and there is no second signature, no notice period and no confirmation dialogue. Lifting is instant and complete. It does not retroactively conceal anything the screened lawyer saw before the wall went up, and it does not narrow access by document or by room: a wall is all-or-nothing on the whole matter. The basis you type is stored (truncated at 500 characters) and shown to everyone who is not screened.

Firm administration — the Model gateway POST /admin/ai · kernel/api.js ai.chat()

The single, audited door through which any part of Chambers may talk to a language model. If it is off, nothing in the application can reach a model at all.

How to use it

On /admin, under 'Model gateway', the current state shows either 'off — no endpoint' or 'configured' with the model name and endpoint. Fill 'OpenAI-compatible endpoint (blank to disable)' — for example http://localhost:11434/v1 for a local Ollama — plus 'Model name' such as qwen2.5:14b, and 'API key (only if the endpoint needs one)'. Press 'Save gateway'. You will see 'Model gateway configured (settings encrypted at rest).' or, if you cleared the endpoint, 'Model gateway disabled.' A malformed endpoint is refused with 'Endpoint must be a full http(s) URL.'

Guarantees

There is exactly one code path to a model and it runs through this configuration; with no endpoint and model set, every request is answered 'No model endpoint configured (admin sets it at /admin).' Every call that does go out is written to the audit chain as 'ai.call' with the matter and the model name, and configuration changes are logged as 'ai.gateway.configured' or 'ai.gateway.disabled'. The settings, API key included, are stored in the firm's AES-256-GCM sealed log like everything else. A matter whose data-handling policy is set to forbidden (in the Moot Room) refuses model use entirely, and the refusal is audited as 'ai.denied.policy'.

Does not do

It does not make a remote endpoint private. Point it at a third-party service and client text goes to that third party; only a local endpoint keeps everything inside the building, and the note on the card says exactly that. It does not filter, redact or review what a room sends. It does not prevent an administrator from reconfiguring it at any time without notice to the other seat, beyond the audit entry.

Firm administration — the Audit chain panel GET /admin · auditTrail().verify() · kernel/audit.js

A one-line statement of whether the firm's tamper-evident record of who did what is still whole.

How to use it

At the bottom of the right-hand card on /admin, read the line under 'Audit chain'. It shows 'intact' or 'BROKEN' followed by the number of entries. The same indicator appears as a tile on the Desk, so you see it whenever you sign in. Check it; if it ever reads BROKEN, stop and treat it as an incident.

Guarantees

Every entry is chained to the one before it with an HMAC under a secret key held in the data directory at 0600, so the chain cannot be recomputed by anyone who can merely write the file. The count and final hash are separately anchored in a keyed head file written under the same lock, which means deleting entries off the end — the realistic insider move — makes the chain disagree with what was last recorded and reports BROKEN rather than a shorter, plausible history. Verification walks every link on each page load, so the number you see is checked, not cached. The chain records logins, denials, rate-limit trips, password changes, 2FA changes, seat releases, invites, wall denials, key events, ledger posts and model calls.

Does not do

It records metadata only. No client content, no document text, no citation string and no password ever enters it — so it will tell you that a matter was read or destroyed and by whom, never what was in it. It is evidence of tampering, not prevention: someone with file-level access can still damage the log, and this panel's job is to make that damage impossible to hide. The panel shows only the verdict and the count — there is no screen in Chambers that lets you read the entries themselves; that requires access to the audit.log file on the server.

Signing out

Watch out

A 'BROKEN' verdict has three ordinary causes worth ruling out before you assume malice: a restored or partial backup of the data directory, a hand-edited log, and an audit.key that no longer matches the log it is being checked against. All three are still incidents — a chain you cannot verify is a chain you cannot rely on in a discovery dispute.

Signing out GET /logout-form · POST /logout

Ending the session on the device in front of you.

How to use it

Click 'sign out' at the right-hand end of the top bar on any page. A blank page appears for an instant and submits itself, and you land back on the bare front door.

Guarantees

The session is deleted from the server's memory, not merely forgotten by the browser, so the cookie is worthless afterwards even if it was copied. The cookie itself is cleared with an immediate expiry. Because sign-out goes through a POST, and every state-changing request in Chambers is checked for same-origin, a link on another site cannot sign you out or act as you.

Does not do

It signs out this device only. Sessions on other browsers or machines keep running for their remaining eight sliding hours, and there is no control anywhere that ends them all. It does not lock the account, and it is not audited — sign-outs do not appear in the chain the way sign-ins do.

The two-seat lock

Watch out

Sessions slide: every request pushes the eight-hour expiry forward, so a tab left open on an unlocked machine stays valid indefinitely. Sign out, or lock the machine. If a device is genuinely lost, the reliable answers are a seat release from the other administrator or a restart of the server, which drops every session in the firm at once.

The two-seat lock SEATS / seatCap() / activeCount() in kernel/auth.js

The rule that makes Chambers a two-person firm and nothing else. It is the reason there is no signup page, and the reason a third simultaneous account is not merely discouraged but impossible.

How to use it

There is nothing to operate — the lock is simply a count. The build names its seats in code as 'Dan G:admin,Matt D:admin', giving a cap of two. Every attempt to create an invite compares the number of ACTIVE accounts against that cap and refuses if the firm is full, with 'Seat lock: this build is limited to 2 enrolled accounts.' Every attempt to redeem an invite checks the same thing again and refuses with 'Seat lock: every seat in this build is already enrolled.' To live within it, treat a seat as a thing that must be released before it can be re-issued.

Guarantees

With Dan and Matt both active, no third account can be brought into existence by any route in the application — not by an invite, not by an invite already outstanding, and certainly not by a stranger, because there is no signup page and no unauthenticated route that creates anything. The check happens twice, at issue and at redemption, so a stale invite cannot sneak past a filled firm. And because the count is of ACTIVE accounts rather than of accounts ever created, the lock is recoverable: releasing a seat lowers the count and immediately permits one new invite.

Does not do

It does not cap roles separately. The invite form offers Lawyer, Law clerk and Administrator, but the cap counts people, so while both seats are filled by Dan and Matt no clerk can be added either. It does not limit how many open invites can exist for one free seat, only how many can be redeemed. It does not stop an operator with shell access from changing CHAMBERS_SEATS and restarting to raise the cap — that is a deliberate, server-level act, and it is the only way to make Chambers a three-person firm.

Recovery: lost authenticator, forgotten password, departure

Watch out

The cap is read once at process start. Changing CHAMBERS_SEATS on a running deployment does nothing until a restart, and a restart also signs everybody out. Note too that adding a seat by that route does not mint a new seat invite — first-boot links are minted only once, so a third person would be brought in through an ordinary /admin invite.

Recovery: lost authenticator, forgotten password, departure POST /account/password · POST /admin/deactivate · POST /admin/invite · POST /invite/:code

The exact steps for the three things that will actually go wrong. Read this before you need it, because two of the three require the other lawyer to be reachable.

How to use it

FORGOTTEN PASSWORD, while you can still sign in: go to /account and use the Password card. That is the whole procedure. FORGOTTEN PASSWORD, when you cannot sign in: there is no reset. Ask the other administrator to release your seat on /admin, then to create an invite for your email, and enrol again through the link exactly as you did the first time — new password, new authenticator. LOST OR WIPED AUTHENTICATOR: identical procedure, and the only procedure — the other administrator releases your seat, invites you again, and you enrol and re-enable 2FA. Do it in that order: the invite is refused while your seat is still active. DEPARTURE: the remaining administrator presses 'Release seat' on the departing lawyer's row, which ends their sessions everywhere on their next request and kills any calendar feed they subscribed to, and then invites the replacement. BOTH LAWYERS LOCKED OUT AT ONCE: there is no path back through the application at all. That is the scenario your offline password manager and your authenticator backups exist to prevent.

Guarantees

Each of these three mishaps is survivable so long as one of the two seats can still sign in. A password can be changed by its owner with the current password in hand; a wall raised on the wrong person can be lifted by the other administrator; and a seat can be released and re-issued, which is what makes a lost authenticator and a departure recoverable rather than terminal. Every step is audited — 'password.changed', 'seat.released', 'invite.created', 'user.enrolled' — so the recovery itself leaves a record.

Does not do

Re-enrolment does not restore your old account. It creates a new one: new internal identity, same email if you choose, and none of the old account's ethical walls follow it. The old record stays in the People table marked 'released' and cannot be switched back on. No administrator can reset another person's password or clear another person's 2FA — release-and-re-invite is the only mechanism, and it is deliberately blunt. Nothing here recovers a destroyed matter: destroying a matter destroys its key and removes its records from the live store, and while pre-destruction backups still hold copies until they age out, there is no in-application undo.

Feeds into

Signing in

Watch out

Three practical rules follow. First, keep both authenticator secrets backed up somewhere independent of the phone — an authenticator app with its own encrypted backup, or the secret text stored in your password manager at the moment you enrol. Second, never let both seats go to one device: the entire recovery model rests on one of you being able to sign in. Third, after any release-and-re-invite, an administrator must revisit the Ethical walls card on /admin and re-raise any wall that applied to the person who came back, because the wall was attached to the account you just retired.

Intake Desk /r/intake

This is where a prospective client becomes a screening file, and where a screening file becomes a matter. It collects the six things that decide whether the firm can act and how long it has to act: who the client is, who is on the other side, which court's rules govern, what kind of claim it is, when the claim was discovered, and what happened. From those inputs it runs the limitation clock and holds the file open until the conflict check has been cleared in room 02. Duties to a prospective client attach at the first conversation, so the file starts here, not at the retainer.

How to use it

Fill the left-hand card, headed 'New inquiry'. 'Prospective client' is the only field the server insists on. 'Adverse parties' takes a comma-separated list and every name you type is split out and stored separately. 'Jurisdiction' is a dropdown of the seven jurisdictions the rulebook knows — Ontario (Superior Court of Justice), British Columbia (Supreme Court), Alberta (Court of King's Bench), Quebec (Cour superieure), Canada Federal Court, US Federal (FRCP) and New York (CPLR) — and it defaults to Ontario. 'Claim type' offers Commercial dispute, Personal injury, Employment, Estates, Real property and Other. 'Discovered' is the date the claim was discovered; it is what the limitation clock is run from. 'What happened' is free narrative. Press 'Open screening file'. The green banner that comes back tells you one of three things: the limitation date and the rule that produced it, or that you must enter a discovery date to run that rule, or that the jurisdiction has no limitation rule on file at all. The file now appears in the right-hand 'Screening' card. That card is sorted by urgency — the closest limitation date first, files with no date at the back — and its heading turns red when any open file is within ninety days of expiry. Each screening card repeats the limitation date with the rule citation beside it, shows the conflicts position (either 'cleared' or 'waiver on file' with the date the run was made and who made it, or a red 'not cleared' chip with a link reading 'run the check in room 02'), and lists the adverse parties, the discovery date and your summary. Two buttons sit at the bottom: 'Accept — open matter' and 'Decline'. The Accept button is rendered in red while the file is uncleared, and pressing it then produces a red refusal banner naming the client. Once a clear or waiver run is on file, press 'Accept — open matter': the room creates a matter titled '<client> — <claim type>', copies across the client, the adverse parties and the jurisdiction, sets it open and pre-filing, mints its encryption key, and — if a limitation date was computed — writes a deadline reading 'Limitation period expires' into that matter's encrypted scope, triggered 'Claim discovered <date>'. 'Decline' needs no clearance: it marks the inquiry declined and generates a non-engagement letter record addressed to the client. Both outcomes drop the file into the 'Disposed inquiries' table at the foot of the page, which shows Client, Claim, Jurisdiction, Limitation and Outcome. One thing the page does not do for you: accepting does not open the new matter in the application. To work in it, pick it from the matter dropdown in the top bar and press 'Open'.

Guarantees

An inquiry with no client name is refused. A discovery date that is not a real calendar day — the classic '2026-02-31' — is refused with a red banner and no record is written; the clock is never run from a day the client did not live. The limitation date is computed by the shared rulebook (kernel/rules.js), and because the rule carries category 'limitation' the computed date is returned with NO weekend or holiday roll: a limitation date that falls on a Saturday stays on that Saturday, because rolling it forward would manufacture a statute-barred trap. Where the clock could not be run, the record says why in words rather than sitting silently empty: 'none — no rule on file, counsel to diary manually' where the jurisdiction has no limitation rule (Canada Federal Court and US Federal are both in that position), or 'not run — no discovery date recorded, counsel to diary manually' where the rule exists but no trigger date was given. Acceptance is gated: the room refuses to create a matter unless a conflictRun with outcome 'clear' or 'waiver' exists that ties to this inquiry by id, or names the client among its parties, or was run on the client's exact name. A refusal writes an audit line 'intake.accept.blocked'; a successful acceptance writes 'intake.accept' with the inquiry and matter ids. The limitation deadline it writes carries the rules.js rule id whenever that id resolves to a real rule and omits the field entirely otherwise — it never writes a placeholder id — which is what makes the date visible to the firm-wide dual-diary control in Workflow (room 27).

Does not do

It does not give you legal advice about the limitation period, and the date it prints is the output of one hard-coded rule per jurisdiction with a fixed day count. Claim type is collected but has no effect anywhere except New York: in Ontario, British Columbia, Alberta and Quebec every claim type — including 'Real property' and 'Estates' — gets the single basic limitation or prescription rule for that jurisdiction. In New York the only split is personal injury (CPLR 214(5), three years) against everything else (CPLR 213(2), six years), so an Employment, Estates or Real property inquiry in New York is dated on the six-year contract rule. Nothing here models the ultimate limitation period, municipal or Crown notice periods, wrongful-death or estate variations, real-property limitation statutes, minority or incapacity suspension, fraudulent concealment, or any discoverability argument. It does not warn you when the computed limitation lands on a weekend or a court holiday, even though the rulebook can detect that and the Trial Calendar does warn — so you must check that yourself and confirm any statutory extension. The clearance gate checks only the CLIENT's name: nothing requires that any adverse party has ever been screened, and a matter can be opened with the other side unchecked. There is no way to edit or reopen an inquiry — if the discovery date, jurisdiction or claim type was wrong, or the discovery date was left blank, the limitation date cannot be recomputed here and no deadline is written at all; nothing later reminds you that the file has no limitation entry. Nothing sends the non-engagement letter, and, more sharply, no screen in this application will show it to you again: it is stored, but the only surface that lists letters is room 02, and that surface lists conflict-waiver letters only. Accepting does not open the matter, does not draft a retainer, and does not create any calendar entry other than the single limitation deadline.

Feeds into

The matter record it creates is the file every other room works in, and its encryption key is minted at that moment. The limitation deadline it writes is read by Trial Calendar (21) and by Workflow (27), where it is flagged LIMITATION and carries the dual-diary tick that a second lawyer must apply; by Jurisdiction Desk (09), which marks it stale if the matter's jurisdiction changes; by the Client Portal (36) key-dates list; by the ICS calendar feed; and by the Closing Room (26) transfer bundle. The inquiry record itself is read by Ethics & Conflicts (02), which screens every inquiry's client and adverse parties whatever the inquiry's status, by Retainer (03), which uses the originating inquiry to find the conflict run that clears the matter, and by Workflow (27), whose 'In screening' figure counts inquiries still in screening and links back here.

Watch out

The limitation rules count calendar DAYS, not calendar years: 730 days for a two-year period, 1095 for three, 2190 for six. In a window containing a leap day the computed date therefore falls one or two days BEFORE the anniversary — a discovery date of 2024-01-10 in Ontario produces 2026-01-09, and 2020-01-01 in New York on the contract rule produces 2025-12-30. That errs early, which is safe, but it is not the statutory anniversary and you should not quote it as one. The route that accepts an inquiry does not check the inquiry's status before acting, so re-submitting that POST (a browser back-and-refresh on the confirmation) would create a SECOND matter with a second key and a second limitation deadline and re-point the inquiry at it; the rendered page gives you no button to do this, but do not resubmit. Declined and accepted inquiries stay in the conflicts search graph for ever, which is deliberate — a prospective client you turned away is still someone the firm must screen against. The disposed table's 'accepted' row says 'matter opened' but gives you no link to the matter.

Ethics & Conflicts /r/conflicts

This is the party graph and the screen. It holds every name the firm has touched — clients, adverse parties, related entities, insurers, witnesses, lateral hires and their aliases — and checks a new name against all of them. Its output, a recorded run with a human decision on it, is the key that unlocks both downstream gates: no matter opens in room 01 and no fee agreement executes in room 03 without one. It also holds the continuous side of the duty: a firm-wide re-screen of every past run, a watch list, and the waiver letter for a consentable conflict.

How to use it

The top-left card is 'Run a conflict check'. Type the name into 'Name to clear', then choose in 'Clearing for' which file the run is for — the dropdown offers 'Firm directory (unattached)', every matter you can see, and every inquiry still in screening; it defaults to the matter currently open in the top bar. Press 'Check against everything on file'. If there are no hits the run is recorded 'clear' immediately, with no human step. If there are hits the run is recorded 'pending' and appears at the top of the 'Conflict runs' table — pending runs always sort first — showing the name checked, the file it was tied to, and each hit with the role it came in as, the matter or inquiry it came from, and the exact tokens that matched. Three buttons sit under a pending run: 'clear', 'waiver needed' and 'declined'. Pressing one records your decision with your name and the time. Pressing 'waiver needed' also carries you straight to the waiver letter form at the bottom of the page with the run's own particulars filled in — the conflicting party in 'Conflicting party / other client', and the client of the tied matter or inquiry in 'Consenting client'. Add a 'Matter description' and press 'Generate waiver letter'; the letter is stored and the three most recent are printed in full underneath the form, ready to print from the browser. The second card, 'Record a party', is how you put a name into the graph that is not yet a client or an adverse party on any file: 'Name', 'Aliases / former names' (comma-separated), a 'Role' from Client, Adverse party, Related entity, Corporate parent, Insurer, Witness or Lateral hire, and 'Attached to' using the same file dropdown. A recorded party is listed under 'Awaiting re-check' until some run happens after it was added, and that row carries its own 'Run check' button pre-filled with the name and file. 'Firm-wide re-screen' has one button, 'Re-screen every stored run': it re-runs every stored run's name against today's graph and lists only the hits that were not there before, per run, each with the same decision buttons so you can re-resolve it. 'Watched names' takes a bare name and a 'Watch' button; each watched name is re-checked and its current hits shown every time this page is drawn, and 'Remove' deletes the watch. The 'Screens & walls' card at the bottom right counts runs, undecided runs and parties, and gives administrators a link to /admin to raise an ethical wall.

Guarantees

Every run, every outcome, every re-screen and every watch is written to the tamper-evident audit chain, with the hit count and the file the run was tied to. The stored hits are the evidence of what the check saw at the time. A name with nothing matchable in it — nothing left after lower-casing, stripping accents and punctuation, dropping tokens shorter than three characters and dropping corporate noise words — is refused rather than recorded as a clean check. No outcome is ever changed by the machine: the firm-wide re-screen reports new hits and stops, leaving the decision to a person. Ethical walls are honoured throughout: the candidate list is built from matters you are entitled to see, parties attached to a matter you are screened from are excluded, stored hits whose source is a matter you are screened from are dropped before the page renders, and a run tied to a walled matter shows no matter title. A run recorded 'clear' or 'waiver' is what the intake and retainer gates read.

Does not do

The matching is exact token overlap and nothing else. The room says so itself: probabilistic record linkage is not implemented. 'Jon' does not match 'John', 'Bob' does not match 'Robert', 'Smyth' does not match 'Smith', and any typo misses. Tokens of one or two characters are dropped entirely, so a two-letter surname such as Ng, Li or Ho is unmatchable and cannot even be run on its own. Corporate noise words (inc, llc, llp, ltd, lp, plc, corp, corporation, co, company, holdings, group, limited, partners, partnership and a few others) are stripped before matching, so two unrelated 'Holdings' companies will not collide — but common geographic and generic words such as Canada, Ontario or National are NOT stripped and will generate hits that mean nothing. The search covers only what is inside this installation: matters, inquiries and parties you have entered. There is no corporate registry lookup, no former-firm data, no external conflicts database, and nothing is imported when a lateral joins beyond the names you type in. It does not detect positional or issue conflicts, does not consider the lawyers' own interests, and does not decide anything — 'clear' on a run with hits is entirely your judgment. If you are screened by an ethical wall from a matter, that matter's names are invisible to your search, so your run can come back 'clear' when a real conflict sits behind the wall; the banner reading 'clear against every matter, inquiry and party on file' means everything YOU can see. Generating a waiver letter is not consent: nothing sends it, nothing records that it came back signed, and nothing checks for a signature before the downstream gates open. Marking a run 'waiver needed' opens the intake and retainer gates at once, whether or not the letter is ever written. The firm-wide re-screen runs only when someone presses the button — there is no schedule and no alert.

Feeds into

A run marked 'clear' or 'waiver' is the key to two gates: Intake (01) refuses to open a matter without one for the prospective client, and Retainer (03) refuses to record an engagement as signed without one for the matter. Waiver letters are stored firm-wide and are displayed only here. The party graph feeds every later run, including the firm-wide re-screen and the watch list. Ethical walls themselves are raised in firm administration at /admin, not in this room; this room only respects them.

Watch out

A check with zero hits is recorded 'clear' automatically, and that automatic clear is enough to open both downstream gates — a run nobody looked at can unlock the file. The 'Awaiting re-check' list watches recorded PARTY records only: a new inquiry or a new matter, and the adverse parties on them, join the search graph immediately but never show up in that list, so 'graph screened' does not mean everything new has been through a run. The re-screen compares hits by name, role and source label, and the source label for a matter contains the matter's title — retitling a matter can therefore surface an old hit as a 'new' one. Watched names are recalculated only while this page is being drawn; nothing pushes an alert to you anywhere else in the application.

Retainer /r/retainer

This room holds the engagement terms for the open matter: what the firm will do, what it expressly will not do, and on what fee basis. It generates the engagement letter from those fields, tracks it through drafted, sent and signed, and refuses to record a signature on a matter the firm has not cleared for conflicts. Terms are versioned and never edited: a scope change is a new version, and the prior one is marked superseded with its text intact. The signature is also the moment the money side of the firm learns what the client agreed to.

How to use it

Open a matter in the top-bar dropdown first — with no matter open the room only tells you to pick one. The right-hand card is the editor. 'Scope in — what we will do' is required and becomes section 1 of the letter. 'Scope out — expressly excluded' becomes section 2; if you leave it blank the letter says so in terms, recording that work outside section 1 needs a further written engagement. Choose a 'Fee model' — Hourly rate, Flat fee or Contingency % — and then fill only the matching box of the three that follow ('Hourly rate $', 'Flat fee $', 'Contingency %'); the other two are ignored and stored as null. A standing note under the form points at the Ontario contingency rules (Solicitors Act s. 28.1 and O. Reg. 563/20) and tells you to verify the governing jurisdiction's current rules before sending. Press 'Draft engagement v1'. The left-hand card now shows the current engagement: version and status, the conflicts position, the fee, both scopes, and the drafted, sent and signed dates. Below the cards, the full engagement letter appears exactly as it was generated, with a 'Print / save as PDF' link — printing drops the chrome, the forms and the version history and sets the letter in a serif face. To advance the file, use the single form in the current-engagement card: it shows a date field defaulting to today and one button, first 'Record sent' and, once sent, 'Record signed'. Clear the date field to date the step today, or type the real date it happened. If the matter has no cleared conflict run, a red 'conflicts gate' notice sits above the button, the button itself is red, and pressing it produces a refusal banner and no change. Once signed, the card reads 'Signed and in force' and the editor's button changes to 'Issue new version — supersede current'. Every version is listed in the 'Versions' table at the foot of the page with its status, fee, dates, supersession and scope.

Guarantees

Scope in and a fee model are required, and each model is validated on its own terms: hourly needs a positive rate, flat needs a positive amount, contingency needs a percentage above zero and no more than one hundred. Versions are immutable — issuing a new version marks every prior non-superseded version 'superseded' with the date and the superseding version number and leaves its text alone. The letter text is generated at creation from the record and stored on it, so what was sent is what stays on file. Status moves strictly draft to sent to signed; any other transition is refused with a banner. A typed date that is not a real calendar day is refused rather than rolled forward. The signing gate is real: the room refuses to move an engagement to signed unless a conflictRun with outcome 'clear' or 'waiver' ties to this matter, to the inquiry it was opened from, or to the client's name, and a refusal is audited as 'engagement.sign.blocked' with no signature and no marker written. A recorded signature stamps the signer's name onto the version and posts a firm-scope marker carrying the matter, engagement id, version, fee model, the one relevant figure, the expected retainer where the model is flat, and the signing date and signer. If that marker write ever fails, the next visit to this room backfills it — but the backfill only mirrors a signature that already exists; it can never perform one, so the conflicts gate cannot be walked around that way.

Does not do

It does not capture a signature. 'Record signed' is a bookkeeping entry made by whoever is logged in; there is no e-signature, no upload of the executed copy, no client acknowledgment, and no check that the letter was ever sent to the client at all. It does not transmit the letter — printing or saving a PDF and sending it is yours to do. It does not check that the sent date precedes the signed date, and it does not reject a date in the future. There is no unsign and no undo: a mistake is corrected only by issuing a new version. It does not stop anyone recording time or issuing an invoice before an engagement is signed — Billing falls back to hourly at each time entry's own rate when nothing is signed, and Trust & Books simply reports that there is no signed engagement on file. It does not carry the hourly rate into billing either: invoices take the rate from each time entry, not from this letter, so changing the rate here changes nothing about what is billed. It does nothing to check that the work actually done stays inside the scope you described.

Feeds into

Billing (34) reads the engagement records in the matter to decide the fee model behind every invoice: newest signed version by version number wins, failing that the newest version of any status, failing that a default of hourly with no engagement on file. Trust & Books (28) reads the firm-scope marker this room posts on signature to show the 'Fee commitment' card, and where the model is flat it treats that amount as the expected retainer and raises a REPLENISH flag when the trust balance falls below it. The conflicts clearance it reads comes from Ethics & Conflicts (02); the matter and, where there was one, the originating inquiry come from Intake (01). Every draft, supersession, signature and blocked signature is written to the audit chain.

Watch out

Drafting a new version has an immediate effect on billing that the screen does not warn you about. Issuing v2 marks the signed v1 'superseded', and Billing's fee-model lookup counts only versions whose status reads 'signed' — so the moment you draft v2 there is no signed version, and Billing falls back to the newest version of any status, which is the unsigned v2. A scope change you have merely drafted therefore re-prices the next invoice before the client has agreed to anything. Trust & Books does not follow it, because the signature marker for v1 is never removed, so the two rooms will disagree until v2 is signed. Separately: the date printed at the top of the letter is the DRAFTED date and is never regenerated, so a letter printed after signature still carries the drafting date; the letter's 'Yours truly' names the lawyer who drafted it, while the signer recorded on the record is whoever pressed the button; and the printed letter is always the current version only.

Case Value /r/value

This is the money before the case: a scratchpad for modelling what the matter is worth, deliberately banded rather than pointed, because a point estimate on a case value is a number that will be quoted back to you under oath. It takes your own damages range, your own view of liability and your own costs figures and returns expected recovery, net if tried, net under a contingency, and a settle-versus-try comparison against any offer on the table. Several scenarios can sit side by side so the question 'which one' is a scan rather than a read.

How to use it

Open a matter in the top bar first. In 'New scenario', give the scenario a name (optional — it stores as 'Unnamed scenario' if you leave it) and fill the three required damages figures, 'Damages — low', 'Damages — likely' and 'Damages — high', plus 'Liability (%)'. 'Costs to date' and 'Budget to trial' are optional and treated as zero when blank. 'Contingency %' should be left blank on an hourly retainer. 'Offer on the table' should be left blank if there is none. Press 'Model it'. The card beside the form, 'How the bands are built', states the four formulas the room uses, and the room applies exactly those: expected recovery is each damages figure multiplied by the liability percentage, giving P-low, P-mid and P-high; net if tried subtracts costs to date and budget to trial from each of those; net to the client under a contingency multiplies each by one minus the fee percentage; and settle net is the offer minus costs to date only. Each scenario then appears as its own card showing the damages band, the liability percentage, the costs arithmetic, the expected recovery band, a P-low/P-mid/P-high table, and a plain-language settle-versus-try paragraph with a chip reading 'above the whole try band', 'above mid band', 'inside the try band' or, in red, 'below the try band'. Where there are two or more scenarios a comparison table appears above the cards with one row each — scenario name (linking down to its card), damages band, liability, expected P-mid, net if tried at P-mid, the offer and the same chip. 'Remove scenario' at the foot of a card deletes it immediately, with no confirmation step. There is no print button, but Ctrl-P produces a clean valuation sheet headed 'Case valuation — <matter> — as at <today>' with the forms and buttons dropped.

Guarantees

The inputs are validated before anything is stored: the three damages figures and the liability percentage must be numbers and are required; damages must run low no greater than likely no greater than high, all zero or more; liability must be between zero and one hundred; costs to date and budget must be numbers of zero or more; contingency must be between zero and one hundred or blank; an offer must be zero or more or blank. Anything else is refused with a red banner and nothing is written. Nothing is invented: every figure on the page is arithmetic on the numbers you typed, recomputed at display time from the stored inputs, and the room says outright that comparable verdict and settlement data is not implemented. Recovery is always presented as a band, never as a single number. Scenarios are stored inside the matter's encrypted scope under its own key, and creation and deletion are written to the audit chain.

Does not do

It has no comparables, no verdict database, no venue or claim-type benchmarks, and no model behind the numbers — the liability percentage is a multiplier you supplied, not a probability anything computed. It does not model offer-to-settle cost consequences (Ontario r. 49.10 and its equivalents); the room points you at Mediation & ADR (23) for that. It does not model prejudgment or postjudgment interest, costs awards or partial-indemnity recovery, tax, structured settlements, the time value of money, or the defendant's ability to pay. The contingency line does not deduct disbursements or liens — that arithmetic lives in Settlement Waterfall (24) — so the 'net to client' row is gross of both. The settle line subtracts only costs to date, never the budget to trial, so it is a snapshot of stopping now. Nothing in this room reads the signed engagement: the contingency percentage is typed here by hand and can differ from the retainer the client actually signed. And nothing outside this room reads the scenarios: they are not on the Client Portal, not in the Closing Room transfer bundle, and not referenced by Billing or the Waterfall.

Feeds into

Nothing. The scenario records are written and read only by this room. Their practical audience is the lawyer preparing to advise on settlement, and the numbers must be carried by hand into Mediation & ADR (23) for the offer-to-settle analysis and into Settlement Waterfall (24) for the actual distribution.

Watch out

'P-low', 'P-mid' and 'P-high' are simply your low, likely and high damages figures scaled by the liability percentage — they are not percentiles from any distribution, and nothing about them is probabilistic. Negative results render with a leading minus sign, which is exactly what you want to see when the budget to trial exceeds the expected recovery, and that case is common enough to be the point of the room. Because costs to date are subtracted on both sides, the settle-versus-try comparison is only apples to apples if the offer you entered is on the same basis as the damages you entered. Deleting a scenario is instant and unconfirmed.

Client Desk (Room 05) /r/client

This is the written record of what you told the client, what the client decided, and what the file has cost so far. It exists so that the two things clients most often dispute — "nobody told me" and "I never agreed to that" — are answered from the file rather than from memory. It also holds the single budget figure the whole product measures actuals against. Everything on this screen is scoped to the matter currently open; with no matter open the room shows only a prompt to open one through Intake (01).

How to use it

The page opens on two cards. On the left, "Send a status update": type into the box labelled "Update — plain language", confirm or change "Date sent" (pre-filled with today) and "Sent by" (pre-filled with your own name), and press "Record update". The room scores the reading level as it saves and flashes it back to you — anything over grade 9 comes back with a prompt to shorten sentences. On the right, "Budget vs actual" prints seven lines: Budget / retainer, Fees taken to income, Disbursements, Unbilled time (WIP), Actual to date, Remaining, and Held in trust. Under them is a single field, "Budget / retainer figure"; type a positive number and press "Save figure on matter" (the button reads "Update figure" once a figure exists). Below the cards, the "Status updates" heading carries a cadence chip — "no update sent yet", "last update N days ago", or a red "N days since the last update" once you pass thirty — followed by a table of every update, newest first, with its date, full text, reading-level chip and author. Last comes "Decision memos — the calls that are the client's to make": fill in "Decision put to the client" (required), optionally "Options explained (one per line)", then "Client's decision" (required), "Date decided" and "Authority recorded by", and press "Record decision". Recorded memos print underneath in a table with the client's decision in bold.

Guarantees

An update with no text is refused. A memo missing either the question or the client's decision is refused — you cannot record an open question here as though it were an instruction. Both date fields are round-tripped through a real calendar: "2026-02-31" is rejected with an error rather than silently rolled to March 3. The budget field refuses anything that is not a positive finite number and stores it rounded to two decimals on the matter record. Every figure in the budget card is computed live at page render from the encrypted ledger (fees taken to income, disbursements, trust:bank balance) and from unbilled time entries — none of it is stored, so it cannot go stale, and hours and rates are each coerced through Number(x) || 0 so a corrupt entry reads as zero rather than printing NaN. Both writes go through the per-matter encrypted scope and are therefore audited like every other record.

Does not do

It does not send anything. "Record update" writes a file note; no email, letter, portal message or notification leaves the building. If you record an update and never actually send it, the software will tell you the client was updated and the client will not have been. The room's own note says the reminder and EN/FR delivery pipeline is unbuilt (Build Sheet 05). There is no edit and no delete route for either an update or a decision memo — a typo, a wrong date or a misattributed instruction stands on the record permanently. The reading grade is a crude inline approximation (0.4 × (average words per sentence + 100 × the proportion of words with 7 or more letters)); it has no corpus, no legal-vocabulary awareness, and it is not a plain-language compliance test — it will happily score an incomprehensible sentence at grade 6. The 30-day cadence is the firm's own house standard, not a rule of any kind, and it is measured from the "Date sent" you typed, so backdating an update silences the chip. The budget figure is not a cap: nothing anywhere refuses to bill, disburse or work past it; "OVER BUDGET" is a coloured chip and nothing else. "Held in trust" is displayed for context only — no money can be moved from this room.

Feeds into

The Client Portal (36) builds its client pack from here: it takes the newest clientUpdate by sentOn (falling back to createdAt) as the pack's status section, recomputes the reading grade with a byte-identical copy of this room's function, and reads matter.budget for the pack's budget block. Answered decision memos also close out matching open decision requests in 36 — the match is on a normalised question string and the memo must post-date the request, so a question re-posed after an earlier answer is asked again rather than dropped. The budget figure written here is stored on the matter record itself in firm scope, so it survives independently of this room.

Watch out

The "Reading level" column recomputes the grade from the stored text every time the page renders — it does not display the grade field that was saved with the record. Today the two agree; if the formula is ever changed, historic rows will silently re-score. A question still waiting on the client does not belong here: this room refuses a memo without a decision, and an open question must be raised as a decision request in Client Portal (36). Note also that "Actual to date" adds unbilled WIP to fees already taken to income, so it will usually exceed anything the client has yet been asked to pay.

Chronology (Room 06) /r/chronology

The sourced fact timeline for the matter — the spine every later room hangs off. Its governing rule is source-or-drop: a fact does not enter the record without a pin to where it comes from. It exists so that when you plead an element, outline a cross-examination or draft a statement of facts, every proposition already carries the exhibit, transcript line or document id that proves it, and so that the silences in the record are visible rather than assumed away.

How to use it

With a matter open you get two cards. "Add a fact" takes "Date of fact" (a date picker, required), "Actor (who did it)" (required — e.g. "Harness Holdings", "J. Doe"), "The fact — one sentence, past tense", "Source pin (required)" (free text: "Ex. 4 p.2", "Doe transcript 41:12", or an Evidence Room document id), a "Disputed?" selector defaulting to "Undisputed", and "Issue tags (comma-separated)". Press "Enter fact" and the flash confirms the pin it was filed under. "State of the record" beside it prints chips for the total fact count, undisputed and disputed counts, gap count, and the date span, plus two filter selects — "Filter by actor" and "Filter by issue", both populated from what is actually on the file — and an "Apply filter" button. Below is the timeline table: Date, Actor, Fact, Source pin, Issues, Status, and per-row controls. The actor cell and each issue tag are clickable filters, and clicking one preserves whatever other filter is already set. The last column gives each row a "mark disputed" / "mark undisputed" toggle and a red "drop" button. Where more than 90 days pass between two consecutive facts, a red "gap — N days" row is inserted asking what happened in between. The button "Statement of facts →" opens /r/chronology/narrative: the same facts rendered as numbered paragraphs — "On 2026-03-04, J. Doe: …" with the source pin in brackets and "[disputed]" where applicable — with its own "Actor contains" / "Issue contains" filter boxes and a "Print / save as PDF" button.

Guarantees

No fact enters without a pin. POST /add refuses an empty source with an explicit source-or-drop refusal, refuses empty fact text, and refuses any date that is not a real YYYY-MM-DD calendar day — the date is round-tripped through Date, so an impossible date like 2026-02-31 is rejected outright rather than rolled forward into a day that reorders your timeline. An actor left blank is stored as "Unattributed" rather than empty. Gap detection is computed over the full timeline and is deliberately suppressed while any filter is on, so a filter can never invent a gap that is not in the record; the room says so in a note at the foot of a filtered view. Both the on-screen filtered header and the printed Statement of Facts stamp themselves as a filtered extract — the print header reads "FILTERED EXTRACT … not the whole chronology" — so a partial print cannot be mistaken for the complete record.

Does not do

It does not check your pin. The source field is free text and is never resolved, validated or matched against a document in the Evidence Room — "Ex. 4 p.2" and "see file" are equally acceptable to the software. Source-or-drop guarantees that something was typed, not that it is true or that it exists. It does not check the fact against anything: nothing verifies your date, your actor or your sentence, and "undisputed" means only that nobody has clicked the toggle. Marking a fact disputed has no gating effect anywhere — no room refuses to plead, brief or file on a disputed fact. The 90-day gap threshold is a fixed house heuristic, not a legal standard, and it detects only silence between facts you have already entered; it cannot know about the period before your first fact or after your last. There is no edit route — a fact can only be dropped and re-entered, and dropping is immediate with no confirmation step.

Feeds into

Pleadings (10) lists these facts to map to the elements of each cause of action, and its POST /link refuses to map an element to anything that is not a real fact id in this matter — so element support inherits source-or-drop. Depositions (14) pulls facts into a witness outline by fuzzy-matching the fact's actor against the witness name, carrying the source pin forward, and stores a fact id on an impeachment digest as contraFactId. Closing (26) exports facts in the matter transfer bundle. Nothing writes facts back into this room.

Watch out

The two filters are not the same filter. On the timeline the actor filter is an exact string match and the issue filter is exact membership in the tag list; on the Statement of Facts page both are case-insensitive substring matches. The "Statement of facts →" button carries the timeline's filter values straight into that page, so a printed extract can contain more facts than the filtered screen you clicked from showed (filtering the timeline on "J. Doe" then printing will also pull in "J. Doe Jr."). Check the count in the print header against the count on the timeline before you rely on an extract. Dropping a fact is silent downstream: if that fact was mapped to a cause-of-action element in Pleadings (10), the mapping is simply skipped at render, and the element can flip from "supported" to "no factual support yet" with no warning here and no notice there.

Research Desk (Room 07) /r/research

Per-matter legal research on the record: an issue framed as a question, a conclusion recorded against it, and the authorities weighed under it. Its organising principle is the candour duty — authority that cuts against you renders first, at the top of the page, before your own memos, and stays there until the memo deals with it. It is also the on-ramp to the citation gate: an authority you intend to cite is sent from here into Citation Check (08) against a named draft.

How to use it

With a matter open, any adverse authority on file appears first in a bordered "Adverse authority" card tagged "candour duty". Below that, "Frame a new memo" takes "Issue as framed" (required) and "Conclusion (leave blank if still open)", with an "Open memo" button. Beside it, the "Desk state" card counts memos, unresolved memos, authorities, binding authorities and adverse authorities, and — if any are pending — shows a red "N awaiting citation check" chip that links to room 08. Memos then print as cards, unresolved ones first, each showing Issue, Conclusion (or a red "unresolved" chip), when it was framed, and its authorities table. Inside each memo card, the "Add authority" disclosure holds the entry form: "Citation string" (required), "Court", "Year", a "Weight" selector ("Binding on this court" / "Persuasive only", defaulting to binding), an "Adverse?" selector ("Supports our position" / "Adverse — cuts against us"), and "Proposition it stands for" (required) — then "Cite it". A second disclosure, "Record conclusion" (or "Revise conclusion"), takes the conclusion text and "Save conclusion". In each authority row the "Citation check" cell holds a small drop-down reading "— which draft cites it? —" listing every draft on the matter, with a "send" button; picking a draft and pressing send mints the citation instance in room 08. Once sent, the cell instead reads "in citation check" with an "open the gate →" link. Each row also has a red "drop".

Guarantees

An authority is refused without both a citation string and a proposition — the room's refusal message is that without a proposition "that is a citation, not research". A year must be exactly four digits or blank. An authority must be filed under a memo that actually resolves, and a memo is refused without an issue. POST /conclude refuses an empty conclusion rather than blanking one you already recorded. Adverse authority is sorted to the top of the page by construction, then binding before persuasive, then oldest first. Sending to the gate is hard-gated on a draft: the selector has no default and the route refuses a blank one, because an instance with no draftId can never be counted by the gate in 08 nor verified by anyone. Double-sending is refused once the authority carries a check id. A connector row — an authority pulled in by CanLII (29) or CourtListener (30) — is refused outright at send: you must re-enter it under a memo with the proposition it stands for first. The room honours 08's per-draft, case-insensitive duplicate guard from this side: if that citation is already queued on that draft, your authority is linked to the existing instance instead of minting a second row. And if the draft you send against was already reading "clear", this room immediately moves it to "blocked" and writes an audit line (research.gate.blocked) — it can push the gate shut but never open it.

Does not do

There is no search here. The room fetches nothing, searches nothing and suggests nothing; every authority is typed in by hand, and its own note says retrieval against CourtListener/CAP is unbuilt (Build Sheet L07). It does not check that the case you typed exists, that the citation is well-formed, that it is binding on the court you named, or that your proposition is what the case holds — "binding" and "adverse" are your assertions, stored as you made them. Marking an authority adverse does nothing except move it to the top of this page: no room refuses to file, brief or argue because adverse authority is unaddressed, and nothing checks that your memo actually distinguishes it. An "unresolved" memo blocks nothing anywhere. Dropping an authority deliberately does not remove its citation instance from room 08 — the draft stays blocked until someone verifies or fails it there, precisely so that deleting a row here can never be a way to clear a blocked draft.

Feeds into

POST /send writes a citation_instance carrying draftId, status 'unverified' and source 'research' — the same shape room 08 mints for itself, so it appears in 08's verification queue tagged "from Research (07)" and counts in 08's gate arithmetic exactly like an extracted cite. It stamps the authority with checkId and draftId. Every authority written here carries source: 'research'; rooms 29 and 30 stamp their own connector rows differently and this desk filters them out of its own tables, counting them instead in a note that points at their rooms. Closing (26) exports citation instances in the transfer bundle.

Watch out

The draft selector labels a draft "— gate currently clear" where it is; sending to such a draft will shut that gate immediately, which is intended but will surprise you if you were about to file. The desk-state chip "N awaiting citation check" counts only instances this room sent (source 'research') that are still unverified — it is not a count of everything blocking your drafts, and citations extracted in room 08 never appear in it. If the matter has no draft at all, no send button is offered anywhere on the page; the note on the desk-state card tells you to register one in Citation Check (08) or send one from Brief Writer (18) first.

Citation Check (Room 08) /r/citations

The blocking gate. A draft does not leave this room while any citation in it is unverified or failed, and the Filing Room reads the flag this room sets. It exists to stop a hallucinated, misquoted or overruled citation reaching a court — the failure that produces the reported decisions the room's own code cites (Ko v. Li, 2025 ONSC 2766; the Federal Court's Notice on the Use of AI). Its founding rule is that nothing here verifies anything by machine: extraction is deliberately over-broad, and every row is cleared by a named human making four confirmations at once.

How to use it

Open the room with a matter selected. The "Draft gate board" lists every draft on the matter with its citation count, unverified count, failed count, a gate chip, an "open queue →" link and — where the gate is genuinely clear — a "Print certificate →" link. If no draft is selected, or you want to gate something that did not come from Brief Writer, use "Register a draft for checking": "Draft title" and "Draft text" (paste the body), then "Register draft". Once a draft is open, its card shows Unverified, Failed and Verified counts, "Last extracted", and the draft's character count, with a button reading "Extract citations from draft" (or "Re-extract citations"). Press it and the regex pass mints one unverified row per new citation-like string. Each row then appears under "Awaiting verification" as a card headed by the citation, with a "Look up on CanLII ↗" deep link, and — where the installation has the connector wired — a "Resolve via connectors" button. Beneath it the verification form: "Pinpoint relied on (para / page)" (required), "Source URL / neutral citation seen (optional)", and three tick boxes — "Resolves to a real case — looked up, not assumed", "Quoted / paraphrased passage matches the source", "Treatment current — not overruled, reversed or negatively treated" — then "Mark verified — all four confirmed". A separate form below takes a "Failure reason" and a red "Mark failed". Decided rows drop into a "Decided" table showing status, pinpoint, quote, treatment and the name of the person who checked it, with a "Re-queue" button on failed rows. At the foot, "Add a citation the extractor missed" takes a citation string and "Add to queue". When every row is verified, "Print certificate →" renders /r/citations/certificate?draft=… — a print-ready table of authorities with the four confirmations, the verifier's name and date and the source seen, a Method paragraph, and an unsigned signature block for the lawyer of record.

Guarantees

Verification is all four or nothing: POST /verify refuses unless a non-empty pinpoint is supplied and all three boxes are ticked, and the refusal tells you the alternative is to mark it failed. There is no partial verification anywhere in the room. Every transition to verified records checkedBy as the logged-in user's name and checkedAt as today; no machine ever promotes a row. The gate itself is arithmetic, recomputed on every write path: citeStatus becomes 'clear' if and only if every citation instance carrying that draft's id is verified, otherwise 'blocked' — and that includes instances sent over from Research (07). Adding a cite by hand, failing one, or re-queuing one all re-run it immediately. The empty-set hole is closed loudly rather than silently: a draft that scans clean regates to 'clear' but is stamped noCitationsFound, and every surface that shows the gate carries the warning "no citations detected — confirm extraction did not silently fail" — on the board, in a red banner over the queue, on the certificate as a bordered caveat card, and downstream as "clear — none found" in Brief Writer and "[no citations detected]" in the Filing Room's draft picker. The verify → edit → certify loophole is closed by a stamp: each regate records the draft's updatedAt, and a draft written to afterwards reads as stale — its gate chip becomes "blocked — edited since scan" and the certificate route refuses with "Re-extract and re-verify first". Duplicates are guarded per draft, case-insensitively, on both the extractor and the manual add. Opening the room also runs two defensive passes: any draft marked for cite-check that has never been scanned is extracted automatically, and any draft reading 'clear' whose instances are not all verified is re-gated shut (audited as citation.regate.tightened) — the re-gate moves in the blocking direction only and never re-opens a gate. Scan, verify, fail, lookup, certificate and autoscan each write their own audit line.

Does not do

The extractor is a regex pass, not a citation parser. It matches styles of cause, bracket-year reports, neutral citations, volume-reporter-page cites, rule-book cites and statutory pinpoints, it deliberately over-captures, and it caps at 200 matches. It will miss citations written in a form it does not know, and it will miss everything if the draft text never reached this room — which is exactly why the empty-queue warning exists and why "Add a citation the extractor missed" is on the page. Clearing the gate means the citations that were found were confirmed; it does not mean the draft's citations were all found. A connector match is not a verification, and the code is emphatic about it: "Resolve via connectors" runs the citation through the CanLII or CourtListener connector and records what came back beside the row as a finding — it stores only an http(s) URL, pre-fills the source-URL box, ticks nothing, changes no status, and deliberately does not re-gate the draft. The kernel resolver behind it will not treat a bare 200 response as a resolution: a payload with no case title comes back unresolved, precisely so a non-existent citation cannot be handed machine corroboration. Even a genuine match tells you a record with that citation exists — it says nothing about whether your quotation is accurate or whether the case has since been overturned. Those two confirmations are yours alone, and the room's on-screen note says so. The room does not read the draft for you: the pinpoint gate tests only that the field is non-empty, and its own placeholder offers "none: cited generally" as acceptable text. Nothing enforces separation of duties — the author of a draft may verify its own citations, and both seats on this installation are admin. There is no delete: neither a draft nor a citation instance can be removed from this room, only failed and re-queued. And the certificate is a printed representation, not a signature — you print it and sign it by hand.

Feeds into

citeStatus on the draft is the flag the rest of the product reads. Brief Writer (18) refuses "Mark final" unless citeStatus is 'clear', and resets citeStatus to 'none' (demoting a final draft back to draft) whenever any of its six sections changes. The Filing Room (22) lists only drafts where citeStatus is 'clear' and status is 'final', and POST /prepare refuses anything else. Pleadings (10) registers a companion draft through "to citation check", which arrives here as unchecked; re-sending the same pleading forces it back to unchecked and drops the scan stamp, so the clearance drops with it. Research (07) mints instances into this room's queue. Closing (26) exports drafts and citation instances in the transfer bundle.

Watch out

The staleness test and the stored gate flag are not the same thing, and they can disagree. Staleness is computed at render from the gate stamp; the stored citeStatus is not changed when a draft goes stale. Brief Writer's save always rewrites the record, so even a metadata-only edit there (court, word limit) bumps the draft's timestamp — after which this room will show "blocked — edited since scan" and refuse a certificate while the Filing Room, which reads only citeStatus and status, still offers that draft for filing. Treat the "edited since scan" chip as a stop sign and re-extract before you file, because nothing downstream will stop you. Second: opening this room writes data — the auto-extract and defensive re-gate passes run on a plain page load and can change a draft's gate before you have touched anything. Third: the certificate's ✓/✗ confirmation column can only ever print ✓, because the certificate renders only when every row is verified and verification forces all four values true; it restates the gate rather than independently testing it. Fourth: a draft that was scanned and found to contain no citations at all cannot reach the certificate through any link on the page (both the board link and the draft card's button require at least one citation), though the certificate route itself will render the zero-citation form if you reach it directly — and that form says in terms that it attests the pass found nothing, not that the draft was read and found to cite no authority.

Jurisdiction Desk /r/jurisdiction

This is where you tell Chambers which rulebook a matter runs under, and where you read the deadline rules and the court's dark days for any court in the loaded tranche. It is the single control that every deadline computation in the product keys off: change the governing jurisdiction here and every deadline room computes against the new rules from that moment. It also carries the alarm for the thing that a jurisdiction change actually breaks — deadlines that were already computed under the old rulebook. The reference tables work with no matter open, so you can use this room as a lookup sheet.

How to use it

Open the room with your matter selected. If any already-computed deadline on this matter was flagged by an earlier jurisdiction change, the page opens on a red-bordered card headed 'Recompute needed' with a count of stale entries and, separately, a count of limitation bars among them. Each row shows the date it was due, the deadline description, a 'LIMITATION BAR' or 'procedural' tag, the rule it was computed under and what the jurisdiction was before, and a 'Clear flag' button. Do not press Clear flag first: go to Trial Calendar (21), rebuild the date from the current rules, mark the superseded entry done, then come back and clear. Below that, the left card 'Governing law — this matter' shows the matter title, client, the current governing jurisdiction with its code, and the posture. Pick from the 'Set governing jurisdiction' dropdown — the seven entries are Ontario (Superior Court of Justice), British Columbia (Supreme Court), Alberta (Court of King's Bench), Québec (Cour supérieure — civil law), Canada Federal Court, US Federal (FRCP), and New York (CPLR) — and press 'Set governing law'. If you pick the jurisdiction it already has, you get a flash saying no change and nothing else happens. If it is genuinely different, the matter is updated and every open deadline on the matter (anything whose status is not 'done') is stamped stale, recording what it was computed under and whether it is a limitation bar; the confirmation flash tells you how many were flagged and how many of those are limitation bars. The right card 'Courts in the tranche' lists each court code, its name, how many rules are loaded for it and how many holidays are in its table, with a 'this matter' tag on the row you are on. Below that, 'Side by side — rules and dark days' has two dropdowns, 'Court A' and 'Court B', and a 'Compare' button; Court A defaults to your matter's governing law. Pressing Compare reloads the page and redraws both columns underneath — each column gives that court's rule table (Trigger, Deadline, Kind, Days, Citation) and its 2026 holiday table (Date, Day).

Guarantees

Setting the governing jurisdiction writes it to the matter record and is audited as 'jurisdiction.change' with the before and after codes and the stale counts. Every open deadline on the matter is flagged for recompute on a genuine change — the software will not let a jurisdiction change pass silently over deadlines computed under the old rulebook. The rules engine enforces the kind distinction absolutely: a rule whose category is 'limitation' is computed to its true statutory expiry and is never rolled off a weekend or a court holiday, so you are never handed a later, false-safe limitation date. Procedural rules do roll forward to the next business day. Rolling always moves away from the anchor, so a backward-counted rule (negative days, which is how the pretrial cascade in room 21 is built) rolls backward and the lead time it exists to protect is preserved. Only jurisdictions in the loaded tranche can be set — anything else is refused. If the matter's encrypted scope is unavailable (shredded), the jurisdiction change is still recorded and the flagging step is skipped without error.

Does not do

It does not recompute anything. 'Clear flag' clears the flag and stamps the time it was cleared — that is all it does. It never edits a date, never rebuilds a deadline, and never checks that you actually rebuilt one in room 21. You can clear every flag on a matter without touching a single date, and the room will then report nothing outstanding. The rule tranche is deliberately small and is not a rulebook: Ontario carries four rules, Québec carries exactly one (extinctive prescription under art. 2925 CCQ), and the page says plainly that you should compute nothing else against Québec here. Québec is civil law and the room warns in a boxed note that common-law doctrine, precedent structure and these rules do not cross that line. There is no court-specific variation, no effective-dating and no versioning in this tranche. Most seriously: the holiday tables in kernel/rules.js contain 2026 dates and nothing else. A procedural deadline that lands in 2025 or 2027 or later is rolled off weekends only — every statutory court holiday in that year is invisible to the engine, and the date you get back will look authoritative and may be a day or more wrong. Nothing on screen warns you of this. Finally, the flagging is per-matter: changing one matter's jurisdiction does not touch any other matter, and the room shows you nothing about other matters.

Feeds into

The matter's jurisdiction is the input for: Trial Calendar (21), which computes and calendars dates from these rules; Discovery Desk (12), which uses it to pick the response-deadline rule and to decide whether the FRCP 33 interrogatory cap applies; Pleadings (10), which uses it to choose whether you are shown the Ontario or the US federal affirmative-defence reference set; and Workflow (27) and the client pack in Client Portal (36), which read the resulting deadlines. The stale flags this room writes are read back by this room only; the deadlines themselves are rebuilt in Trial Calendar (21).

Watch out

The recompute card only appears when something is flagged — on a clean matter there is no card at all, which is correct but means its absence is not evidence that deadlines were ever checked. A deadline flagged stale still shows its old date everywhere else in the product until you rebuild it; the flag is a note, not a suppression. Court A defaults to the open matter's governing law only when you have not passed a comparison of your own, so after a Compare the page keeps showing the pair you chose. The 'Court dark days — 2026' heading is hardcoded to 2026 and will keep saying 2026 in any later year. A court with no holiday table of its own would fall back to the US federal table — currently every court in the tranche has its own table, so that fallback is dormant, but the note on screen still describes it.

Pleadings /r/pleadings

This room answers one question: which elements of which causes of action still have no pleaded fact behind them, and which affirmative defences are registered but not yet pleaded. It holds the claim side (causes of action, with each element mapped to a sourced chronology fact) and the defence side (the affirmative-defence register, counterclaims and crossclaims). It is also where pleading drafts are typed and where a pleading is registered into the citation gate. It is a work-product register — it does not produce a pleading document.

How to use it

Open a matter first; without one the room shows only a prompt. The page opens on 'Before you serve — [matter title]' with a gap count. The card under it summarises jurisdiction, how many claim causes are pleaded and how many are fully supported, counterclaim and crossclaim counts if any exist, and the defence tally (registered / pleaded / not). If there are gaps, a table lists them: 'Where' links to the card that fixes it, 'What is missing' names the element or defence, 'Risk' shows 'no fact behind it', 'nothing to test the claim against' or 'waived if omitted', and the last column is a 'map a fact →', 'add elements →' or 'mark pleaded →' link. 'Export pleadings register (.txt)' downloads the whole register as a plain text file named pleadings-register-[matter]-[date].txt. To add a cause, scroll to 'Add a cause, counterclaim or crossclaim'. Choose Side (Cause of action (claim), Counterclaim, or Crossclaim); a counterclaim or crossclaim is refused unless you fill 'Asserted against'. Pick a 'Reference element set' — Negligence (Ontario), Breach of contract, Unjust enrichment, or Negligence (US common law), each showing its element count — or leave it on '— custom cause (build your own elements) —' and fill 'Custom cause label' and, optionally, 'Custom cause authority'. Press 'Add to matter'. A reference cause arrives with its elements already listed and none supported; a custom cause arrives with zero elements. Each cause gets its own card showing its label, jurisdiction tag, side tag and a coverage tag ('all N elements supported', 'N/M elements supported', or 'no elements yet'), the reference authority, and a table of Element / Supported by (chronology facts) / Coverage / drop. Use 'Add an element' plus 'Add element' to extend the set; use the 'Element' and 'Chronology fact' dropdowns plus 'Map fact to element' to attach a fact; 'unlink' removes one mapping; 'drop' removes an element (and its mappings); 'remove this cause' deletes the whole cause. For defences, use 'Register an affirmative defence': pick from the 'Reference defence' dropdown (labelled ON or US depending on the matter's jurisdiction) or type a name into 'Or a custom defence name', add the 'Factual basis / particulars', and press 'Register defence'. Every registered defence appears in the register table with its authority, basis, status and a 'mark pleaded' / 'unmark' toggle and a 'drop'. While anything is unpleaded, a red 'Waiver trap' banner sits above the table. To draft, use 'Draft a pleading': Title (required), Type (Claim, Defence, Counterclaim, Crossclaim), Body (required), then 'Save draft'. Saved drafts appear in the 'Pleading drafts' table with a 'Citation gate' column and two buttons: 'to citation check' (or 're-send to 08' once sent) and 'drop'.

Guarantees

An element can only be mapped to a fact that actually exists in this matter's chronology — the /link handler refuses anything that is not a real fact id, and room 06 refuses to record a fact without a source pin, so every mapping you see already carries a pin. A counterclaim or crossclaim cannot be created without naming the party it is asserted against. A reference cause cannot be added twice for the same combination of set, side and party. An element label must be unique within a cause, case-insensitively. Deleting an element also deletes its mapping. A defence name cannot be registered twice, case-insensitively. The gap queue, the on-screen gap table and the exported register are all computed by one shared function, so the screen and the file can never disagree. Registering a defence and toggling its pleaded state are separately audited. Sending a pleading to Citation Check mints a companion draft record carrying the pleading's text; re-sending the same pleading resets that gate hard — citation status back to unchecked, the scan stamp dropped, and a draft that had reached 'final' demoted back to 'draft' so the Filing Room (22) cannot file it on a clearance that no longer describes the text.

Does not do

It does not write a pleading. The Body field is a plain text box; there is no formatting, no numbered paragraphs, no court style of cause, no template and no export of the draft itself from this room. It does not assess whether a fact actually supports the element you mapped it to — one mapped fact turns the coverage tag green, and a fact marked disputed in the Chronology counts exactly the same as an uncontested one. It does not check the sufficiency, particularity or pleading style of anything. The reference element sets and defence lists are labelled reference data with citations to leading statements of the tests; the room says on screen they are a checklist and not legal advice, and they are neither complete nor jurisdiction-tailored beyond the crude ON/US split. Nothing here gates anything: the gap queue does not stop you saving a draft, sending it to Citation Check, or filing it. The only gate on the road to the Filing Room is the citation gate in room 08 plus the 'final' status set in room 18 — a pleading with every element unsupported and every defence unpleaded will file exactly as readily as a complete one. Marking a defence 'pleaded' is a self-declaration; the software does not read your served defence and cannot verify it. And it does not check limitation dates, service dates or anything else on the calendar.

Feeds into

Chronology (06) supplies the facts that elements are mapped to. 'to citation check' registers a companion draft that Citation Check (08) scans and verifies; Brief Writer (18) can then mark that draft final (it refuses unless citations are clear); Filing Room (22) only accepts drafts that are both citeStatus 'clear' and status 'final'. Closing Room (26) exports the companion draft and the citation instances, never the pleading record itself — so a pleading's text only reaches a transfer bundle through its registered draft. The matter's jurisdiction, set in Jurisdiction Desk (09), decides which affirmative-defence reference set you are shown.

Watch out

Dropping a pleading draft with 'drop' deletes the pleading but leaves its companion draft standing in Citation Check and Brief Writer, pointing at nothing — it can still be marked final and filed. If you delete a pleading, delete its draft in room 08 or 18 as well. Re-sending to 08 always resets clearance; do not press 're-send to 08' casually on a cleared pleading. A pleading arrives in room 08 with status 'draft', not 'cite-check', so room 08 will not auto-extract it — you must open room 08, select it and press 'Extract citations from draft', or move it to cite-check from room 18. The affirmative-defence set is chosen crudely: only a jurisdiction starting 'us' or equal to 'ny' gets the FRCP 8(c)(1) list; Québec, BC, Alberta and the Federal Court all get the Ontario common-law list citing the Ontario Rules of Civil Procedure, which for a Québec matter is flatly wrong and contradicts the civil-law warning in room 09. A matter with no jurisdiction set also silently gets the Ontario list. Reference causes keep their own jurisdiction tag regardless of your matter, so a BC matter can show 'Negligence (Ontario)' tagged ON. The duplicate check only covers reference causes — you can add the same custom cause label as many times as you like. A cause with no elements is itself reported as a gap, which is the right answer but means a fresh custom cause immediately raises an alarm until you add elements. Counterclaim and crossclaim sections only appear once one exists.

Court Book /r/courtbook

A firm-wide directory of the courts you file in: the name, the jurisdiction, the level, the e-filing portal, and four standing notes — filing fees, page and word limits, formatting requirements and standing orders — each entry carrying the date a human last confirmed it against the court's own website. It exists because fees, page limits and standing orders drift constantly and a filing made against a stale note is a filing made wrong. The daily use is a lookup seconds before a filing; the daily action is reverification. It needs no matter open and is shared by both lawyers.

How to use it

Open /r/courtbook. On first view the room seeds three reference entries — Ontario Superior Court of Justice (Toronto region), Federal Court of Canada, and U.S. District Court, Southern District of New York — each stamped verified as of that day and tagged 'reference'. If any entry has gone past 180 days since its last verification, the page opens on a 'Reverify before you file' card listing those courts with their last-verified date and a 'Verified today' button plus an 'edit' link. Reconfirm the entry against the court's own site first, then press 'Verified today' — that stamps today's date and is audited. Below is the 'Directory' table: Court, Jurisdiction, Level, E-filing, Notes, Verified, and the controls. The Notes cell folds the four standing notes behind a summary line naming which of them are on file (for example 'fees · limits · format · standing orders'); click it to expand. The Verified cell shows the date plus either a green 'Nd ago' tag or a red 'stale — Nd' tag. Each row carries 'Verified today', 'edit' and 'Delete'. To add a court, use the 'Add a court' form at the foot: Court name (required), Verified on (required, defaults to today), Jurisdiction, Level (Trial, Appellate, Final appellate, Tribunal, Other), Filing fee note, Page / word limit note, E-filing portal, Formatting notes, Standing-order notes, then 'Add to court book'. Clicking 'edit' on a row moves that form to the top of the page pre-filled and headed 'Edit — [court]', with 'Save changes' and a 'Cancel' link. Printing the page (Ctrl-P) yields the directory as a reference sheet with every standing note unfolded and the forms and chrome dropped.

Guarantees

'Verified on' is required and must be a real calendar day — the handler round-trips the date, so a shape like 2026-02-31 that JavaScript would happily roll forward is refused with an error rather than silently accepted. Court name is required. Anything not reverified within 180 days is lifted into the queue at the top of the page and tagged stale in the directory; an entry with no parseable verification date reads 'never verified'. Any hand edit through the form permanently drops the 'reference' label, so a seeded entry you have touched no longer claims to be untouched reference data. Every verification stamp is audited, as is the initial seeding.

Does not do

Nothing in this book is fetched. There is no connection to any court website, docket system, RECAP or Juriscraper; the entries are whatever a human typed, and the 'Verified today' stamp is a record that a person says they checked — the software cannot tell whether you actually opened the court's site. The three seeded entries are stamped verified as of the day the room was first opened even though nobody verified them, and they will read as freshly checked for 180 days. The notes are free text: the room does not parse a page limit, does not compare your document to it, and does not warn the Filing Room about anything. It does not carry judge-level individual practices beyond whatever you type into the standing-order note — the S.D.N.Y. seed says in words that the assigned judge's individual rules override the local defaults, but the software has no field for them and no way to check. Deleting an entry is immediate and unconfirmed.

Feeds into

Filing Room (22) reads this list as its court picker, so a court you have not entered here cannot be selected there. Nothing else consumes it. Because it is firm-level rather than matter-scoped, it carries no client content and is not affected by ethical walls.

Watch out

The staleness clock is 180 days and starts from the seed date, so all three reference entries go stale on the same day roughly six months after first use — expect a burst of three at once. Editing an entry to fix a typo silently strips its 'reference' tag; that is deliberate but it is not reversible through the UI. The 'Verified on' field in the add/edit form defaults to today, so saving an edit without touching it re-stamps the verification date even if you only corrected a spelling — the stamp will then say a human confirmed the entry today. The 'Level' value is whitelisted: anything outside the five listed options is stored as 'Other'.

Discovery Desk /r/discovery

The board for every discovery instrument on a matter — requests for production, interrogatories, requests for admission, undertakings and notices to produce — in both directions, with the response deadline computed from a rule where one is on file and calendared into the diary. It also holds the negotiated discovery plan and proportionality record, the ESI protocol checklist, the meet-and-confer log that supports a motion to compel, and the deficiency letters generated from unanswered items. It is the one room in this track that produces something which leaves the building.

How to use it

Open a matter first. The page opens on 'Instruments' with an overdue count if any. Each row shows type, direction (inbound / outbound), party, served date, response due (with its rule citation, or the word 'manual'), status (open / overdue / responded), objection count with a red 'boilerplate' tag if any objection was flagged, items answered as a fraction, and an 'open →' link. To track something, use 'Track an instrument': choose Type and Direction, enter Served (required, a real date), optionally Response due, name the 'Responding / serving party', and paste the requests into 'Items / requests (one per line)' — one item per line — then press 'Track instrument'. The note under the form tells you which types are computed for this jurisdiction and their citations. Opening an instrument gives you its detail panel: the key facts, a 'Mark responded' button, a 'Deficiency letter — chase N' button when items are unanswered, the numbered item list where each item's ✓ / · button toggles it answered, and an Objections panel where you type into 'Objection basis — state it with specificity' and press 'Record objection'. The response-due row also shows whether the diary entry is linked, still open, or closed. 'Mark responded' sets the instrument responded and closes its diary entry; the flash tells you which date was closed, or warns you to close it by hand in Trial Calendar (21) if no entry could be matched. The ESI card has four checkboxes — Custodians listed, Date range set, Formats agreed (production spec), Clawback / non-waiver order entered — and a 'Save checklist' button; the heading reads 'negotiated — collect' only when all four are ticked. If any interrogatory sets exist, an 'Interrogatory count — FRCP 33(a)(1) cap' table appears with an estimated count including discrete subparts against the cap of 25. 'Discovery plan & proportionality' shows the plan as a readable record once saved, with 'Download plan (.txt)' and a foldaway 'Revise the plan'; the form fields are Scope of discovery, Custodians / sources (one per line), Date range — from and to, Production format, Proportionality — cost and burden against the amount in issue, and Agreed dates / milestones, saved with 'Save discovery plan'. 'Log a conference' takes Date (required), Attendees, Issues raised and Resolutions / next steps, and 'Log conference' writes it to the history beside it. Generating a deficiency letter puts the letter on a sheet at the top of the page with 'Print / save as PDF', 'Download (.txt)' and a link back to the desk; the letter lists every unanswered item, states when responses were due and under what rule, demands complete responses within 14 days and says you will move to compel and seek costs.

Guarantees

A tracked instrument needs a valid type and a real served date. Where a rule exists for the jurisdiction and type — US federal interrogatories (FRCP 33(b)(2), 30 days), US federal requests for production (FRCP 34(b)(2)(A), 30 days), and Ontario undertakings (r. 31.07 practice, 60 days) — the due date is computed by the rules engine, the row carries the rule's citation, and the deadline record carries the rule's internal id so downstream rooms can resolve its source. A due date always mints a diary deadline, and the deadline is written first so its id can be stored back on the instrument; 'Mark responded' then closes exactly that entry, so an answered instrument never leaves its response date standing open in Trial Calendar (21), Workflow (27) or the client's next-key-dates pack (36). An instrument tracked before that back-link existed has a diary entry adopted only where the match is provably unambiguous in both directions — exactly one still-open unclaimed deadline carrying this room's exact description, trigger and due-date signature, and no other unlinked instrument that could equally claim it. Anything less and it guesses nothing and tells you to close the entry by hand. An objection matching the boilerplate pattern and under 90 characters is stored flagged and flashed back to you. The discovery plan is refused if every field is empty or if the date range ends before it starts. A meet-and-confer entry is refused without a valid date and without at least one of attendees, issues or resolutions. A deficiency letter is generated only from items marked unanswered; if everything is answered the room says there is nothing to chase and writes nothing. The plan export, the letter export and the meet-and-confer log are audited.

Does not do

It does not send anything. The deficiency letter is text on a screen and a .txt download; nothing is emailed, served or filed, and the letter carries no signature block, no sender name and no address. Its fourteen-day demand is hardcoded and is not checked against any rule or against the recipient's actual obligations — review and sign it before it goes out. It does not compute a response date for anything outside the three mappings above: an inbound US federal request for admission gets no computed date and no warning, even though the rules engine holds the FRCP 36(a)(3) rule and even though silence on an RFA admits. Ontario matters get no computed date for anything but undertakings. The interrogatory count is an estimate — subparts are guessed from parenthesised letter and roman-numeral markers in the item text, the room says so on screen, and on an Ontario-seated matter the whole table is explicitly informational because Ontario has no written interrogatories. The boilerplate flag records; it never blocks. It does not read your actual responses, does not verify that a ticked item was really answered, and does not check proportionality — the plan is a record of what you agreed, not a test of it. The ESI checklist is four booleans with no evidence behind them and no gate on collection. There is no route to delete or amend a tracked instrument, to add items after it was tracked, to un-mark it responded, or to delete a deficiency letter, a plan or a conference entry.

Feeds into

The matter's jurisdiction from Jurisdiction Desk (09) selects the response rule and decides whether the FRCP 33 cap is treated as live or informational. Every computed or typed due date becomes a deadline read by Trial Calendar (21), the firm-wide diary in Workflow (27), the ICS feed, and the next-three-key-dates section of the Client Portal pack (36); 09's recompute list picks these up if the jurisdiction later changes. The discovery plan and meet-and-confer log are the record behind a motion to compel and behind Ontario's r.29.1.03 plan requirement. Closing Room (26) exports the discovery records as part of a transfer bundle.

Watch out

If a rule matches, anything you type into 'Response due' is discarded without a word — the rule date wins and the row is stamped with the rule's citation. If counsel has agreed an extension on a US federal RFP or interrogatory set, this room will calendar the rule date instead and the diary will say it came from FRCP. A matter with no jurisdiction set silently defaults to Ontario for rule lookup and the interrogatory panel will assert 'This matter is Ontario-seated'. Because items can only be entered when the instrument is first tracked, an instrument tracked without pasting the requests can never be chased through the item list or a deficiency letter — you have to track it again, which mints a second diary entry. Since nothing can be deleted, a mistyped served date lives on the board permanently. The boilerplate flag only fires under 90 characters, so padding a boilerplate objection past that length defeats it entirely. Marking an instrument responded is one-way; there is no reopen. Printing the page yields the selected deficiency letter alone, in a serif face on plain paper, with the board, forms and history dropped — that is deliberate, but it means Ctrl-P on this room never gives you the instrument board.

Document Review /r/review

This is the encrypted review set for one matter: every document you intend to look at, code and either produce or withhold. Document text is stored as an encrypted blob under the matter's own key; only the metadata (title, custodian, date, Bates, coding) rides in the index. Two decisions made here — responsive yes/no and the privilege call — determine what goes out the door in Production and what your client swears to in the Affidavit of Documents. Bates numbers are assigned here, on intake, and are the matter's numbering of record.

How to use it

Open the matter in the topbar first; with no matter open the room shows only 'Open a matter to build its review set.'

There are two ways in, both on the page. 'Add document' takes a Title (required), Custodian, Document date, a Privilege call and a Responsive call from the dropdowns, the pasted Document text (required), Issue tags as a comma-separated list, and three privilege-log fields — Author, Recipients, Withheld subject. Press 'Add — next bates auto-assigned'. The text is written to an encrypted blob before the record is stored, the next Bates number is computed, and you are flashed 'DEF-000001 added — text encrypted under this matter's key.' A document date that is not a real calendar day (2026-02-31, say) is refused before anything is written.

'Intake an email (.eml)' takes the raw RFC822 source pasted into 'Raw RFC822 source' — in most mail clients that is File → Save As .eml, or 'Show original'. Press 'Intake email — service timestamp preserved'. The room parses the headers, takes the first text/* part as the body, and creates one document record for the message plus one for each attachment, each with its own Bates number. Custodian is set from the From header, the date from the Date header, and the full sent timestamp is kept on the record. You can also POST the file itself from the command line: curl --data-binary @served.eml -H 'content-type: message/rfc822' /r/review/eml.

Once documents are in, the 'Review set' table lists them Bates-ordered. Each row carries a 'Recode' form in the last column: two dropdowns (Privilege, Responsive) and an issue-tags box, always live; the three privilege-log boxes (author, recipients, withheld subject) appear in the form only once a privilege other than 'No privilege' is selected on that row. Press 'Recode' to save. Clicking the title opens the document view, which decrypts and shows the full body plus a 'Code it' card with the same fields and a 'Save coding' button — coding from there returns you to the document, not the index.

The filter card at the top takes a free-text 'Search document text' term plus Custodian, Privilege and Responsive dropdowns; press 'Apply', and 'Clear' to drop the filter. Search decrypts each candidate body in memory and shows a 45-character-either-side snippet in a 'Match' column — nothing is indexed in the clear.

Below the table, two lists build themselves from the coding and never take input: the 'Privilege log' (every document with a privilege claim, showing Bates, Created, Author, Recipients, Description, Basis) and the 'Production list' (everything coded responsive and not privileged). Printing the page yields exactly those two documents — the search card, the review table and the intake forms drop out.

Guarantees

Document plaintext is never stored in the metadata index and never leaves the encrypted blob store — it is decrypted at request time and HTML-escaped before display. Bates numbers are monotonic per matter: the room scans every existing DEF-nnnnnn, takes the maximum plus one, and pads to at least six digits, so a number is never handed out twice, including past DEF-999999. A document date that is not a real calendar day is refused, and refused before any blob is written. The privilege log and production list are generated from the coding rather than maintained by hand, so they cannot drift from the set — and the partition is strict: privilege beats responsiveness, so a document is either on the production list or on the privilege log, never both. Titles and pasted text are both required. An .eml message that exceeds the hard caps (1000 MIME parts, 100 attachments, 25 MB of decoded attachments) is refused with nothing persisted — zero blobs, zero records. An unreadable Date header is stored as an unknown sent time and flagged on the row rather than guessed at.

Does not do

It does not delete. There is no route to remove a document from a review set, and no de-duplication — paste the same letter twice and you have two records, two Bates numbers, and two lines on the production list. It does not check your coding: nothing here reviews, samples or second-guesses a responsiveness or privilege call, and there is no reviewer sign-off, no second-pass QC and no per-reviewer audit of coding changes beyond the generic record-write entry. The 'missing' flag on an incomplete privilege-log entry is advisory only — it stops nothing. Production will still assemble and serve a volume, and the Affidavit of Documents will still render Schedule B for swearing, with the author and description blank. It does not OCR, extract text from PDFs or Office files, or read anything but text you paste and .eml source; a scanned document has to be transcribed by hand. Search is a literal case-insensitive substring match on one term — no stemming, no boolean operators, no proximity, and a body that fails to decrypt is silently dropped from the results rather than reported. The .eml parser is one level deep: nested multipart structures beyond the first level are not walked, and an attachment inside an attached message will not be found. No redaction is applied or tracked anywhere in this room.

Feeds into

The Evidence Room (room 16) links an exhibit to a document by id, carrying its Bates and title. Production (room 33) reads the identical partition — responsive and not privileged is the producible set, anything privileged is the withheld set — and freezes those ids into a volume at assembly time. The Affidavit of Documents (room 35) builds Schedule A (produced) and Schedule B (withheld on privilege) live from this coding every time the page is rendered, so a recode here changes what the deponent will swear. The Closing Room (room 26) exports document metadata only — id, title, Bates, custodian, date, privilege, issues, created date — in a transfer bundle; blob text never enters it.

Watch out

A document intaken from .eml is coded 'none' privilege and 'no' responsive by default — including every attachment. Until you go back and code it, it is invisible to the production list, to Production and to Schedule A. Coding drives a SWORN document: change a responsiveness call after the affidavit is sworn and Schedule A silently changes with it, because it is assembled live rather than stored. A production volume already assembled in room 33 is frozen and does not follow a later recode, so the two can legitimately disagree — that is by design, but you have to know it. The .eml row's Date header is the service timestamp: use the sent time, not the date alone, when you compute a responding deadline (Ontario deems an email served after 4:30 p.m. effective the next day, r. 16.06.1); a row tagged 'sent time unknown' had no readable Date header and must be confirmed before you diarise off it. The privilege log's Created column and the affidavit's sort key both fall back through dateCreated, then date — the room never writes dateCreated, so in practice it is the document date you typed. Recoding preserves any field the submitted form does not carry, so switching a row back to 'No privilege' hides the log boxes but does not erase what you already typed into them.

Depositions /r/depositions

The examination file: who is being examined, what you will put to them, what they said, and what they promised on the record. It builds an outline from your sourced chronology so the document is in hand when the question is asked, indexes the transcript page:line by page:line, pairs impeachment candidates with the fact they contradict, and keeps the register of undertakings, refusals and under-advisements that Canadian practice runs on. It also shows a firm-wide board of every open promise across every matter you can see.

How to use it

With a matter open, start at 'Add a witness': Name (required), Side ('Theirs — adverse', 'Ours' or 'Third party'), Examination date, Role. Press 'Add to the bench' and you land in that witness's workspace. Names appear on 'The bench' table on the left with topic and digest counts.

Click a witness name on the bench to open the 'Examination workspace'. On the left is the Outline. If the chronology contains facts naming this witness as actor, a button reads 'Pull N new facts from chronology' — pressing it creates one numbered topic per fact, carrying that fact's source pin across, and skips anything already pulled. Actor matching is fuzzy in both directions: it matches if the chronology's actor field and the witness name are equal or if either contains the other, case-insensitively. Add anything else with 'Manual topic' plus an optional 'Source pin' and the 'Add topic' button. Each row has a 'drop' button.

On the right is the Transcript digest. Enter 'Page:line' in the form 41:12 (required, and format-enforced), pick a Kind — Admission, Denial or Impeachment candidate — paste the verbatim Quote (required), and optionally pick a 'Contradicting fact' from the chronology dropdown. Press 'Log entry'. Entries logged as impeachment candidates appear in the 'Impeachment table' below, showing the transcript cite, what the witness said, the contradicting fact and that fact's source pin; an unpaired one shows 'no fact paired'.

The register at the bottom is 'Track one'. Pick the Witness, pick the Kind — Undertaking, Refusal or Under advisement — type the text 'As given' (required: the undertaking, or the question refused), and optionally Question no., Page:line, Ground and Answer sought (the last two are stored only for refusals and under-advisements), Given and Due. Press 'Track it'. Leave Given blank and it reads as today. Leave Due blank and it is computed: on an Ontario matter, 60 days from the given date rolled forward off weekends and court holidays per r. 31.07 practice; on any other jurisdiction, a flat +60 calendar days described on the row as '+60 days (house default)'. Whichever applied is recorded on the row and shown under the Due column. When the answer arrives, press 'answered today' on that row.

For a witness with refusals or under-advisements, the workspace also builds a 'Refusals chart — motion-ready' in question-number order, with columns Q#, Page:line, Question as put, Ground of refusal, Answer sought, Status. Print the page with a witness open and that chart is what comes out, in the tabular form the Toronto Region consolidated practice direction expects.

The 'Cross-matter undertakings board' at the bottom of the page (and on the room with no matter open) splits every unanswered promise firm-wide into 'Ours to answer' and 'Theirs to chase' by the witness's side, sorts overdue first, and gives each row its own 'answered' button that names its own matter.

Guarantees

A page:line reference must look like a page:line reference (one to five digits, a colon, one to four digits) or the entry is refused; a digest entry must carry a verbatim quote. A given or due date that is not a real calendar day is refused with a flash, never stored and never a crash. An undertaking cannot be recorded without a witness that resolves on this matter and without the text as given. A due date is never left blank — if you do not set one, one is computed and the basis for it is recorded on the row. Pulling from the chronology is idempotent per fact: pull twice and nothing is duplicated, and every pulled topic inherits the fact's source pin. A contradicting fact is stored only when the id resolves to a real fact in this matter. The cross-matter board respects ethical walls and skips destroyed matters — a walled matter's undertakings are not merely hidden from the board, they are unreachable, and its 'answered' button is matter-qualified so it can never act on the wrong file.

Does not do

Nothing on this register reaches your calendar. The room never writes a deadline record, so an undertaking due date — including an overdue one — does not appear in the Trial Calendar, the cross-matter diary in Workflow, the ICS feed on your phone, or the client pack. 'Overdue' is only visible to someone who opens this room. It does not chase anything, send anything or remind anyone. A witness record is write-once: there is no route to change a name, side, role or examination date, and none to remove a witness — a hearing scheduled or moved after you added the person stays wrong on the bench. Marking something 'answered' is irreversible and stamps today's date; there is no un-answer and no way to record that an answer was given on some other day, and no delete for a register entry. It does not verify that an undertaking was in fact answered, or that what came back satisfies it. The impeachment pairing is your judgement recorded, not a contradiction the software found. This room's witnesses are entirely separate from the Trial Book's trial witnesses and from the sponsoring-witness field in the Evidence Room — nothing joins them.

Feeds into

Nothing downstream consumes the register operationally. The Closing Room (room 26) exports witness, depoTopic, digest and undertaking records into a file-transfer bundle. Outline topics are pulled one-way out of the Chronology (room 6) and carry its source pins; impeachment pairings read the same facts. The cross-matter board is this room reading itself across every matter you can see.

Watch out

The undertakings rule lookup only finds a rule in the matter's own jurisdiction whose id names undertakings, and the rulebook holds exactly one — Ontario's r. 31.07 practice, 60 days. Every non-Ontario matter therefore gets the '+60 days (house default)' with no rule behind it. That is a house convention, not any court's rule; check the governing rule before you rely on the date. Chronology actor matching is deliberately loose — a witness named 'Lee' will match a fact whose actor is 'Leeson', and pulling will create a topic for it. Ground and Answer sought are stored only when the Kind is Refusal or Under advisement; type them against an Undertaking and they are discarded silently. The refusals chart is built per witness, so a motion covering several witnesses means printing several pages. Records created before the Kind field existed read as plain undertakings.

Experts /r/experts

One file per expert, ours and theirs, from identification through retainer, service of the report, and any challenge to qualification. It tracks the admissibility prongs under both regimes you might face (FRE 702/Daubert and Mohan/White Burgess), the FRCP 26(a)(2)(B) written-report contents, Ontario's Form 53 acknowledgment of the expert's duty, and the two dates that matter — the report due date and the disclosure date — both of which post to the Trial Calendar as real deadline records.

How to use it

With a matter open, use 'Add expert': Name (required), Discipline, Side (Ours / Theirs), Report due, Rate basis (Hourly / Daily), Rate, and 'Scope of retainer / opinion sought'. Press 'Open expert file'. If you gave a report due date, a deadline record is created at the same moment and the flash confirms it was posted to the Trial Calendar. A date that is not a real calendar day is refused rather than dropped.

Every expert then gets a card under 'Expert files'. The card shows Rate, Report due, Disclosure due, Scope and Challenge. The two date rows are read back from the deadline records themselves, so they say 'diarised', 'overdue', 'done' or 'not on the calendar' — what the calendar actually holds, not what the expert record asserts.

Admissibility: two columns of checkboxes, 'Daubert / FRE 702 (US federal)' with three items and 'Mohan / White Burgess (Canada)' with five, each labelled with its authority. Tick what the work supports and press 'Save checklist (n/8)'.

Pipeline: a single button advances the stage — 'Mark retained' from identified, then 'Mark report served' from retained. Only the adjacent step is offered and only the adjacent step is accepted. To record a challenge, use the 'Record challenge' form on the card: choose 'Challenge by' (Us / Other side), type the 'Ground', and press it; status moves to challenged. When the court rules, the 'Record ruling' form appears — pick qualified or excluded and press 'Record ruling'.

Dates: the 'Post deadline' form on the card takes a report due date and either creates the deadline or moves the existing one in place. The 'Disclosure & independence' block at the foot of the card has its own 'Disclosure rule' dropdown (Ont. r. 53.03(1) or (2); FRCP 26(a)(2)(D)(i) or (ii)) and a date field labelled 'Set disclosure deadline' or 'Move disclosure deadline'; press 'Post disclosure deadline'.

Form 53: in the same block, fill 'Engaged by (party)' (defaults to the matter's client), 'Date acknowledged', and 'Independence — connections to a party disclosed', tick the acknowledgment box, and press 'Record Form 53'. The card then offers 'download draft', which serves a plain-text working draft of Form 53 with the expert's and party's names filled in, clearly labelled as a draft to verify against the current prescribed form.

Also in the block: the six-item FRCP 26(a)(2)(B) report-contents checklist, saved with 'Save report checklist (n/6)'. The reference tables for all four instrument sets sit in a collapsible 'Qualification & disclosure reference' fold at the foot of the room.

Guarantees

The pipeline cannot be skipped: an expert can only move identified → retained → report served, one step at a time, and any other transition is refused. An outcome can only be recorded on an expert whose status is 'challenged', and only as qualified or excluded. A challenge cannot be recorded once qualification has been ruled on. Form 53 will not be recorded unless the acknowledgment box is ticked and a party is named. Any date entered here is validated as a real calendar day before it is written, because it becomes a deadline record that four other rooms sort and compare. Re-setting the report due date or the disclosure date updates the existing deadline in place — it never leaves a stale duplicate on the calendar. Both dates are written with an explicitly null rule id, which is an honest statement that no rule in the engine computed them: counsel took them from the scheduling or case-management order.

Does not do

It computes no dates. Nothing here derives a report or disclosure deadline from a trial date, a pre-trial date or a rule — the disclosure rules listed in the dropdown are reference citations shown beside a date you typed, and the deadline record carries the citation but no rule behind it. Ticking an admissibility prong records that the work was done; it is not a ruling, not an opinion on sufficiency, and nothing checks whether the boxes and the status agree. The FRCP 26 checklist records that the draft report covers an item, not that it is adequate. The Form 53 download is a working draft generated from stored text, not the prescribed form, and the room does not check it was actually signed, served or attached to the report. There is no delete: an expert file cannot be removed once opened, and the name, discipline, side, rate and scope cannot be edited afterwards. There is no route back down the pipeline — 'report served' cannot be undone, a challenge cannot be withdrawn, and a ruling cannot be corrected. Nothing here bills, tracks expert fees against the ledger, or stores the report itself.

Feeds into

The report due date and the disclosure date each become a deadline record in this matter, which is what the Trial Calendar (room 21), the cross-matter diary in Workflow (room 27), the Jurisdiction Desk's staleness sweep (room 9) and the client pack (room 36) read; closing one in the Trial Calendar is reflected back on the expert card as 'done'. Nothing else reads the expert record — it is not in the Closing Room's transfer-bundle export.

Watch out

The roster's 'reports overdue' chip and the expert card's 'Report due' row are computed from different sources: the chip counts the date stored on the expert against today (and only for experts not yet at 'report served' or beyond), while the card reads the linked deadline. Close the deadline in the Trial Calendar without advancing the expert and the card says 'done' while the roster still counts it overdue. 'Record challenge' is offered on any expert not yet ruled on, including one still at 'identified' — pressing it jumps the status straight to 'challenged', and because the advance map has no next step from there, the 'Mark retained' and 'Mark report served' buttons disappear for good. Once an expert is qualified or excluded, the 'Post deadline' form for the report date is hidden, so the date can no longer be moved. Saving either checklist replaces it wholesale: any box you untick is gone, and a box ticked by your co-counsel and not shown as ticked in the form you submit is cleared too. The expert's name is baked into the deadline description when the deadline is first created; correcting a misspelling later is impossible, and the calendar keeps the original. Form 53 is required of any expert whose report is served, r. 53.03(2.1) — theirs included, where 'not on file' on their side is a point to take, not a defect on yours.

Evidence Room /r/evidence

The exhibit list you carry into court, and the register of motions in limine that go with it. Each exhibit is numbered per side, described as it will be called on the record, and carries the two things that make it admissible in practice — who sponsors it and the foundation under which it comes in — plus the hearsay path if there is one. Exhibits can be linked to a reviewed document so the Bates number and title come across rather than being retyped.

How to use it

With a matter open, fill 'Add exhibit': Description (required — name it as it will be called on the record), Side (Plaintiff / Applicant, or Defendant / Respondent), 'Sponsoring witness (who authenticates)', 'Link a reviewed document — carries its Bates and title' (a dropdown listing every document coded in Document Review, Bates-ordered), Foundation, and 'Hearsay path'. Press 'Number & list'. The exhibit is given the next number for its side (P-1, P-2… / D-1, D-2…) and appears on the 'Exhibit list'. If you left the witness or the foundation blank, the flash comes back as an error telling you exactly which one is missing and that the exhibit cannot be admitted without it.

The exhibit list shows No., Description, Document (a link to the reviewed document's full text, or 'doc removed' if the record is gone), Witness, Foundation, Hearsay path, Status and a status control. Missing witness and foundation cells are rendered as a red 'missing' tag. Chips above the table count P and D exhibits, offered, admitted, refused, and how many are 'not yet admissible'.

To move an exhibit, use the dropdown in the last column — listed, offered, admitted, refused — and press 'Set'. Setting 'admitted' is refused unless both a foundation note and a sponsoring witness are on that exhibit; you get a flash naming the exhibit and what is missing. An admission is written to the audit chain.

'Move to exclude' records a motion in limine: Target evidence (required) and Ground (required), then 'Add motion'. The 'Motions in limine' register lists Target, Ground and Status, with its own dropdown — draft, filed, granted, denied — and 'Set' button.

The 'Print / save as PDF' button at the top yields the exhibit list and the in-limine register alone, headed with the matter title and today's date; the forms, the chrome and the status controls drop out.

Guarantees

An exhibit cannot be marked admitted without both a non-empty foundation note and a non-empty sponsoring witness — the same test is used for the row cells, the readiness chip and the enforcement in the status route, so what the screen shows and what the software refuses cannot diverge. Numbers are assigned per side as the count of that side plus one and are never reused within a side. A description is required. A linked document is validated on write: if the id does not resolve in this matter it is stored as no link at all, and a document that later disappears renders as 'doc removed' rather than as a broken reference. Status values are whitelisted on both the exhibit and the motion registers. Every admission writes an audit line.

Does not do

This is a list, not a ruling engine, and it does not evaluate anything: the foundation and hearsay fields are counsel's own free text, checked only for being non-empty. Typing 'business record' in the foundation box satisfies the admission gate whether or not a business-record foundation is available. Nothing here consults an evidence code, and the sponsoring-witness field is a free-text name unconnected to the witnesses in Depositions or the Trial Book — nobody checks that the person is on any witness list, or is being called at all. Once listed, an exhibit cannot be edited or deleted: there is no route to change a description, add a missing witness or foundation, correct a hearsay path, or link a document you forgot. There is no route to renumber, and no gap-proofing. Motions in limine are recorded but connected to nothing — granting a motion against a piece of evidence does not change any exhibit's status, and the room never checks whether an exhibit you marked admitted is the target of a granted motion. Status can be set in any direction (an admitted exhibit can be set back to listed) and the room does not require that an exhibit was ever offered before it is admitted.

Feeds into

The Trial Book (room 20) reads the exhibit count and the number admitted for its readiness card and points back here. Nothing else reads exhibits or motions in limine — neither type is in the Closing Room's transfer-bundle export, so an exhibit list does not travel with a file.

Watch out

The absence of an edit route is the trap in this room. List an exhibit without a foundation or a sponsoring witness and it can never be admitted; the only remedy is to list a second exhibit with the same description, which burns the next number for that side and leaves the incomplete one on the list forever, still counted in the 'not yet admissible' chip and still printed on the list you hand up. Enter both fields before pressing 'Number & list'. Linking a document is the right way to bring in a Bates number — retyping it into the description means nothing checks it. The printed list reflects whatever the statuses currently say, including an exhibit set back from admitted, so re-print after any change rather than reusing yesterday's PDF.

Tools ×20 /r/tools

The drawer of small calculations you would otherwise do on the back of a file: deadline what-ifs against any rule in the engine, a limitation quick-check, business days between two dates, prejudgment interest, a rough settlement net, and a Bates run planner. It stores nothing — every card computes from what you type and renders the answer straight back on the page. The room's own note says six are live against a build sheet of twenty.

How to use it

No matter needs to be open, though if one is, its jurisdiction seeds every jurisdiction dropdown and floats that jurisdiction's rules to the top of the rule list.

'Deadline what-if' — pick a Rule from the dropdown (every rule in the engine, labelled jurisdiction · trigger → result, with limitation rules marked '[limitation]') and a Trigger date, press 'Run'. The answer comes back as one line naming the trigger, the computed date and the rule's citation. If the rule is a limitation period, a second line says the date is returned at its true statutory expiry and never rolled forward, and warns you if it lands on a weekend or holiday.

'Limitation quick-check' — pick a Jurisdiction and 'Date claim discovered', press 'Run'. Every limitation or prescription rule the engine holds for that jurisdiction is run against the date, each answer citing its rule; where more than one exists you are told how many run there and that which one applies turns on the cause of action. If the jurisdiction has none on file you get an error telling you so.

'Business days between dates' — From, To and Jurisdiction; the count excludes the first day and includes the last, and skips weekends and that jurisdiction's holiday table.

'Prejudgment interest' — Principal, Annual rate %, From, To. Returns the day count, simple interest, the per diem and the total. Simple interest on a 365-day year.

'Settlement net quick-calc' — Gross, Fee %, Costs, Liens. Returns fee, and net to client after fee, costs and liens.

'Bates label run' — Prefix, Start number and Count; returns the first and last label and the run size, padded to at least six digits.

All six share one 'Run' button per card. The card you just ran keeps its inputs so a tweak is a one-field edit; the others stay blank. A bad input flashes an error at the top of the page and clears the form.

Guarantees

The rules engine is doing the arithmetic, not this room, so the limitation distinction is honoured exactly as it is elsewhere: a procedural deadline that lands on a weekend or court holiday rolls forward to the next business day; a limitation or prescription date does not roll and is returned at its true statutory expiry, with a warning when it falls on a non-business day. Every deadline answer is returned with the rule's citation. An unrecognised or hand-edited jurisdiction code falls back to Ontario rather than computing against no holiday table at all. Every field is validated: a missing or non-numeric figure, a negative amount, or a To date before the From date produces a flash and no answer. Nothing typed into this room is stored anywhere — no record, no audit of the figures, no trace on any matter.

Does not do

It gives no advice and applies no judgement. The limitation quick-check is arithmetic over the rules the engine happens to hold: discoverability, tolling, ultimate limitation periods, and which period applies to your cause of action are all yours. The holiday tables are a labelled 2026 reference tranche, not a complete or maintained court calendar, and the rulebook itself is a reference tranche — a rule your court applies may simply not be in the dropdown. The interest card does not look up any rate: in Ontario the prejudgment rate comes from the quarterly table published under the Courts of Justice Act, ss. 128–130, and you must supply it. The net quick-calc uses one fee convention only and is explicitly rough — the real waterfall, with both fee conventions, the staged trust receipt and the lien schedule, is room 24. The Bates planner only sizes a run; it does not stamp, reserve or allocate anything, and the matter's real DEF- sequence is owned by Document Review. Nothing computed here is diarised — no answer becomes a deadline, and no result reaches the calendar.

Feeds into

Nothing. This room writes no records at all; any date or figure you want kept must be re-entered in the room that owns it — the Trial Calendar for a deadline, room 24 for a settlement, Document Review for Bates numbering.

Watch out

Unlike the rest of this group, the date fields here do not reject an impossible calendar day. A trigger date of 2026-02-31 is accepted and silently treated as 3 March, and the answer line echoes back the date you typed beside a result computed from the rolled one — check the date you entered before relying on a limitation answer. The jurisdiction dropdown is seeded from the open matter but stays free: if you switch matters and re-run without looking, you may be computing against the wrong holiday table. The rule dropdown has no blank default — whatever sits at the top of the list when the page loads is what runs if you do not choose. Room 17 is labelled 'Tools ×20' in the sidebar; six of the twenty exist, which the room discloses on the page but the sidebar label does not.

Brief Writer (room 18) /r/briefs

This is where a factum, motion brief or letter is written and where it is stopped from going anywhere until its citations have been checked by a human. It gives you a six-box CREAC scaffold (conclusion first, so the reader knows where the argument lands before it starts), a live word count against the court's limit, and the draft's table of authorities pulled from Citation Check. It is also the only room that can move a draft to 'final', which is the state the Filing Room requires.

How to use it

Select the matter in the picker at the top-left of every page and press Open. If the matter has no drafts, the New draft card leads the page: type a Title (this is the name the court will see — 'Factum of the Moving Party'), choose a Type from the dropdown (motion, factum, brief or letter; the dropdown opens on 'factum'), and press Create. You land in the editor for that draft.

The editor is one form. The top row holds Court (free text, e.g. 'ONSC (Toronto)'), Word limit (a number), and a read-only Words figure that shows the current count and, if you have set a limit and gone past it, an OVER LIMIT tag. Below that are the six argument boxes in CREAC order: Conclusion, Rule, Explanation, Application, Counter-arguments, and Conclusion (closing). Write into them and press Save draft. If you changed the text of any of the six boxes, the flash tells you so and says citation status has been reset; if you only touched Court or Word limit, the flash is the plain 'Draft saved.' and a cleared draft stays cleared.

When the argument is drafted, press Send to Citation Check. That marks the draft 'cite-check' and writes an audit line; it does not extract anything here. Go to room 08 Citation Check: a cite-check draft that has never been scanned is extracted automatically the moment you open that room, and each detected citation appears as an unverified row you must clear by hand (pinpoint plus all three confirmations). When every row reads verified, room 08 writes 'clear' back onto this draft.

Come back to /r/briefs and press Mark final. If citations are not clear the button is styled as a danger button and the press is refused with 'Blocked: this draft has unverified citations. Clear them in Citation Check (room 08) first.' If they are clear, the draft becomes final and the Filing Room will accept it.

The Table of authorities — this draft table below the editor lists every citation instance bound to this draft with its Pinpoint, Status and Checked by. The Print / save as PDF link produces the assembled brief on paper: the draft title, the matter, the word count, then the non-empty sections in CREAC order — forms and chrome drop out. The Drafts list on the right switches between drafts (Title, Type, Updated, Words, Status, Citations, and an 'open →' link).

Guarantees

Marking a draft final is refused unless its citeStatus is exactly 'clear' (18-briefs.js POST /status, line 159). Editing any of the six section boxes diffs them against what was stored and, on any change, sets citeStatus back to 'none' and demotes a 'final' draft to 'draft' (POST /save, line 142-144) — verified text is only the text that was verified. Metadata-only edits (Court, Word limit) deliberately do not disturb a cleared final draft. The word count reads all three body shapes (sections, then `text`, then `body`), so a draft registered by Pleadings or Citation Check prints and counts its real body rather than showing zero. A draft that cleared the gate with zero citations detected is never shown as plainly 'clear': it carries a 'clear — none found' tag and an explicit warning to confirm extraction did not silently fail.

Does not do

It does not check your citations — nothing in this room reads a case, and nothing machine-verifies. 'Send to Citation Check' mints no citation rows; it only sets a status, and the extraction happens when you open room 08. It does not spell-check, cite-check, format to a court's rules, or enforce the word limit — going over the limit shows an OVER LIMIT tag and nothing more; you can still mark such a draft final and file it. It has no delete route: a draft created here can never be removed from this room, and a draft registered from Pleadings whose pleading was later deleted keeps standing here with a dead link. It does not carry the section text into any filing — room 22 records filing metadata only, and no document is transmitted anywhere by this software. Finally, the 'edit resets the gate' protection is one-directional and can be undone in room 08: pressing 'Re-extract citations' there re-runs the gate over the existing instances, so if your edit introduced no new citation string the draft can return to 'clear' with nothing re-read by a person.

Feeds into

Room 08 Citation Check (extraction, verification, the certificate and the gateStamp staleness test), room 19 Moot Room (the draft selector; only a Brief Writer draft with section text can be sent to the model adversary), room 22 Filing Room (which lists only drafts where citeStatus === 'clear' AND status === 'final'), room 10 Pleadings (which registers companion drafts here via its 'send to cite' route) and room 26 Closing (drafts are exported in a transfer bundle).

Moot Room (room 19) /r/moot

A place to argue against your own draft before the other side does, and to keep the record of having done so. You log the opposing argument at its strongest, log your answer to it, and log the questions you least want from the bench with the answers you will give. There is also an optional model adversary that will write an opposition draft, tagged as machine-written, where the firm has configured a model gateway and the matter permits it.

How to use it

Open the matter, then open /r/moot. The 'Draft under attack' card at the top carries a dropdown of every draft on the matter (each labelled title · status · cite status) and an Open button; pick one and press Open. If there are no drafts the card says so and sends you to the Brief Writer.

To record an attack, use the 'Log an attack' card. Choose the Target section (Conclusion, Rule, Explanation, Application, Counter-arguments, Closing), choose a Severity (fatal, serious or minor — the dropdown opens on serious), type the opposing argument into 'The strongest opposing argument' (required; the placeholder tells you to put it as they would put it, at its best), optionally type 'Our response', and press Log it. Logging a fatal attack returns a red flash. The Attacks table then lists everything logged, sorted so anything still open outranks anything resolved and fatal outranks serious outranks minor. The right-hand button on each row toggles between Resolve and Reopen.

For bench preparation, use 'Add a bench question': type the 'Question the bench will ask' (required) and optionally the 'Prepared answer', then press Add question. The Hot bench table shows each question, its answer (or a 'none yet' tag), whether it has been drilled, and a button reading Drilled or Un-drill to toggle that.

The 'Model adversary' card at the foot of the page shows two tags: whether the gateway is configured and whether model use is allowed on this matter. The single button in the left column toggles the matter's policy — it reads 'Forbid model use on this matter' or 'Allow model use on this matter'. When the gateway is configured and the matter is not forbidden, a 'Generate opposition draft' button appears; pressing it sends the draft's six sections (truncated to 24,000 characters) to the configured endpoint and stores what comes back. Each returned passage is displayed inside a bordered block with a red 'model-generated — <model id>' tag and the note that it is a starting point, never the record.

When you print, the page yields the podium sheet: the attacks with their responses and the bench questions with their answers, forms and chrome dropped.

Guarantees

An attack cannot be logged without text and without a draft, and a bench question cannot be logged without a question (19-moot.js lines 148 and 161). Severity and Target are whitelist-coerced — anything not in the list becomes 'serious' and 'conclusion' respectively, so the triage sort is always meaningful. Anything returned by the model is stored with the model id and is always rendered inside the model-generated tag; the room never mixes it into the attack record. The gateway itself refuses and audits when the matter's policy is 'forbidden', and the model call is audited on every attempt. 'Generate opposition draft' is refused with 'That draft has no content to attack yet.' when the draft's six sections are empty.

Does not do

An unresolved fatal attack does not stop anything. The card says so in terms: it 'does not stop the Filing Desk — that judgment stays with counsel.' Room 22 never reads a critique, so a draft with three open fatal attacks assembles, signs and files exactly like any other. There is no route to edit an attack, its response, a bench question or its prepared answer once submitted — the only writes available afterwards are Resolve/Reopen and Drilled/Un-drill. If you get the response wrong you must log a second attack; nothing can be corrected in place and nothing can be deleted. This room only attacks drafts with CREAC sections: a draft registered from Pleadings or pasted into Citation Check carries its body in another field, and 'Generate opposition draft' refuses it as having no content, even though the draft plainly has text. Model use is permitted by default — a matter with no aiPolicy set reads as 'allowed', and any signed-in user can flip the policy; there is no role check on that button. When the endpoint an administrator configured is a hosted service rather than a local one, pressing Generate sends privileged draft text out of the building.

Feeds into

Nothing downstream consumes critiques, bench questions or opposition drafts — they are read only in this room. The matter-level model policy this room toggles is stored on the matter record in firm scope and is enforced by the kernel gateway for every model call anywhere in the product, not just here.

Trial Book (room 20) /r/trialbook

The binder counsel carries to counsel table: the call order with a time estimate for evidence, a seven-step readiness checklist, the jury instructions you intend to request, the verdict questions you want put to the trier of fact, and a fixed objection card. The page is designed to be printed and handed over as the book itself.

How to use it

Open the matter, then /r/trialbook. In the 'Call order' card type the Witness name (required; the placeholder asks for surname then how they are called), then Direct (mins) and Cross est. (mins) as whole numbers, and press Add next in order. Witnesses are called in the order entered — the flash confirms the position ('added — called 3rd'). The table shows #, Witness, Direct, Cross est. and Total, and the card heading carries a running total of estimated evidence time in hours and minutes. The note beneath tells you to give that figure to the trial coordinator, and states plainly that it excludes openings, argument, objections and rulings.

The 'Readiness' card holds seven checkboxes: Opening drafted, Closing skeleton drafted, Witnesses confirmed and prepared, Exhibits tabbed and copied, Jury instructions requested, Verdict form drafted, Objection sheet in the binder. Tick what is true and press Save readiness; the flash names everything still outstanding. The heading tag reads 'n/7 ready'. Beneath it, the card reports how many exhibits are numbered on this matter and how many are admitted, with a link through to the Evidence Room where that numbering and those rulings actually happen.

In 'Jury instructions' type a Topic (required — the placeholder suggests starting with burden of proof) and, optionally, a Pattern source (reference), then press Request. In 'Verdict form' type a Question for the trier of fact and press Add question; questions are numbered Q1, Q2 and so on in the order entered.

The 'Objection sheet — the binder card' at the foot is fixed reference text: six common objections (Leading, Hearsay, Foundation, Speculation, Asked and answered, Relevance) each with the move to make. Press Print / save as PDF and you get all of the above as the binder, with a printed tick-box copy of the readiness list substituted for the on-screen form.

Guarantees

A witness needs a name, an instruction needs a topic, and a verdict question needs text — each POST refuses and flashes otherwise. Minutes are coerced to a whole non-negative number: a blank, a negative or a non-numeric entry is stored as 0 rather than poisoning the evidence estimate. The readiness record stores array indices into the seven-item list and, on read, any index outside the current range is ignored rather than counted, so a stale record can never report the book more ready than it is. Saving readiness replaces the whole set, so unticking a box genuinely unticks it.

Does not do

There is no route to reorder, edit or delete a witness, an instruction or a verdict question. If you enter witnesses in the wrong order, the only remedy is to keep adding and read past the mistake — the call order is the insertion order, permanently. The evidence estimate is exactly the sum of the minutes you typed; nothing validates it and nothing warns when it exceeds the days the court has allotted. The readiness checklist is entirely self-reported: ticking 'Exhibits tabbed and copied' checks nothing, and the room does not verify a single tick against the Evidence Room, the Brief Writer or the Trial Calendar. It gates nothing — no other room reads the readiness record, and a book showing 0/7 ready does not stop a filing, a trial date or anything else. The witnesses recorded here are a separate record type from the witnesses in room 14 Depositions; the two lists are not joined, and adding someone here does not add them there or vice versa. The jury instruction 'Pattern source' is a free-text reference you type — no pattern instruction library is consulted or supplied.

Feeds into

Nothing outside this room reads its call order, instructions, verdict questions or readiness record. In the other direction, the exhibit counts on the Readiness card are read live from room 16 Evidence Room (total numbered, and how many carry status 'admitted').

Trial Calendar (room 21) /r/calendar

The matter's deadline diary, and the only room that computes a date from a rule rather than accepting one typed by hand. It holds four separate things: rule-computed deadlines, bring-forward ticklers kept deliberately apart from court dates, a trial-anchored pretrial cascade back-calculated from the trial date, and a private ICS link your phone's calendar app can subscribe to. It also raises an alarm when a judgment sits on the file with no appeal deadline calendared.

How to use it

Open the matter, then /r/calendar. The rules offered are those for the matter's jurisdiction (shown in the card heading, e.g. 'Rule (on)'), which is set in room 09 and defaults to Ontario.

To calendar a deadline: in 'Compute a deadline' pick the rule from the dropdown — each option reads as 'trigger → what falls due', e.g. 'Statement of claim served (in Ontario) → Statement of defence due'. Enter the Trigger date (the day the thing that starts the clock actually happened) and press Compute & calendar. The flash states what was calendared, the computed date and the citation. Nothing on this calendar is typed: the date comes from the rule.

Read the deadline rules before you rely on a date. A PROCEDURAL deadline is counted forward in calendar days and, if it lands on a weekend or a court holiday for that jurisdiction, is rolled FORWARD to the next business day. A LIMITATION or prescription date is NOT rolled — ever. It is returned exactly as it falls, because pushing a statutory expiry to a later, false-safe day is how a claim becomes statute-barred. When a limitation date lands on a weekend or holiday, the flash comes back in red saying so and telling you to confirm any statutory extension and work to the business day before. That red flash is your only warning, and it appears once, at the moment of computing.

To set a tickler use the 'Bring-forward' card: type What to chase and a BF date and press Set BF. BFs live in their own list under the diary, tagged BF, and are labelled on the phone feed as ticklers rather than court deadlines.

The Diary table lists Due, Deadline, Trigger, Authority (the citation string) and Status, with a Done button on each open row. A row overdue shows an OVERDUE tag; one within fourteen days shows a day count. The chips beside the heading count overdue, due-within-14-days, and open.

To build the pretrial plan, open the 'Trial-anchored cascade' card, enter the Trial date and press Compute & calendar the cascade (the button reads Recompute the cascade once a trial date is set). This deletes every deadline this cascade previously created and rebuilds the chain from the new date: the trial date itself, then four back-counted milestones — expert disclosure at 90 days before trial, discovery close at 60, dispositive motions at 45, and the pretrial conference at 30. The preview table shows each milestone with its computed date and its Basis, and the Basis column is the part to read: a milestone tagged 'rule' cites a real rule (in US federal matters, FRCP 26(a)(2)(D)(i) and FRCP 16(e)), while one tagged 'firm default' is the firm's own backward-planning template and is scheduling-order controlled. Confirm every firm-default date against the court's actual order.

Backward-counted milestones roll AWAY from trial. If 30 days before trial lands on a Saturday, the milestone moves to the preceding Friday, not the following Monday — rolling it forward would silently shorten the very lead time the milestone exists to preserve. (Worked example against the live rulebook: trial 2026-11-16, Ontario; the pretrial-conference milestone computes raw to 2026-10-17, a Saturday, and is calendared as 2026-10-16.)

If the matter carries a recorded judgment and no open deadline whose rule id, citation or description contains the word 'appeal', an 'Appeal clock UNCALENDARED' card appears at the very top of the page. Where the jurisdiction's rulebook carries an appeal rule, the card offers a 'Calendar the appeal clock' button pre-loaded with the date the judgment was entered; press it and the appeal deadline is computed from the rule. Where the rulebook carries no appeal rule for that jurisdiction, the card says so and computes nothing rather than inventing a period.

The 'Phone feed' card mints a private link. Press Create feed link and the address appears; subscribe your phone's calendar app to it. Every open deadline (with its rule citation in the description) and every open BF across every matter you can see appears as an all-day event, BFs prefixed 'BF:' and categorised BRING-FORWARD. Pressing Regenerate link (kills the old one) deletes the previous link immediately and issues a new one.

Guarantees

Every date on the diary was computed by kernel/rules.js from a rule you picked and a trigger date you supplied; this room has no route that accepts a hand-typed deadline date. Both the rule's citation string and the rule's id are written onto every deadline record positionally, so no write path in this room can forget the id that the Workflow room's limitation flag and appeal watchdog read. Limitation and prescription dates are returned with no weekend/holiday roll at all (kernel/rules.js compute(), line 98) and the room flags rather than moves them. Backward-counted cascade milestones roll backward, away from trial, preserving the lead time (rules.js line 92, and the deadline direction test asserts across 5,840 generated cascade dates that none lost lead time). Typed dates are round-tripped through Date, so '2026-02-31' is refused rather than rolled into March. Recomputing the cascade deletes strictly the rows this cascade stamped and nothing else — a trial-anchored deadline written by another room (an expert report date, a discovery cutoff) is left alone and is shown in the diary tagged 'not cascade-managed'. Firm-default milestones are labelled as firm defaults and never presented as statutory. The ICS feed is bound to the visible matters of the account it belongs to, skips shredded matters, and skips any record whose date cannot make a valid event rather than breaking the whole subscription.

Does not do

THE HOLIDAY TABLES COVER 2026 ONLY. Every jurisdiction's holiday list in kernel/rules.js is a labelled 2026 reference tranche, and isBusinessDay() consults nothing else. A procedural deadline that computes into 2027 or later still rolls off Saturdays and Sundays, but rolls off no holiday at all — verified: an Ontario notice of appeal from a judgment entered 2027-06-01 is calendared as 2027-07-01, Canada Day. Check any computed date that falls outside 2026 against the real court calendar before you rely on it.

The diary does NOT mark which rows are limitation dates. The Due/Deadline/Trigger/Authority/Status table renders a two-year limitation expiry exactly like a twenty-day defence deadline; the only difference visible on the page is the citation text in the Authority column. The limitation warning is a one-time flash at the moment of computing, and it is gone as soon as you navigate. The limitation tag, and the dual-diary second-lawyer tick (which refuses to accept a verification from the same user who calendared the date), live only in room 27 Workflow — not here. Nor does this room show the 'stale' flag that room 09 stamps on every open deadline when a matter's governing jurisdiction changes: a deadline computed under the wrong rulebook and flagged as such in room 09 appears in this diary as an ordinary open date with no warning.

There is no route to delete a deadline, to edit one, or to reopen one marked Done — Done is final in this room. Recomputing the cascade deletes cascade rows regardless of status, so milestones you had already marked Done disappear from the record along with the superseded dates.

The cascade is four milestones and a trial date; it is not a scheduling order and does not read one. Nothing checks a computed deadline against what the court actually ordered.

The phone feed link IS the credential and it never expires. Anyone holding the URL can read the feed, and the server admits it without a session cookie — the 'Integration note' printed on the Phone feed card, which says a cookie-less phone cannot reach the handler, is out of date and understates the exposure. Feed fetches are also deliberately not written to the audit chain, so a subscription being read is the one action in the product that leaves no trace. And every event carries the matter title in its summary and the deadline description in its body, so subscribing a phone that syncs to a third-party calendar service pushes client-identifying metadata to that service.

Feeds into

Deadlines written here are read by room 27 Workflow (cross-matter diary, the LIMITATION flag, the dual-diary second tick and the cross-matter appeal alarm), room 09 Jurisdiction (staleness on a governing-law change), room 36 Client Portal (the three soonest open dates in a client pack), room 26 Closing (transfer bundle) and the ICS feed. In the other direction this room's diary shows deadlines written by room 01 Intake (the limitation bar), room 12 Discovery (response dates), room 15 Experts (report and disclosure dates) and room 23 ADR (the brief-due date), and its appeal card reads judgments recorded in room 25.

Filing Room (room 22) /r/filing

The sign-off gate. A packet is assembled here only from a draft that is final with citations clear, it is signed by a lawyer typing their own name, and the registry's confirmation is recorded back against it. The room's own note is the honest description of what it is: it prepares and records; it does not transmit. Where a court portal has no API — CM/ECF and most provincial systems — a human files the packet and comes back here to record what happened.

How to use it

Open the matter, then /r/filing. Anything waiting on a person sits at the top of the page under 'Waiting on you', one card per packet.

To assemble a packet, use the 'Prepare a filing' card. The 'Draft — final, citations clear' dropdown lists only drafts that are both final and citation-cleared; if it is empty you get a message telling you to verify the citations in room 08 and mark the draft final in room 18. A draft that cleared the gate with zero citations detected is labelled '[no citations detected]' in the dropdown, with a warning to confirm extraction did not silently fail before you sign. Pick the Court (a dropdown of the courts recorded in the Court Book, or a free-text field if none are recorded), enter the Court file no. (optional, e.g. 'CV-26-000123'), the Style of cause (required, e.g. 'Harness Holdings v. Fixture Corp.'), the Parties served (required — opposing counsel, by name), and the Service method (email (consented), courier, personal service, or e-filing portal). Then tick all three pre-flight boxes: Personal identifiers redacted, Exhibits tabbed and referenced, Page/word limits checked against the Court Book. If any Court Book entry carries a page or word limit note, a fold-out labelled 'Page & word limits — from the Court Book (11)' sits directly above the button so you can check the third box without leaving the page. Press Assemble packet.

The packet now appears at the top as a card showing Draft, Style of cause, Court, Service, Provenance and Status 'awaiting signature'. To sign it, type your name into 'Sign as lawyer of record — type your name exactly' — it must match your provisioned name character for character; the field's placeholder shows you what that is — tick 'I have read this filing and take responsibility for it.' and press Sign. The card's Provenance line then reads 'drafted in Chambers · signed by <name> · <timestamp>'.

File the packet with the court yourself. When the registry confirms, come back to the card (now showing 'signed — file it with the court') and record it: 'Filed on' defaults to today's date and can be changed, 'Registry stamp / confirmation ref' is free text, then press Record confirmation. The packet moves down to the 'Filed' table, which lists Draft, Style of cause, Court, File no., Filed, Registry ref and Signed by. Printing the page yields that record of filings for the file.

Guarantees

Assembly is refused unless the chosen draft has citeStatus === 'clear' AND status === 'final' (22-filing.js line 98) — that check is re-run on the POST, not merely on the dropdown, so a stale page cannot get round it. Assembly is also refused without a court, a style of cause and served-party details, and refused unless every one of the three pre-flight boxes was ticked. Signing is restricted to role 'lawyer' or 'admin' — a clerk sees 'A clerk cannot sign a filing.' instead of the form. Signing requires the typed signature to equal the signer's provisioned name exactly and the responsibility box to be ticked, and only a packet in 'awaiting-signature' can be signed. Recording a confirmation requires a packet already in 'signed' and a filing date that round-trips as a real calendar date. Each of the three transitions writes its own explicit audit line (filing.assembled, filing.signed, filing.confirmed) on top of the automatic record audit.

Does not do

It does not file anything. Nothing is transmitted to any court, portal or party by this room or anywhere in this product; the packet is an assembled record, and the actual filing and the actual service are done by a person outside the software. It does not generate or attach a document — no draft text, no exhibits and no PDF are bundled or stored with the filing record; only the fields you typed plus the draft's title are kept. It does not check formatting, page limits, word limits or redactions: the three pre-flight boxes are self-certification and the software verifies none of them. It does not read the Moot Room, so unresolved fatal attacks on a draft do not block a filing. It does not check that service was actually effected or that the method you selected was permitted. There is no route to cancel, edit or delete a packet: a packet assembled in error sits under 'Waiting on you' permanently, and a filing recorded with the wrong date or reference cannot be corrected. Signing is a typed name plus a tick — it is not a cryptographic signature and produces no signed document.

Feeds into

Nothing downstream reads a filing record — it is written and read only in this room, and printed for the file. Upstream it depends entirely on the citation gate chain (room 18 for 'final', room 08 for 'clear') and on room 11 Court Book for the court list and the page/word limit notes. The room's closing flash tells you to go to room 21 and calendar any dates the filing triggers; nothing does that for you.

Mediation & ADR (room 23) /r/adr

The settlement record: every offer either side makes with its dates, the mediation or arbitration sessions with their outcomes, and priced Rule 49 scenarios showing where the presumptive costs consequences land on the dates and amounts on file. The page is built to print as the schedule handed up on a costs submission.

How to use it

Open the matter, then /r/adr. Three cards sit across the top.

'Log an offer': choose the Direction ('We made it' or 'We received it' — the dropdown opens on received), enter the Amount (a positive number), the date it was 'Served / received on', optionally the 'Open until' expiry, and any Terms, then press Log offer. Log every offer either side makes; the dates are what Rule 49 runs on. The Offers on file table shows Date, Direction, Amount, Open until, an r. 49 status chip and Terms. The chip is arithmetic on the expiry date only: an offer you made with an expiry in the past reads 'expired', one expiring within fourteen days reads 'expires <date>' in red, anything else reads 'r. 49 live'; an offer you received reads 'open — no expiry', 'open to <date>' or 'expired'.

'Rule 49 position': pick the Logged offer from the dropdown, say who the Offeror was (Plaintiff's offer or Defendant's offer), enter the Hypothetical judgment as a number, enter the Hearing date, and press Price the consequences. The room computes two qualification tests from the record: whether the offer expired before trial opens, and whether it was served fewer than seven days before the hearing. If either fires, the scenario is stored as not qualifying, with the flag spelled out and the outcome recorded as costs in the court's discretion under r. 49.13. If neither fires, the outcome states the presumptive r. 49.10 switch: a plaintiff's offer met or beaten at trial produces partial-indemnity costs to the offer date and substantial indemnity from that date; a defendant's offer the plaintiff fails to beat produces partial indemnity to the plaintiff only up to the offer date and to the defendant from that date; anything else produces no presumptive shift. The scenario is stored with your name and the date, and the Rule 49 scenarios table lists Offer, Offeror, Judgment, Qualifies (which shows the disqualifying flags where there are any), Outcome and Priced by.

'Schedule a session': choose the Process (mediation, arbitration or judicial dispute resolution), enter the Provider / neutral (required), the Session date (required) and optionally the Brief due date, then press Schedule. If you gave a brief-due date, a deadline is written into the Trial Calendar reading '<process> brief due (<provider>)' with the authority 'ADR schedule', and the flash tells you so. The Sessions table lists Date, Process, Provider, Brief due and Outcome; a session whose date has passed with no outcome recorded shows a red 'outcome not recorded' tag. To close one out, type into the inline outcome box on that row ('settled at $… / no resolution') and press Record.

Guarantees

An offer needs a positive amount and a real calendar date; a session needs a provider and a real session date; a scenario needs a logged offer and a hypothetical judgment above zero — each POST refuses and flashes rather than storing anything. Every date typed is round-tripped through Date, so an impossible date such as 2026-02-31 is refused instead of being rolled forward. Rule 49 qualification is computed from the stored record rather than assumed, and `qualifies` is true only when no flag fired. The brief-due deadline written into the calendar carries an explicit null rule id — the honest statement that a provider's schedule, not a rule, produced the date. Every scenario priced writes an audit line, and the scenario table records who priced it and when.

Does not do

It computes no dollar figure for costs — deliberately, because no costs figures exist on the file; the outcome text names the indemnity scale and the switch date and stops there. Entitlement and quantum remain r. 49.13 discretion and counsel's call, and the room says so.

Watch the Hearing date field. If you leave it blank, the 'expired before trial opens' test measures the offer's expiry against TODAY'S date, not against the trial date — so an offer expiring next month prices as qualifying even if trial is a year away, and the seven-day test is skipped entirely. Enter the hearing date or the arithmetic is answering a different question from the one you asked.

The Offeror you select is not cross-checked against the offer's direction or against which side you act for; you can price a scenario with the offeror set to the wrong party and nothing objects. The r. 49 status chip on an offer you made claims nothing about leverage — it is expiry arithmetic only, and 'r. 49 live' appears for any offer you made that has no expiry at all.

The brief-due deadline is fired once, at the moment you schedule the session, and is never linked back to the session record. Changing the session or its brief date is impossible — there is no edit or delete route for a session, an offer or a scenario — so rescheduling means adding a second session, which mints a second, unlinked deadline in the calendar while the first stays open. Recording an outcome is the only later write available, and once an outcome is recorded the Record control disappears, so an outcome cannot be corrected.

Rule 49 is Ontario-specific and the arithmetic here does not vary by the matter's jurisdiction; the room offers it whatever rulebook the matter sits under.

Feeds into

A session's brief-due date writes a deadline record read by room 21 Trial Calendar, room 27 Workflow, room 36 Client Portal and the ICS phone feed. Offers, scenarios and sessions are read only in this room and in room 26 Closing's transfer bundle; the Settlement Waterfall (room 24) does not read an offer logged here — its gross recovery figure is entered there separately.

Settlement Waterfall /r/waterfall

This is the room you open with the client on the phone when a number has been put on the table. It takes a gross settlement figure and walks it down through liens, costs advanced and your contingency fee to the net the client actually receives. Because the retainer — not this software — decides whether your percentage is taken on the gross or on the net of liens, the room computes and displays BOTH conventions side by side on every statement and refuses to nominate one as the answer. Once the money actually arrives, the same card is where you post the gross into trust.

How to use it

Select the matter at the top of the page first; with no matter open the room shows only a prompt to open one. In the 'New waterfall' card, fill 'Gross settlement' (must be greater than zero), 'Contingency fee %' (0 to 100), and optionally 'Costs advanced' (cannot be negative). Then type every lien into the single 'Liens — name:amount, comma-separated' field in the form 'OHIP subrogation:4200, Medical lien:1800' — the name goes before the last colon, the number after it. Press 'Compute'. The page reloads with a flash reading 'Statement computed — both fee conventions are shown; the retainer says which one governs', and a new statement card appears at the top of the list (newest first). The card is a full settlement statement: Gross settlement, then one 'Less lien — <name>' row per lien, a 'Total liens' row if you entered more than one, 'Less costs advanced', 'Less fee N% on gross', 'NET TO CLIENT — fee on gross', then 'Or fee N% on net of liens' and 'NET TO CLIENT — fee on net of liens'. If either net comes out below zero the card prints a red warning that on these figures the client nets nothing and tells you to renegotiate the liens or the fee before the client signs. Use the browser's own print to produce the statement for signature — printing this room drops the room heading and the entry form and yields the statement cards alone, headed 'Settlement statement — <matter> — as at <today>'. When the settlement cheque is actually in your hands, press 'Stage gross into trust' on that statement's card. The flash confirms the figure received and the tag on the card heading flips from 'not yet in trust' to 'staged to trust'.

Guarantees

The arithmetic is deterministic and shown in full: fee-on-gross is gross × pct, fee-on-net is (gross − total liens) × pct, and both nets are gross − liens − costs − that fee. The record stores neither convention as 'the' answer, so no one can later claim the software picked the fee basis. Creation refuses a gross of zero or less, a fee percentage outside 0–100, and a negative costs figure. 'Stage gross into trust' posts a genuinely balanced, audited double entry — debit trust:bank, credit trust:client, kind 'trust-receipt' — through the kernel ledger, which independently refuses any unbalanced, zero-value or non-finite transaction. Because the entry credits trust:client (a liability), the money is booked as the client's, never as income; the kernel throws outright on any transaction that touches a trust account and an operating income account unless it is explicitly flagged 'trust-transfer'. Staging is a one-shot gate per statement: the handler refuses with 'Already staged to trust.' if that record's staged flag is already set, so one statement cannot post two receipts.

Does not do

It does not know your retainer. It never reads the engagement letter, so it cannot tell you which fee convention governs, and it will happily compute a contingency percentage on a matter whose signed retainer is hourly. It does not apply any statutory reduction, court-approval requirement, structured-settlement rule, or HST on fees — the note under the form says so and means it. It does not disburse anything. Staging puts the GROSS into trust and stops; nothing in this room or anywhere else in Chambers pays a lienholder, pays the client their net, or reimburses costs out of trust. It does not verify a lien exists, that the amounts are current, or that a lienholder has been notified. It does not check that the money actually arrived — 'Stage gross into trust' is your assertion, not the bank's. Statements cannot be edited or deleted once computed; a correction means a new statement and both remain on the file.

Feeds into

POST /r/waterfall/stage writes a ledgerTxn that appears immediately in Trust & Books (28) in the firm and per-matter ledger, in the 'Position' card, in both computed legs of the By-Law 9 s.18 three-way reconciliation, and in the trust CSV for the accountant. Because it raises trust:bank for the matter, it also raises the ceiling on 28's earned-fee transfer gate, and it blocks the Closing Room (26) from closing the matter until trust:bank is back to zero. The waterfall records themselves are read only by this room — they are NOT in the Closing Room's transfer-of-file bundle, and Billing (34) never reads them; a contingency invoice in 34 simply carries fees of zero and points you back here.

Watch out

The lien field is split on commas FIRST, so a lien amount typed with a thousands separator is silently mangled: 'OHIP subrogation:4,200' becomes a $4 lien named 'OHIP subrogation' plus a $0 lien named '200'. The client's net is then overstated by $4,196 and nothing warns you. Type lien amounts with no commas. Anything after the last colon that is not a number becomes 0, again silently. A negative lien amount is accepted and increases the client's net. The stage-once gate is per statement record, not per matter: if you compute the waterfall twice (a revised figure, a typo re-entered) you have two statement cards and each carries its own 'Stage gross into trust' button — staging both posts the gross into trust twice and doubles the trust liability, with no warning. Stage exactly one statement per settlement and satisfy yourself the tag on every other card still reads 'not yet in trust'. Fee-on-gross and fee-on-net are both computed after costs advanced are deducted from the net, but costs are never deducted from the fee base. Selecting a destroyed matter and opening this room produces a bare '410 — This matter has been destroyed under its retention schedule' page rather than an explanation.

Judgment & Enforcement /r/judgment

The room for the period after you win, when a judgment is a piece of paper and not yet money. It records each judgment as entered, runs simple post-judgment interest to today so you always know the current figure to demand, tracks which enforcement steps are running against which debtor, and records recoveries until the debt is satisfied. It also carries a standing appeal-clock alarm, because a judgment on the file means an appeal period is running whether or not anyone diarised it.

How to use it

Open the matter. In 'Record a judgment', fill 'Judgment debtor' (as named in the order — required), 'Court' (required, e.g. 'Ontario Superior Court of Justice'), 'Amount' (positive; you may type it as '$1,500.50' — dollar signs, commas and spaces are stripped), 'Entered' (a date picker; must be a real calendar date), and 'Post-judgment interest %' (required; you may type '5.25%'; enter 0 if no interest runs). Press 'Record'. Nothing here guesses a rate — enter the rate the order fixes or the rate prescribed by the debtor's jurisdiction as at the date of entry. Each judgment then renders as a card headed '<debtor> — <court>' with a tag reading 'outstanding' or 'SATISFIED', and a one-row table: Entered, Rate, Principal, Interest to today, Per diem, Recovered, Owing today. On an outstanding judgment you get two forms side by side. Left: type the figure into 'Payment received' and press 'Post recovery' — the flash tells you the amount posted and either 'Judgment satisfied.' or 'Still owing ~<figure>.' Right: choose from the 'Enforcement step' dropdown — demand letter, garnishment, writ of seizure / judgment lien, examination in aid of execution, domestication (other jurisdiction) — and press 'Start step'. Started steps appear in a Step / Started / Status table on the card. If any judgment is on the file and no open deadline on the matter mentions an appeal, a red bar appears at the top reading 'APPEAL CLOCK UNCALENDARED' with a link 'Calendar the appeal clock →' to room 21. Use 'Print / save as PDF' to produce the 'Statement of judgment debt — <matter> — as at <today>' — forms, chrome and the room heading drop out; the cards, the summary line and the per-judgment tables print.

Guarantees

Interest is computed, never stored: principal × rate/100 × whole days since entry ÷ 365, simple, recomputed every time you load the page — so the figure on screen is always current to today and can never go stale in the record. A judgment whose entry date will not parse accrues zero rather than poisoning every column with NaN. Money and rate inputs are validated by regex and refused with a flash rather than coerced silently: a garbage amount never becomes zero behind your back. Debtor, court, amount, a real entry date and a rate are all mandatory. Enforcement steps are drawn from a fixed whitelist and the room refuses a duplicate — starting a step already active against the same judgment flashes 'Already running: <step> against <debtor>. Nothing recorded twice.' On a recovery, the ledger entry is posted BEFORE the judgment record is touched, so if the books refuse the transaction the recovery is not recorded on the judgment; there is no half-state. Satisfaction is derived, not typed: owing = principal + accrued interest − recovered, and satisfied is set when that is at or below half a cent. Every judgment, step and recovery is written to the tamper-evident audit chain, and the ledger posting is audited separately.

Does not do

It does not calculate your post-judgment interest rate — it uses only the number you type, and it will run 12% for a decade if that is what you entered. It does not compound. It does not know exemptions, garnishment procedure, priority between execution creditors, or reciprocal-enforcement routes; the note on every card says these are per-jurisdiction reference material to be checked before you levy. Enforcement steps have no completion, abandonment or outcome state anywhere in the code — every step you start reads 'active' forever, and there is no way to close one. It does not calendar the appeal period; the alarm only tells you no open deadline on this matter mentions an appeal, and you must go to room 21 and compute it. It does not chase anything, generate a demand letter, or produce a writ.

Feeds into

Each recovery writes a ledgerTxn that shows in Trust & Books (28) in the ledger table and the accountant's general-ledger CSV (it does not touch trust, so it is absent from the trust CSV and from both computed legs of the three-way reconciliation). The judgment records drive the appeal-clock alarm cards in Calendar (21) and the cross-matter alarms on the Desk (27), and both 'judgment' and 'enfStep' records ride in the Closing Room's transfer-of-file bundle. Nothing in Billing (34) reads a judgment, so a costs award recorded here is never billed to the client from this record.

Watch out

A recovery is posted to the FIRM'S OPERATING account: debit operating:bank, credit ar:client, kind 'recovery' — the note under the form says in terms 'a recovery is not trust money'. There is no route in this room to receive a judgment recovery into trust. If what you have collected is your client's money rather than your own taxed costs, that posting is not where it belongs and you must not rely on this room to keep client funds out of the firm's account. Crediting ar:client with no matching invoice will also drive the matter's receivable negative. 'Satisfied' is sticky and is judged on the interest accrued at the moment of that payment: a judgment closed out by a payment that just covered it will show SATISFIED forever, its payment and enforcement forms disappear, and it drops out of the 'Owing today' total — even though the same arithmetic keeps accruing interest in the background. If a debtor pays 'in full' and interest continues to run, this room gives you no way to record it. Recoveries cannot be reversed or corrected: there is no edit or delete for a judgment, a step or a payment. The 'Owing today' figure is clamped at zero for display, so an overpayment is invisible. The appeal-clock test here matches any open deadline whose rule id, citation or description contains 'appeal' in any case, which is broader than room 21's test — so silencing this bar does not necessarily silence room 21's, and that is deliberate.

Closing Room /r/closing

Where a file is closed properly, held for its retention period, and — eventually — destroyed with a certificate you can hand a client. It carries three things: a three-step closing checklist that is a real record on the file and a real gate on closing; the retention and destroy-eligible dates; and, for an administrator, the transfer-of-file bundle you produce when the client discharges you or takes the file to successor counsel. On a destroyed matter it is the only room that still renders anything, and what it renders is the certificate of destruction.

How to use it

Open the matter. The left card, 'Closing checklist — <matter>', shows a small summary: how many closing steps are recorded, the trust balance, the appeal window for the matter's jurisdiction (with a 'calendar it →' link), and the status. Below that are three tickboxes: 'Final account rendered to the client', 'Original documents returned', and 'Closing letter sent — appeal window and remaining limitation dates spelled out'. Tick what is actually done and press 'Save checklist'; the flash reads 'Closing checklist recorded — N/3 steps done' and a line appears reading 'Recorded by <name> on <date>'. Partial progress is kept, and unticking is allowed while the matter is open. When all three are recorded a 'Close the matter' button replaces the outstanding-steps note; press it. If any step is unrecorded you get 'Refused: N of 3 closing steps are not recorded.' If money is still in trust you get 'Refused: <figure> still held in trust for this matter. Disburse it in Trust & Books first.' On success the flash reads 'Matter closed on a recorded checklist. Retention clock running', the status tag becomes 'closed <date>', and the checklist becomes read-only — the form is replaced by the recorded ticks. The right card, 'Retention & destruction', shows the reference retention period (10 years for Ontario and federal Canada, 7 for US federal and New York, 10 for anything else) and the destroy-eligible date, computed as closedAt plus that many years. Once the matter is closed and you are an administrator, a destruction form appears: type the matter title exactly into 'Type the matter title exactly to destroy it', tick 'I understand destruction is cryptographic and irreversible', and press the red 'Destroy — shred the encryption key'. The bottom card, 'Transfer of file', is administrator-only: type the matter title exactly and press 'Export transfer bundle (JSON)' to download a file named transfer-<matterId>-<date>.json. Both the closing summary and the certificate print cleanly via 'Print / save as PDF'.

Guarantees

The closing gate reads the STORED checklist record, not the boxes on the screen — you cannot close by ticking on the way past. If you tick something on the close form itself, those ticks are merged into the stored record and persisted BEFORE the gate is tested, so a refusal never loses a tick. The trust gate is real: closing is refused while k.ledger.balances(matter)['trust:bank'] exceeds half a cent. Both gates are re-tested on every close attempt. Once closed, the checklist is frozen — POST /check refuses with 'The matter is closed — its checklist is the closing record and no longer editable' — and a second close attempt is refused with the date the retention clock started. Destruction is administrator-only (checked in the handler, not just hidden in the page), refuses a matter that is not already closed, and refuses unless the typed title matches the stored title exactly AND the acknowledgement box is ticked. It then destroys the matter's encryption key and removes its sealed records from the live store; the room says plainly on the certificate that archives taken before that date still hold the sealed records and the wrapped key until they age out, so destruction is not yet irreversible everywhere. The certificate's date and author are recovered from the audit chain — the one place they survive the key. The transfer bundle is administrator-only, refuses a destroyed matter, requires the exact title typed, reads everything through the matter-scoped store and the matter-filtered ledger so no other matter's data can enter it, and reduces documents to metadata only (id, title, bates, custodian, date, privilege, issues, createdAt) — decrypted document text never enters a browser download. Both the export and the destruction are written to the audit chain, the export recording how many records left.

Does not do

It does not stop you destroying a matter before its destroy-eligible date. The date is displayed and nothing enforces it: the moment a matter is closed, an administrator can shred it. Treat that date as a note to yourself, not a lock. It does not check that a final account was actually rendered, that originals actually went back, or that a closing letter was actually sent — all three are self-declarations. It does not check for unbilled time, an unpaid invoice, an outstanding receivable, an open limitation or appeal date, an undertaking still owing, or an active enforcement step; none of those block closing. The retention periods are a labelled reference schedule and the card says to confirm them against the current law society schedule. The transfer bundle is NOT the whole file: it carries fact, deadline, bf, document metadata, witness, depoTopic, digest, undertaking, adrSession, offer, judgment, enfStep, timeEntry, draft and citation_instance records plus the matter's ledger and balances — and nothing else. Invoices, disbursements, the engagement letter, conflicts records, exhibits and production volumes are not in it. It does not send the bundle anywhere, and it does not hand over the encrypted documents themselves — those move by separate secure handover between counsel.

Feeds into

Closing writes status 'closed' and a full-ISO closedAt onto the matter record, which every room sees via ctx.matter and which drives the destroy-eligible date here. Destruction sets status 'destroyed' and destroys the key, after which rooms 25 and 26 show a plain explanation, rooms 24 and 34 return a 410 page, and room 28 filters the matter's transactions out of its screen and its CSVs (though those transactions survive in the firm ledger log). The closing checklist record is read by this room only. The transfer bundle is a download and feeds nothing inside the application.

Watch out

The trust gate tests 'greater than 0.005'. A NEGATIVE trust balance on a matter therefore passes it and the matter closes with the books out. Check the 'Trust balance' row reads 'zeroed' from the position card in room 28 rather than assuming a passed gate means zero. There is currently no way at all in Chambers to pay a client, a lienholder or a third party out of trust — the only routes that reduce trust:bank are room 28's flagged earned-fee transfer to operating. In practice that means a matter with settlement funds staged from room 24 cannot be brought to a zero trust balance by any honest posting available in the software, and therefore cannot be closed here. Do not resolve that by calling the client's money 'fees' and transferring it out; get the balance corrected properly outside the app. The three checklist steps are stored by key name, not position, so the list can be reordered safely — but if a developer ever renames one, every matter that had it ticked silently loses that tick and reopens the gate. The appeal-window row shows the first rule in the matter's jurisdiction whose id contains 'appeal'; it is reference text and a link, not a diarised date. On a destroyed matter, if the shred entry has scrolled past the last 500 audit entries this room reads, the certificate prints 'recorded in the audit chain' instead of a date and author.

Trust & Books /r/books

The firm's ledger and its trust account, plus the daily docket. Everything with a dollar sign that any other room posts — settlement receipts from room 24, enforcement recoveries from 25, disbursements and invoices and payments from 34 — lands here in one append-only, double-entry ledger. This is also where you record time, where you receive a retainer into trust, where you move earned fees out of trust by the one flagged path that is permitted, and where you run and record the By-Law 9 s.18 monthly three-way trust comparison. The page opens with the time form because docketing is the thing done here every day.

How to use it

With a matter open, the page leads with 'Time — <matter>' and a tag showing unbilled work in progress. Fill 'Hours' (must be greater than zero), 'Rate', the 'UTBMS' dropdown (L110 Fact investigation, L120 Analysis & strategy, L190 Other case assessment, L210 Pleadings, L310 Written discovery, L330 Depositions, L430 Trial & hearing) and 'Narrative — the task, not the file', then press 'Record time'. If the narrative is empty, under twelve characters, or one of the boilerplate phrases ('work on file', 'attend to file', 'various', 'general', 'as discussed', 'per instructions' and the rest), the entry is still saved but the flash warns you and the row is tagged 'lint: <reason>' in red. Below the time table sits the 'Fee commitment' card, which reads the executed engagement room 03 posted on signature: the signed version, the fee terms, and — on a flat-fee engagement only — the expected retainer against what is actually held, tagged 'funded' or 'REPLENISH'. Then three cards. 'Position' shows Trust bank, Owed to clients, and whether they agree. 'Receive retainer into trust': enter a positive 'Amount' and an optional 'Memo', press 'Post to trust'; the flash reads 'Posted <figure> to trust — held for the client, not earned.' 'Transfer earned fees': enter 'Amount (invoiced & earned)' and a mandatory 'Invoice reference' such as 'Invoice 2026-014', then press the red 'Trust → operating (flagged)'. Below sits 'Three-way reconciliation — firm trust account': legs 1 and 2 are computed for you (trust ledger balance, and the sum of client trust liabilities broken down per matter), and you type the bank's own number into '3 · Bank statement balance' with a 'Statement date' and press 'Run three-way reconciliation'. The result is stored either way and the last six comparisons are tabled beneath, tagged RECONCILED or OUT OF BALANCE with who ran them. At the foot, 'Accountant handoff': choose 'Whole firm' or 'This matter' in the 'Scope' dropdown once, then press 'General ledger CSV', 'Trust ledger CSV' or 'Time entries CSV'. Printing this page yields the trust statement — position, reconciliation record and ledger; every form and the accountant handoff drop out.

Guarantees

The kernel ledger enforces true double entry on every posting from every room: at least two lines, an account on each, debits equal to credits in integer cents, no infinite or non-numeric leg, and no zero-value transaction. Above that sits the rule that matters most: any transaction touching a trust account and an operating income account is thrown out unless its kind is explicitly 'trust-transfer'. Fees cannot come out of trust by any other route, in any room. The earned-fee transfer here is additionally gated by By-Law 9 s.7 through kernel/trust.js: the amount is refused if it exceeds this matter's own trust holdings, with the two sides deliberately rounded in opposite directions (available floored to whole cents, the payment ceilinged) so a position of $99.996 cannot fund a $100.00 withdrawal. The refusal flash names the figure held and cites s.7. No client's money funds another's. A transfer must name the invoice it satisfies — the handler, not just the form, refuses a blank reference, so the ledger can never hold an unattributed withdrawal from trust. Retainers post as debit trust:bank / credit trust:client, so client funds sit as a liability and never as income. Time entry refuses hours of zero or less. Every figure that reaches a total is coerced so a legacy NaN reads as zero and never poisons a sum or prints 'NaN' on a bill. The three-way comparison is one implementation shared between the card you look at and the record that is written, and the record is stored whether it balances or not — law societies audit the misses too. Every posting, every reconciliation and every CSV export is written to the audit chain. Reads are wall- and shred-aware twice over: the kernel excludes walled matters, and this room additionally restricts everything on screen and in every CSV to matters you can see and never a destroyed one.

Does not do

There is no way to pay money OUT of trust to anyone but yourself. The only route that reduces trust:bank in the entire application is the earned-fee transfer on this page. You cannot pay a lienholder, refund a client, pay a client their net settlement, or fund a disbursement from trust. Do not reach for the fee-transfer button to move client money — it books the amount to operating fee income, which is exactly what By-Law 9 forbids. The 'Invoice reference' on a transfer is free text: nothing checks that an invoice of that number exists, that it was issued, that it was for this matter, or that the amount transferred is what was billed. The s.7 gate proves the money is there; it does not prove the fee was earned or invoiced. Nothing here reconciles your operating account — only trust. Nothing posts a bank fee, an interest credit, a returned cheque or a transfer between trust accounts. The room does not calculate or record HST on anything. It does not remind you that the s.18 comparison is monthly, does not refuse further trust activity after an out-of-balance result (the flash says to investigate; nothing enforces it), and does not check that your statement date is a month end or that you have not skipped a month. The reconciliation record cannot be corrected or deleted. The pre-bill lint stamped on a time entry here is advisory only — the entry saves regardless; the gate that actually blocks a bill lives in room 34.

Feeds into

Time entries created here are the sole source of billable work for Billing (34) — nothing else creates them — and are read by Client (05) for budget-versus-actual, by the client Portal (36), and are carried into the Closing Room's transfer bundle. The trust:bank balance this room maintains is the figure the Closing Room (26) tests before it will close a matter, and the ceiling the s.7 gate enforces on the next fee transfer. Every posting from Settlement Waterfall (24), Judgment & Enforcement (25) and Billing (34) appears in the ledger table here. Reconciliation records are firm-scope and read back only by this room's last-six table. The 'Fee commitment' card reads the engagement marker written by Retainer & Scope (03) and never reopens the matter.

Watch out

The three-way comparison's first two legs are computed over matters VISIBLE TO YOU, but leg 3 is the whole bank account. If an ethical wall screens you from a matter that holds trust money, your reconciliation will read OUT OF BALANCE by exactly that matter's holdings and there is nothing you can do about it from this screen — the other lawyer must run it. The CONTRACT SHEET says this room refuses a rate of zero or less; it does not. The handler refuses only a NEGATIVE rate, and the flash invites 'enter 0 for no-charge time', which stores a zero-value entry that will be swept into a draft invoice as a zero line. Hours are refused at zero, rate is not. The 'REPLENISH' warning only ever fires on a FLAT-FEE engagement, because the expected-retainer figure room 03 posts is null for hourly and contingency retainers — an hourly client whose trust has run dry produces no warning here at all. The retainer and transfer forms do not check whether the matter is closed or destroyed: selecting a destroyed matter still renders both forms, and a posting will succeed and land in the firm ledger, invisible on this page (which filters destroyed matters out) but visible to the closing gate in room 26 and to firm-wide balances. Nothing in this room can be reversed — the ledger is append-only and there is no journal-entry or correcting-entry form, so a mistyped retainer amount can only be answered by an opposite posting you have no form to make. The CSVs disclose memos and time narratives in full and are for your accountant, never for production; every field beginning with =, +, - or @ is prefixed with an apostrophe so a spreadsheet cannot execute it.

Billing /r/billing

The invoice run. It gathers everything unbilled on the matter — time recorded in room 28 and disbursements recorded here — applies the fee model taken from the signed engagement letter, and produces one numbered draft invoice you can review, write down line by line, and issue. Issuing posts the receivable to the ledger and stamps every entry on the bill as billed so it can never be billed twice. It is also where you mark an invoice paid, and where you print or download the statement the client actually receives.

How to use it

Open the matter. If an invoice is open or selected it leads the page as a full invoice sheet; the working desk sits underneath. On the desk, the 'Run a bill' card shows the fee model with its source ('engagement v3', or 'default (no engagement on file)'), the unbilled time and its value, the fees at that model, the unbilled disbursements, and the pre-bill lint verdict. To add an out-of-pocket cost, use 'Record a disbursement': type a 'Description' (required, e.g. 'Court filing fee — statement of claim'), an 'Amount' (must be positive and at least one cent after rounding) and a 'Date incurred' (defaults to today), then press 'Record disbursement'. To bill, press 'Generate draft invoice'. Every unbilled time entry and every unbilled disbursement is swept into one numbered draft ('2026-014' style) and you are taken straight to it. On the sheet, the 'Professional fees' table lists Narrative, Hours, Rate, Amount, Write-down and Net; on a draft the Write-down cell is a number box you can type into, capped at the line's own value. Fill in what you are writing off and press 'Apply write-downs'; the flash reports the net fees. When the sheet is right, press 'Issue invoice'. The flash reads 'Invoice <number> issued — receivable recorded, N time entries and M disbursements marked billed.' From then on the sheet shows 'Mark paid'; press it when the money arrives and the flash reads 'receivable cleared to operating'. A draft you do not want is removed with 'Discard draft' — its time and disbursements go back to unbilled. Every sheet carries 'Print / save as PDF' (which prints that one invoice alone — the desk, the unbilled WIP and every other invoice on the matter are marked no-print and cannot ride out on a client's bill) and 'Download .txt' for a plain-text statement.

Guarantees

Nothing is billed twice. An entry counts as unbilled only if its state is not 'billed' AND it carries no invoice id, and at issue every frozen line on the draft is resolved back to its live record before any money moves: if any line's underlying entry is missing or has been claimed by another invoice, the whole run is refused with the specific lines named and the draft is left untouched. Only one draft may be open on a matter at a time. Only a draft can be written down, discarded or issued; an issued invoice cannot be issued again, and only an issued invoice can be marked paid. Write-downs are clamped between zero and the line's own coerced value, so no line can be written down below zero or beyond what it is worth. The pre-bill lint is the hard gate here: issue is refused, with a flash and an audited 'billing.issue.blocked' entry, while any narrative is empty, under twelve characters, or one of the listed boilerplate phrases. Issue is also refused when the total is zero or less, and the receivable is proved balanced in integer cents before it is offered to the ledger, so a rounding slip flashes a refusal rather than throwing part-way through. The transition itself is a single synchronous run — records marked billed, invoice claimed as 'sent', receivable posted last — so a failure can never leave a posted receivable on an invoice still open to re-issue. The hourly fee model takes each line's rate from its own time entry and never invents a firm-wide rate. Invoice numbers come from a firm-wide counter that is never reused and holds no matter identity, so nothing leaks across an ethical wall. Draft, write-down, issue, block, payment, discard and download are all audited.

Does not do

There is no tax. No HST, GST or PST line appears on any invoice, in the downloaded statement, or in any ledger posting made by this room — the total due is fees plus disbursements and nothing else. If your bills must carry HST, this room does not produce a compliant account and you must not send its output as one. It does not record partial payment: 'Mark paid' books the entire invoice total and there is no way to record anything less. It does not apply a trust credit — an invoice is never netted against money held in trust, and paying a bill out of trust is a separate, manual, flagged transfer you perform in room 28 by typing the invoice reference yourself. It does not chase, age or report on receivables. It does not carry a client address, a payment-terms line, interest on overdue accounts, or the notice of a client's right to have an account assessed. It does not let you edit a narrative — a line blocked by lint must be fixed in room 28, and since a time entry cannot be edited there either, in practice you discard the draft, correct the docket, and regenerate. Once issued, an invoice cannot be reversed, credited or cancelled by anything in this room.

Feeds into

Issuing writes a ledgerTxn (debit ar:client for the total; credit operating:income:fees where fees are positive; credit operating:expense:disbursements where disbursements are positive, kind 'invoice') and marking paid writes another (debit operating:bank / credit ar:client, kind 'payment') — both appear immediately in Trust & Books (28) and in the general-ledger CSV. Recording a disbursement posts its own entry (debit operating:expense:disbursements / credit operating:bank) the moment you save it, before it is ever billed. Issuing stamps state 'billed' plus the invoice id and number onto each time entry, which is what removes it from the WIP figure in room 28, from Client (05) budget-versus-actual and from the Portal (36) pack. The fee model is read from the engagement written by Retainer & Scope (03). Invoice records themselves are read by this room alone — they are not in the Closing Room's transfer-of-file bundle.

Watch out

On a CONTINGENCY matter this room is a trap. The fee model comes from the signed engagement, contingency fees compute to zero here (they come out of the recovery in room 24), but 'Generate draft invoice' still sweeps every unbilled time entry onto the draft — and issuing marks all of it BILLED at zero value, permanently and irreversibly. If the matter has no disbursements the total is zero and issue is refused, so you must discard; but if it has even one disbursement, issuing that disbursement-only bill silently consumes the whole docket. Check the fee model on the 'Run a bill' card before you press issue on a contingency file. The same shape applies to a flat fee: the draft sweeps all the time, the fee is the flat amount less write-downs regardless of what the time was worth, and issuing marks all that time billed. Write-downs are recorded but have no effect at all on a contingency invoice, since fees are fixed at zero. The invoice number's year prefix is taken from today's date but the counter is firm-wide and never resets, so numbering runs 2026-014, 2027-015 — the year in the number is not a per-year sequence. Fix lint before generating the draft, not after: the desk's 'Pre-bill lint' row counts the blocked narratives sitting in your WIP precisely so you find out before a draft is burned. A discarded draft's number is gone forever. Selecting a destroyed matter and opening this room produces a bare 410 page rather than an explanation.

8Research connectors and the daily desk

CanLII /r/canlii

This is the Canadian case-law connector. You paste text — a factum, a memo, an opposing party's brief — and it finds the Canadian citations in it, turns the ones it can into CanLII case identifiers, and pulls the real case record from CanLII's official API so you know the citation points at an actual decision. Resolved cases are saved onto the open matter as authorities, and a firm-wide cache means a case resolved once on any file costs no second API call. It also pulls CanLII's citator counts: how many decisions cite this case, and how many it cites.

How to use it

Open the matter you are working on from the matter selector at the top of the page before you start, or nothing you resolve will be kept. The main card is 'Citation scanner', with a heading chip reading either 'live — official API' or 'link-out — no key'. Paste your text into the box labelled 'Paste any text — factum, memo, opposing brief' and press 'Scan for Canadian citations'. The page reloads with a 'Scan results' table at the very top showing, for each citation found, the Citation, the Kind (neutral, canlii or scr), the derived CanLII ids in the form databaseId/caseId, and the Actions available. Every row gets an 'Open on CanLII →' link, which is a plain search deep link into canlii.org. Rows for neutral cites (2008 SCC 9) and CanLII cites (1999 CanLII 1527 (ON CA)) also get a button reading 'Resolve via API' when a key is stored, or 'Resolve (needs key)' when one is not. Press it. If resolution succeeds you get a flash naming the case and citation, telling you whether it was saved to the open matter, whether it came from cache, and reminding you that 'Resolution is identity, not verification: Citation Check (room 08) still stands.' The case then appears in two places: under 'Resolved authorities — <matter title>' with columns Citation, Case, Decided, Docket and Link, and in the firm-wide 'Resolution cache' table below. To pull the citator, find the case in the 'Resolution cache' table and press 'Pull citator' (or 'Refresh citator' if it has been pulled before); the Citator column then reads 'cited by N · cites N'. The 'Connector' card at the foot shows Mode, the last four characters of the stored API key, and the size of the cache. If you are an administrator — both seats are — you get a field labelled 'API key (blank to clear)' and a 'Save key' button there; saving writes an audit line canlii.key.set (or .cleared) and stores the key encrypted at rest, and clearing it drops the room back to link-out mode.

Guarantees

Scanning is entirely local. kernel/canlii.js parseCitations() is pure regular-expression work over the text you pasted, with no network call of any kind, so pasting a privileged draft into the scanner sends nothing anywhere. When you press Resolve, the only thing that leaves the building is a request to https://api.canlii.org/v1/caseBrowse/en/<databaseId>/<caseId>/ carrying the firm's API key in the query string; the pasted text, the matter, the client and the file name are never transmitted. The citator does the same against /caseCitator/en/. The module never scrapes canlii.org and never bulk-downloads — only the documented REST API and citation deep links, both permitted. Requests carry a 12-second timeout and every HTTP failure comes back as a readable flash (refused key, not found, rate limit, timeout) rather than a crash. Resolving the same citation twice on the same matter does not create a second authority: the handler looks for an existing authority with source 'canlii-api' and the same cite (case-insensitively) and tells you 'already on <matter>'. A URL that did not come back beginning http:// or https:// is never rendered as a clickable link. Resolutions are written into the matter's encrypted scope and generate audit entries; the API key is never written to the audit chain.

Does not do

Resolution is identity, not verification. A green result means CanLII has a case at that identifier — it says nothing about whether the case is still good law, whether it was overruled, distinguished or reversed, or whether it supports the proposition you cited it for. The citator gives you two raw numbers and nothing else: there is no editorial treatment, no flags, no 'negative history' signal of any kind. A case cited two hundred times may have been gutted on appeal and this room will not tell you. Citation Check (room 08) remains the gate before anything reaches a filed document, and it is human-confirmed. SCR citations ([2008] 1 SCR 190) are recognised but marked 'link-out only' — there are no ids and no Resolve button for them, so they are never resolved here. The scanner only knows the court codes hard-coded in kernel/canlii.js; a provincial or tribunal code outside that list is simply not seen, and you will get 'No Canadian citation in that text' with no warning that a cite was skipped. The case identifier is derived arithmetically from the citation, not looked up, so an unusual case can return 'Not found on CanLII (id derivation may not match this cite)' even though the case exists. Nothing here checks pinpoints, quotations or parallel cites. Authorities saved from this room deliberately carry no proposition, no weight (binding or persuasive) and no adverse flag, and the Research Desk (room 07) refuses to send them to the citation gate — you must re-enter the case under a memo with the proposition it stands for. Finally, the outbound API request itself is not written to the audit chain from this room (see concerns).

Feeds into

Resolved cases are written as `authority` records in the open matter's encrypted scope, stamped source 'canlii-api' and resolved: true, with cite, title, url, court (the CanLII databaseId), decisionDate and docket. Only this room reads them back; the Research Desk (07) filters them out of its own authority list and merely counts them. The same underlying connector is reached by Citation Check (room 08) through kernel/cite-resolve.js, which is the path that does write an outbound-egress audit line. The API key lives in the firm-scope `setting` record with id 'canlii' and is read by kernel/api.js as k.canlii.apiKey(). The resolution cache is a firm-scope `canliiCase` record keyed '<databaseId>/<caseId>'.

Watch out

Without an API key the room still scans and still gives you CanLII deep links, but Resolve and the citator both refuse — the citator refusal reads 'Citator needs live mode (API key).' If no matter is open, scanning and resolving still work but nothing is saved, and the flash says so; it is easy to do a morning's work and keep none of it. The resolution cache is firm-wide and is not filtered by ethical walls, so both lawyers see every case either of them has resolved (no matter is named on those rows). The cache table shows only the 25 most recently fetched cases although the Connector card counts all of them. The citator stores a sample of the first ten citing cases but the page never displays it — you get counts only. A cached resolution is never refreshed by Resolve; only 'Refresh citator' re-hits the API, and it refreshes the counts, not the case metadata.

PACER / RECAP /r/uscourts

This is the US federal courts connector. It searches the Free Law Project's CourtListener API — millions of federal opinions, plus every PACER document the RECAP community has already archived — and lets you save what you find onto the open matter. It exists so that you check the free archive before you pay PACER ten cents a page for the same document. PACER itself is not integrated: it is linked, by hand, for what RECAP has never seen.

How to use it

Open the matter first if you want to keep anything. The main card is 'Search the RECAP archive', chipped either 'token — higher limits' or 'anonymous — rate-limited'. Type into the field labelled 'Query — party, case name, keywords' and choose the corpus from the dropdown labelled 'Corpus', which offers 'Opinions (case law)' or 'RECAP dockets & filings'. Press 'Search'. Results render at the top of the reloaded page under a heading giving the total match count and the query you ran, in a table with columns Case (a link out to courtlistener.com), Court, Filed, then either Citation or Docket depending on the corpus, then 'Cited by' as a right-aligned figure, and a final column holding a 'Save to matter' button. At most twenty results are shown however large the match count. Press 'Save to matter' on a row you want on the file. What happens next depends on the corpus you searched: an opinion is saved as an authority and the flash reads 'Saved to <matter>: <case> — an authority. Citation Check (room 08) still verifies it before it reaches a filed document.' A RECAP row is saved as a docket reference and the flash warns 'a docket reference. The archive's copy is not the court's record; pull the filing itself before you rely on it.' Saved items appear under 'On the file — <matter>' with columns Case, Kind (tagged Opinion or Docket), Court, Date and Link. The 'Connector' card at the foot shows the connector status, the last four characters of any stored token, and two PACER links: 'Case Locator →' (pcl.uscourts.gov) and 'pacer.uscourts.gov →'. An administrator can paste a token into 'CourtListener API token (optional, blank to clear)' and press 'Save token'; that writes an audit line courtlistener.token.set or .cleared and stores the token encrypted at rest.

Guarantees

Your query text is what leaves the building, verbatim. The request is GET https://www.courtlistener.com/api/rest/v4/search/?q=<your query>&type=o|r&order_by=score desc, sent with a user-agent header of 'Chambers-platform' and, when a token is stored, an Authorization header carrying it. That means if you type your client's name, the opposing party's name or a distinctive phrase from an unfiled pleading, the Free Law Project receives it — attributed to the firm whenever the token is set. Nothing else about the matter goes with it. The request times out at 15 seconds and rate-limit, refused-token and other HTTP errors come back as readable flashes. Saving is guarded: a URL that does not begin http:// or https:// is refused outright with 'Refused: only http(s) links can be saved to the file', because the stored value is re-rendered as a clickable link. Saving the same document twice is prevented — the handler checks for an existing record of the same kind with the same CourtListener URL and answers 'Already on <matter>'. Saves are written into the matter's encrypted scope and audited; the token itself is never audited. PACER is never scraped and no PACER credential is stored anywhere in this room.

Does not do

This room does not search PACER. If RECAP has never archived a docket, it does not appear here at all, and a nil result is not evidence that no such case exists — you must go to the PACER Case Locator by hand. The archive is a community mirror: a RECAP docket may be stale, incomplete, or missing the exhibit you need, and the room says so in the save flash for a reason. Nothing here contributes your PACER purchases back to RECAP; that is a manual step outside the software. The citation shown is whatever CourtListener returned first in its citation array, and 'Cited by' is CourtListener's raw citation count, not a treatment signal — no Shepard's, no KeyCite, no negative history. An opinion saved here is not a verified authority: Citation Check (room 08) is still the gate, and the Research Desk (07) will refuse to send a connector-sourced authority to that gate until it is re-entered under a memo with a proposition. Only the top twenty results are ever shown and there is no paging, so a broad query silently hides the rest. There is no way to delete a saved authority or docket reference from this room. And the outbound search is not recorded in the audit chain (see concerns).

Feeds into

An opinion saved with corpus 'Opinions' becomes an `authority` in the matter scope stamped source 'courtlistener' with resolved: true (cite, title, court, decisionDate, url). A RECAP row becomes a `docketRef` stamped source 'recap' (caseName, court, dateFiled, docketNumber, url). Only this room reads either back; the Research Desk filters connector authorities out of its own list. The token lives in the firm-scope `setting` record with id 'courtlistener', read by kernel/api.js as k.uscourts.token(). Citation Check (room 08) reaches the same search function through kernel/cite-resolve.js for US citations.

Watch out

Without a matter open the search still runs but the save column reads 'open a matter to save' and nothing can be kept. Without a token the archive is still fully searchable, just rate-limited — a 429 comes back as 'CourtListener rate limit — add an API token or slow down.' The Corpus dropdown resets to Opinions on a fresh page load, so it is easy to run a docket search against the case-law corpus and conclude the docket does not exist. The Kind tag on the 'On the file' table is derived from which record type the row came from, not from anything stored on the row itself.

EDGAR /r/edgar

This is the SEC filings connector. It runs the SEC's official full-text search across everything filed on EDGAR since 2001 and links each hit to the primary document on sec.gov. For litigators it is the fastest route to material agreements filed as exhibits, disclosed litigation, related-party dealings and executive contracts — documents an opponent filed publicly and may have forgotten about. Filings you keep are written onto the matter file as encrypted references.

How to use it

This room will not search at all until an administrator declares a fair-access contact, because the SEC refuses automated requests that do not identify themselves. If none is set, the 'Connector' card renders first, chipped 'idle — no contact', and the search card is replaced by a notice telling you so. To set it, use the field labelled 'Declared contact email (blank to clear)' in the Connector card and press 'Save contact'; the address is validated as an email, stored, and an audit line edgar.contact.set (or .cleared) is written. Once a contact exists the layout flips and the search card leads. Open your matter, then type into 'Query — quotes for an exact phrase' — quotation marks give you an exact phrase — and optionally into 'Form filter (optional)', which takes a comma-separated list in the style of the placeholder, 10-K,8-K,S-1,DEF 14A. Press 'Search EDGAR'. Results appear at the top of the reloaded page under a heading giving the total filing count, your query and the form filter if you used one, in a table with columns Company, Form (a tag), Filed, Document (a link out to sec.gov, labelled with the filing's description) and a final column with a 'Save to matter' button. At most twenty hits are listed. Press 'Save to matter' and the filing is written to the file; the flash reads 'Saved to <matter>: <company> <form>'. Saved filings appear under 'On the file — <matter>' with a count tag, in a table of Company, Form, Filed and Document.

Guarantees

Your query text and the firm's declared contact email leave the building together on every search. The request is GET https://efts.sec.gov/LATEST/search-index?q=<your query>[&forms=<filter>], with a user-agent header reading 'Chambers-platform <the declared contact email>'. The SEC therefore receives both the search terms and an address that identifies your firm. Nothing about the matter or the client is transmitted. There is no bulk pull and no crawl: a request goes out only when you press the button, which is what the SEC's fair-access policy asks for, alongside its ten-requests-per-second ceiling. Searching is hard-gated on the contact being present — kernel/edgar.js refuses before any network call if it is missing. Requests time out at 15 seconds and a 429 comes back as 'SEC rate limit — slow down (max 10 req/s).' Saving refuses any URL that does not begin http:// or https://, and refuses a filing whose sec.gov URL is already on the file, answering 'Already on <matter>: <company> <form>'. Saved filings live in the matter's encrypted scope and are audited; the contact email is a firm setting, and the audit line records only that it was set or cleared.

Does not do

Full-text coverage starts in 2001. Anything filed before then is invisible to this room, and a nil result proves nothing about the pre-2001 record — the room points you at the sec.gov browse UI for that. Only twenty hits are shown with no paging, so a broad query hides the rest behind a total count. What is saved is a link and a little metadata, not the document: the filing itself is never downloaded, never stored, and never encrypted into the file, so if sec.gov moves or withdraws the document your saved row points at nothing. There is no verification that the linked document is the one you actually read, no diffing between filing versions, and no alerting when a company files something new. The form filter is passed straight through to the SEC without validation, so a mistyped form code silently narrows your search to nothing. There is no way to delete a saved filing from this room. The outbound search is not written to the audit chain (see concerns).

Feeds into

Each kept filing becomes a `secFiling` record in the matter's encrypted scope with company, form, date, description, url, adsh and source 'edgar'; it is refused unless both company and url are present. Only this room reads them. The contact lives in the firm-scope `setting` record with id 'edgar' and is read by kernel/api.js as k.edgar.contact().

Watch out

With no matter open, searching works but the save column reads 'open a matter to save'. The room deliberately reorders itself: with no contact declared the Connector card comes first, so if the page looks unfamiliar it is because the connector is idle. Clearing the contact silently disables all searching for both lawyers. The accession number (adsh) is stored and is used as the link label when a filing carries no description, which is why some rows read as a bare number.

Sources /r/sources

This is the honest registry of everywhere the firm does research, and the place where a search run on somebody else's system becomes part of your file. It holds a firm-wide shelf of external services with, for each, how it may lawfully be accessed — official API, credentialed account, commercial database with no API, or open website — and a per-matter log of what was actually searched and what came back. It is the answer, years later, to 'what did you actually look at?', and it is the honest home for the subscription databases that must never be scraped.

How to use it

Open the matter whose research you are recording. The first card is 'Record a lookup — <matter title>'. Choose the service from the dropdown labelled 'Source searched', which lists every name on the shelf. Type what you ran into 'What was searched' — the placeholder shows the register you want, 'Royalty rates, tire retreading licences, 2018–2024'. Then fill 'What came back — reference, export name, rate found' with enough to reconstruct the search, again as the placeholder models it: an export reference, how many comparables, the median figure, where the export was filed. Both fields are required; the software refuses a half-record with 'Query and result are both required — this is a diligence record.' Press 'Record on the file'. The lookup appears under 'Lookup record — <matter title>' with a count tag, in a table of When, Source, Query and Result, newest first. Below that sits 'The shelf', a table of Source (a link out to the vendor), Category, Access (tagged with the access model) and Notes, sorted by name. To add a service, open the collapsed disclosure at the foot reading 'Add a source to the shelf' and fill Name, URL, Category and the 'Access model' dropdown, plus 'Access & licensing notes' — the placeholder asks the right questions: API? Subscription? Scraping prohibited? Who holds the credentials? Press 'Add to shelf'. The button at the top labelled 'Print / save as PDF' produces the diligence record: a dated header, this matter's lookup log and the shelf it was searched on, with all page chrome, forms and buttons stripped.

Guarantees

Nothing leaves the building from this room. There is no connector here and no outbound request of any kind: the shelf is a list of links, and a lookup is text you type. Clicking a shelf link opens the vendor's site in your own browser, which is your browser's traffic, not the platform's. Lookup records are written into the matter's encrypted scope, so they carry the matter's own key and are covered by the ethical wall and by destruction of the matter. A lookup must name a source that is actually on the shelf — the handler checks the firm shelf by name and refuses otherwise with 'Choose a source from the shelf — add it below first if it is not there', because an unattributable search is not a diligence record. A source cannot be added without a name and a full http(s) URL, and any stored URL that is not http(s) is re-checked at render and never becomes a clickable link. The shelf is seeded once, only when it is completely empty, with RoyaltySource, CanLII, CourtListener / RECAP, EDGAR and PACER and their real access models.

Does not do

This room does not search anything. It does not log in to a subscription service, it does not fetch results, and it emphatically does not scrape a commercial database that has no API — the whole design premise is that such a service gets a link, a credential holder and a hand-written record. Nothing verifies that a lookup you recorded actually happened, or that what you typed as the result is what the service returned; this is your attestation, not the software's. There is no attachment: the export you mention is not stored here, only described. There is no edit and no delete for either a source or a lookup — once recorded, a row is permanent, typos and all, and appears in every printed diligence record thereafter. Access models are declarative labels, not enforcement: tagging a source 'commercial — no API' does not stop anyone doing anything, it records what the licence permits. The shelf is firm-wide and is not filtered by ethical walls, though it holds no client information.

Feeds into

Lookups are `lookup` records in the matter's encrypted scope, with source, query and result, both of the latter required. Sources are firm-scope `source` records with name, url, category, access and notes. Nothing else in the app reads either type; the value is the printed diligence record and the file itself. Note that room 08's citation instances carry an unrelated advisory field also called `lookup` — a different thing entirely.

Watch out

With no matter open the record card is replaced by a notice and only the shelf shows; the shelf needs no matter. The 'When' column shows only the date, not the time. The lookup list is sorted by the record's createdAt string, newest first. Because the seed only fires when the shelf is entirely empty, adding your own source before the seed has ever run means the five defaults never appear.

Workflow (the daily desk) /r/desk

This is mission control and the page you land on when you sign in. It reads across every room and owns almost nothing. It carries the firm-wide diary — every open deadline on every matter you can see, in one dated table — plus the limitation flag and the dual-diary second tick that LawPRO expects of a two-lawyer shop, an appeal-clock watchdog for any matter carrying a judgment with nothing calendared against it, and the bring-forward list kept visibly apart from computed deadlines. It is designed to be printed and put on the table at the Monday meeting.

How to use it

Signing in takes you here. Across the top is a strip of figures: Overdue, Due in 14 days, Limitation bars unticked, Open matters, In screening (which links to the Intake Desk), Held in trust (which links to Trust & Books) and 'Audit chain — N entries', which reads 'intact' or 'BROKEN'. Overdue and unticked limitation counts turn red when non-zero. Immediately below, any matter with a judgment on the record and no open appeal deadline gets its own red-bordered card reading 'APPEAL CLOCK UNCALENDARED', naming the matter and citing Courts of Justice Act, s. 6; r. 61.04, with a link reading 'calendar the appeal clock →' that opens that matter in Trial Calendar. Then comes 'Firm diary — every open deadline, every visible matter', a single table sorted by date so overdue rows lead, with columns Due, Days, Matter, Deadline, Authority and Limitation. The Days column shows a signed number — +45 for a date forty-five days out, -3 for one three days past — with a red 'OVERDUE' chip when negative and a 'soon' chip at fourteen days or less. The Limitation column is where the work is: a limitation or prescription date carries a red 'LIMITATION' tag, and beneath it, if nobody has yet ticked it, a button reading 'Verify date'. Press that button as the second lawyer and the tick is recorded under your name; the cell then reads 'verified — <name> <date>'. Below the diary is 'Bring-forwards BF — ticklers, never computed deadlines' listing Note, Due and Matter, with overdue BFs chipped. Last is a Matters table (Matter, Client, Jurisdiction, Posture, Status) linking each matter into the Client Desk, and for an administrator a link to Firm administration. The 'Print / save as PDF' button beside the diary produces the meeting paper: the dated diary, the appeal alarms and the bring-forwards, with the navigation, the statistics strip, every form and every button stripped out.

Guarantees

The dual-diary tick is a real gate, enforced in code and not merely displayed. POST /r/desk/verify refuses when the person pressing the button is the same person who calendared the date, answering 'Dual diary refused: the verifying lawyer must be a different person than the one who calendared the date. Ask your colleague for the second tick.' It refuses a second verification once one is recorded, naming who ticked it and when. It refuses a deadline it cannot reach on a matter you cannot open. A successful tick writes verifiedBy, verifiedById and verifiedAt onto the deadline and an explicit audit entry, diary.verified. The limitation flag itself is deliberately generous: a date counts as a limitation date if the rules.js rule id, or the citation string and description that every writer sets, or the rules.js record standing behind the id, matches limitation or prescription case-insensitively — so a hand-written 'Limitation period expires' with a cite of 'Limitations Act, 2002, s. 4' or 'CPLR 214(5)' is flagged, not missed. The walk across matters is wall-filtered before anything is decrypted: a matter you are screened from contributes nothing to the diary, the counts, the alarms or the Matters table, and you cannot see that it exists. A destroyed matter is skipped rather than crashing the page, and a scope that cannot be opened is skipped, never fatal. Nothing leaves the building from this room; it makes no outbound request at all.

Does not do

This desk computes no dates. It only reads what Trial Calendar (21), Intake (01), Discovery (12), Experts (15) and ADR (23) wrote, so a deadline nobody entered is a deadline this page cannot show you — a blank diary means nothing has been calendared, not that nothing is due. It shows only deadlines and bring-forwards whose status is open: closing a deadline in Trial Calendar removes it from this page entirely, including a limitation date and including its contribution to the 'Limitation bars unticked' figure, so a limitation bar marked done vanishes rather than staying visible as satisfied. It does not show the stale flag that Jurisdiction Desk (09) puts on deadlines when a matter's governing jurisdiction changes, so a date that room has already marked as needing recomputation still prints on the firm diary as though it were sound. The appeal watchdog is a keyword test, not a legal analysis: any open deadline whose id, citation string or description contains the word 'appeal' — an appeal book date, a hand-typed note — silences the alarm for that matter, and conversely once the notice of appeal is served and its deadline is closed the alarm returns and stays lit for the life of the matter. The watchdog fires on the mere existence of a judgment record and knows nothing about whether an appeal is actually available or already taken. The dual-diary tick records that a second person looked; it does not check the date, recompute it, or compare it to the underlying rule — the arithmetic and the weekend/holiday treatment are Trial Calendar's, and this page displays the result without re-deriving it. The tick cannot be undone from here. Verification is available only to the second lawyer as identified by who created the record, so a deadline imported or seeded without a recorded author is not protected by that gate.

Feeds into

Nothing is created here. POST /r/desk/verify updates existing `deadline` records in place, adding verifiedBy, verifiedById and verifiedAt — the only fields on a deadline that this room owns and the only writer of them in the app. Everything else on the page is read: `deadline` and `bf` and `judgment` per matter, firm-scope `inquiry` records in screening, the trust:bank balance from the wall-filtered ledger, and the audit chain's own verification result. Links out lead to Trial Calendar (21) for a matter's dates, Client Desk (05), Intake (01), Trust & Books (28) and, for administrators, /admin.

Watch out

The diary is cross-matter and needs no matter open; the matter selector at the top has no effect on it. A due date that is not a well-formed ISO date leaves the Days column blank rather than warning you. The 'Overdue' and 'Due in 14 days' counts are computed by string comparison against today's date in UTC, so a date due today counts as neither overdue nor, strictly, in the future — it shows as 0 days with a 'soon' chip. Because print hides every form and button, the printed diary shows the LIMITATION tag and any recorded verification but not the un-pressed 'Verify date' buttons: on paper an unverified limitation bar looks like a bare red tag, which is exactly the row to chase. The 'Audit chain — BROKEN' figure is the only warning you get that the tamper-evident chain has failed verification; it is not repeated anywhere else on the page.

9Production, affidavits and the client portal

Production /r/production

This is where you cut a documentary production volume and record, immutably, what went out the door, to whom, and on what date. It does not decide anything about a document: every call about responsiveness and privilege is made in Document Review (room 13), and Production simply takes the set as coded, freezes it, names a recipient, stamps a service date, and gives you two machine-readable load files plus a printable schedule and privilege log. Months or years later, when opposing counsel says you never produced something, the volume page is the answer to "what exactly did we produce, and what did we hold back?". Nothing about a served volume can be edited or deleted once it exists.

How to use it

Open the matter first — with no matter open the page reads "Open a matter to assemble its production volumes." and does nothing else. If no document has yet been coded responsive and not privileged, and no volume has ever been cut, the page shows only the empty state naming the prerequisite and a link, "Go to Document Review →". Do your coding there first.

Once there is something producible, the top left card is "Assemble a volume". It states four figures before you touch anything: "Producible now" (the count of documents coded responsive and not privileged), "Bates range" (the first and last bates in that set), "Withheld" (how many are on the privilege log), and "Not listed" (documents coded not responsive, which are produced nowhere and logged nowhere). Beside it, the "Producible set" card lists every producible document by Bates, Title, Custodian and Date; each bates number is a link into that document in Document Review.

To cut the volume, fill "Produce to (opposing party / counsel)" — this is required and the form is refused without it — and set "Date served", which is pre-filled with today's date. The date must be a real calendar date in YYYY-MM-DD form; a value such as 2026-02-31 is rejected with "Enter the service date as a real calendar date (YYYY-MM-DD)." rather than silently rolled forward. Then press "Assemble & serve this volume".

On success you are returned to the same page with a flash naming the volume, the recipient, the date, the document count, the bates range and the number withheld — for example "PROD001 assembled and served to Smith LLP on 2026-08-26: 42 documents (DEF-000001–DEF-000061), 9 withheld on the privilege log." The volume number is assigned automatically as PROD001, PROD002 and so on, taking the highest existing PROD number plus one.

The new volume appears under "Volumes produced" with columns Volume, Bates range, Produced to, Served, Docs, Privilege log, Status and Load file. Click the volume name to open its own page. That page repeats the particulars, then shows "Index of documents produced" and "Privilege log as served", and is the page you print when you need to serve or re-serve the index and log.

For the load files, press "Load .dat" or "Images .opt" on the volume's row (the same two buttons appear on the volume page). Each downloads immediately as a plain text file named after the volume — PROD001.dat, PROD001.opt. The .dat is a Concordance-convention file with the five columns BATESBEGIN, BATESEND, CUSTODIAN, DATE, DOCTITLE, using ASCII 254 as the text qualifier and ASCII 20 as the field delimiter, CRLF line endings. The .opt is an Opticon image cross-reference with one line per document pointing at \IMAGES\PROD001\DEF-000001.TIF and similar.

To print, use "Print / save as PDF" at the foot of either page. Printing drops the room heading, the working cards, every form and the Load file column, and yields the schedule of productions and the privilege log under a header naming the matter and the date — or, from a volume's page, that volume's index and log under a header naming the volume, the recipient and the date served.

Guarantees

Assembly freezes the set. The volume record stores the actual document ids of the producible set and the actual ids of the withheld set as they stood at that moment; later re-coding in Document Review does not change what a served volume contains. The partition is enforced in code and is absolute: a document with any privilege coding is withheld, and only a document coded responsive with privilege 'none' is producible — nothing can be both produced and on the privilege log at once. A volume cannot be assembled without a named recipient, and cannot be assembled at all when nothing is coded responsive and not privileged. Every assembly writes an immutable line to the tamper-evident audit chain recording the volume, the recipient, the service date, the document count, the bates range and the withheld count; every load-file download writes its own audit line naming the volume, the format and the document count. The load files are generated on demand from the frozen ids and are never stored, so they cannot drift from the volume. Text you typed in Document Review can never break the load-file frame: the qualifier, delimiter and line-break characters are stripped from every .dat field, and commas from every .opt key. The privilege log discloses bates, created date, author, recipients, a description of the subject and the basis — existence and grounds only, never the withheld content. Incomplete log entries are counted and flagged in red both before and after assembly.

Does not do

It does not send anything to anyone. "Assemble & serve this volume" creates a record and an audit line; it transmits no document, no file and no email to the recipient. Service is something you do outside Chambers, and the room will happily record a service date for a production that never left your desk.

It does not produce the documents themselves. The .dat carries metadata only — bates, custodian, date, title — and the .opt paths point at TIFF files that do not exist. There is no imaging step, no Bates endorsement burned onto a page, and no native-file export anywhere in this room. What you hand opposing counsel as the actual documents is not produced here.

It does not track page counts. BATESBEGIN and BATESEND are the same single bates number for every record and the .opt asserts PageCount 1 for every document. A twelve-page contract is described to the receiving platform as one page.

It does not block an incomplete privilege log. If entries are missing an author or a subject description you get a red count and a warning both on the assemble card and in the success flash, but "Assemble & serve this volume" still serves the volume.

It does not exclude what you already produced. There is no supplemental-volume concept anywhere in this room — see the gotchas.

It does not keep a copy of what the log said on the day it was served. The volume page rebuilds the rows from the frozen ids and renders each document as it reads today, so if a privilege description was edited afterwards the page shows the new wording. The page tells you "the served copy governs" but Chambers is not holding that copy — your served PDF is.

It has no amend, unserve, correct or delete. A volume assembled by mistake stands, with its audit line, forever.

It makes no relevance or privilege judgment of its own. Nothing here reviews, suggests or second-guesses a coding call.

Feeds into

Nothing downstream reads a production volume — no other room in the app consumes the `production` record. Its outputs leave Chambers as the two downloaded load files, the printed schedule and privilege log, and the permanent audit lines `production.served` and `production.loadfile`. Its inputs come entirely from Document Review (room 13), which is the only writer of documents and the only place bates numbers are assigned; it shares the exact same responsive/privileged partition with the Affidavit of Documents (room 35), so the producible set here and Schedule A there are always the same set of documents.

Watch out

The one you must plan around: every volume re-produces everything. "Assemble & serve this volume" takes the entire currently-producible set — it does not subtract documents already frozen into an earlier volume. Code twenty more documents responsive after serving PROD001 and press the button again, and PROD002 contains those twenty plus every document in PROD001, with a bates range starting back at the first document you ever produced. The room offers no way to cut a delta. If you need a genuine supplemental production, you must build it outside Chambers or narrow the producible set in Document Review before assembling, and be aware that narrowing it changes the live "Producible set" card for every other purpose too.

The bates range is first-and-last, not a contiguous run. The producible set is normally interleaved with privileged and non-responsive documents, so "DEF-000001 – DEF-000061" for a 42-document volume is a span, not a sequence. That span is what the audit line and the printed header state.

The "Privilege log" at the foot of the main page is the live log — every document currently coded privileged in the matter, not the log that went with any particular volume. The served log is on the volume's own page.

A document deleted from the review set after a volume was served drops out of that volume's index, and the volume page then shows a red count such as "3 no longer in the review set". The documents were still produced; the only surviving record of that is the bates range and the audit line.

Bates sorting is a string comparison, so it is only reliable while every bates number is the six-digit DEF-nnnnnn form room 13 assigns. Hand-entered or differently formatted bates will sort in the wrong place and can therefore misstate the range on the volume.

The two load-file buttons submit a form and hand you a file; there is no on-screen preview of the .dat or .opt before it downloads.

Affidavit of Documents /r/affidavit

This is the Ontario Rule 30.03 / Form 30A affidavit of documents, assembled rather than typed. Schedule A (documents you produce) and Schedule B (documents withheld on privilege) are derived live from your Document Review coding, so the sworn list cannot drift from the coded set. Schedule C — documents that were, but are no longer, in the party's possession, control or power — has no analogue in review coding, so it is the one schedule you enter by hand here. The room also holds the deponent's particulars and prints or downloads the whole affidavit with the Form 30A recitals and a jurat.

How to use it

Open the matter first; with none open the page reads "Open a matter to assemble its affidavit of documents." If the matter's jurisdiction is anything other than Ontario, a red banner appears at the top warning that Form 30A and r. 30.03 are the Ontario procedure and that you should treat what follows as a working draft only — the room still assembles it.

The top card is "Affidavit of documents — <matter title>". It carries the two output controls, "Print / save as PDF" and "Download (.txt)", and a summary: how many documents are in Schedule A, how many in Schedule B (with a red count of any that have no subject description), how many Schedule C entries exist, how many documents are coded not responsive and therefore excluded from the affidavit entirely, and a "Before swearing" line that names which of the three particulars — deponent name, place sworn, date sworn — are still blank.

Under "Deponent & swearing", fill "Deponent (who swears it)" — required — and optionally "Capacity in the proceeding" (for example, the Defendant), "Place sworn" and "Date sworn". Press "Save deponent". The form is refused with an error flash if the deponent name is empty. The particulars are saved onto the matter and pre-fill the form next time; whatever you leave blank prints as a blank for completion in front of the commissioner, and the room never invents one.

Under "Add a Schedule C document", enter "Description of the document" — required — plus "Document date", "When & how possession was lost" and "Present location", then press "Add to Schedule C". Entries accumulate in a "Schedule C entries recorded" table with a "Remove" button on each row, and each appears in full in Schedule C of the affidavit below.

The assembled affidavit itself is rendered at the foot of the page: a centred heading with the court file number, the style of cause and the Form 30A subtitle; the opening "I, <name>, <capacity>, MAKE OATH AND SAY (or AFFIRM):" line; the five numbered Form 30A recitals reproduced verbatim; Schedule A as a numbered table of No., Bates, Date, Description and Custodian; Schedule B as No., Bates, Date, Description of subject, Author, Recipients and Grounds; Schedule C as No., Date, Description, When & how possession lost and Present location; then the jurat and two signature lines, one for A Commissioner for Taking Affidavits and one for the deponent.

Print with "Print / save as PDF" — printing drops the room heading, the intake cards and all forms, leaves the affidavit alone on the page, and allows it to break across pages. "Download (.txt)" hands you the same affidavit as a plain text file named affidavit-of-documents-<matter-slug>-<today>.txt, with missing particulars rendered as [DEPONENT NAME] and underscore blanks.

Guarantees

Schedules A and B can never disagree with your coding, because they are computed from it at the moment the page renders — there is no separate copy to fall out of date. The partition is the same one Production enforces: any privilege coding puts a document in Schedule B, a document coded responsive with no privilege goes in Schedule A, and a document coded neither responsive nor privileged appears in no schedule at all. The recitals are fixed text quoted from Form 30A and cannot be edited from the interface. The deponent's particulars are never invented: a blank name, place or date renders as a visible red flag on screen and as a blank on the printed and downloaded copy. A Schedule C entry is refused without a description. Each download writes an audit line recording the matter and the three schedule counts. Nothing in this room writes to Document Review; the review set is read only.

Does not do

It does not swear anything, and it does not lock. There is no "mark as sworn", no stored version of the affidavit, and no record anywhere that an affidavit was ever sworn or served. The document you print is regenerated from live coding every time the page loads, so if a colleague re-codes one document the day after your client swore the affidavit, this room will silently print a different affidavit and nothing will tell you the two differ. Your sworn PDF is the only fixed copy; treat it that way.

It does not check the truth of the recitals. Recital 1 swears to a diligent search and appropriate enquiries, and recital 5 swears that no other relevant document has ever been in the party's possession. Chambers verifies neither. Those are the deponent's statements and yours to satisfy yourself about.

It does not stop you printing a defective affidavit. Missing deponent particulars and Schedule B entries with no subject description are counted and flagged in red, but nothing blocks "Print / save as PDF" or "Download (.txt)".

It does not fill in the court file number. That line always prints as a blank — see the concerns.

It does not produce Form 30B (the corporate affidavit), a lawyer's certificate under r. 30.03(4), a Schedule for documents no longer in possession that were formerly privileged, or any other variant. It is the individual Form 30A shape only.

It does not validate the Form against the current Rules. The recital text is reference text held in the source; the room tells you on screen and on the printed copy to confirm it against the current Form 30A before swearing, and you should.

It does not send, serve or file the affidavit anywhere.

Feeds into

Nothing downstream reads this room's records. Its two stored types — the deponent particulars and the Schedule C entries — are read only here. Upstream it depends entirely on Document Review (room 13) for Schedules A and B, and on the matter record for the title, client and jurisdiction. It shares its A/B partition rule verbatim with Production (room 33): Schedule A is exactly Production's producible set and Schedule B is exactly Production's privilege log, so if the two rooms ever disagree, one of them has been changed and you should stop and find out which.

Watch out

Schedule A carries only currently-coded documents. Form 30A's Schedule B speaks of documents that "are or were" in the party's possession; Chambers lists only what is in the review set now, so a privileged document that has since left the party's hands does not appear in Schedule B — you would have to record it in Schedule C by hand.

The jurat reads oddly. With a date sworn of 2026-08-26 the line prints "Sworn (or Affirmed) before me at Toronto, this 2026-08-26 day." — it does not render as "this 26th day of August, 2026". Fix it on the copy that goes before the commissioner.

Saving the deponent form overwrites with blanks. The four particulars are written as a set each time, so if you clear "Place sworn" and press "Save deponent" the previously saved place is gone. In practice the form pre-fills with what is already stored, so a normal re-save is harmless — but do not clear a field you want to keep.

There is exactly one deponent record per matter. Changing the deponent replaces the previous particulars; there is no history of who was named before.

Nothing here is audited except the download. Setting the deponent and adding or removing a Schedule C entry leave no audit line of their own (the underlying encrypted record carries who wrote it and when, but the audit chain does not).

Removing a Schedule C entry is immediate and there is no confirmation prompt.

Schedule C entries sort by the order you created them, not by document date.

Client Portal /r/portal

A plain-language status pack you assemble for the client from figures the firm already computes — the latest client update, the next three key dates, budget against actual with unbilled work in progress, and any decision that is genuinely the client's to make. Despite the name, this is not a portal in the usual sense: there is no client account, no client login and no second authentication surface anywhere in Chambers. You generate a frozen, read-only page, Chambers records that it was generated, and you deliver it yourself by whatever means you already use.

How to use it

Open the matter first; with none open the page reads "Open a matter to prepare and share a client status pack."

The left column shows the pack exactly as it will read. "Where things stand" repeats your most recent client update from Client Desk (room 05), with its approximate reading grade and either a green "plain" tag or a red "aim under 9" tag. "Next 3 key dates" lists the three soonest open deadlines that carry a real ISO due date, with their description and rule citation. "Budget vs actual" shows Budget, Fees & costs charged, Unbilled work (WIP), Total so far (tagged OVER BUDGET, over 80% used, or within budget), Remaining, and Held in trust for client. "Decision awaiting the client" lists any open decision request the client has not already answered.

To add a question, use the right-hand card "Pose a decision to the client": fill "Decision that is the client's to make" — required — and optionally "Options explained (one per line)", one option per line, then press "Add to pack". The flash confirms it will appear in the next pack you generate; it does not retroactively enter packs already generated. Open questions gather in an "Open decision requests" card, each with a "Mark answered" button that closes it and drops it from future packs.

When the preview reads the way you want it to, press "Generate & record client pack" in the top-left card. That freezes every figure into a stored snapshot, writes an audit line, and adds a row to "Packs generated — what was shared, and when" showing the date, the update's reading grade, the number of key dates and decisions carried, and who prepared it.

On that row, "View / print" opens the client-facing document in a new tab: a clean, light-themed page headed with the matter title, "Prepared for <client> · <date> · by <you>", a "Read-only summary" badge, then the sections "Where things stand", "What is coming up", "Your budget" and "A decision we need from you", closing with a footer stating that it is a plain-language summary, not legal advice and not a bill. Print it from that tab — the badge drops on paper. "Download" hands you the identical document as an HTML file named client-pack-<matter-slug>-<date>.html, which is what you attach to an email.

When the client answers, record the answer in Client Desk (room 05) as a decision memo, then come back and press "Mark answered" on the request here so the record matches.

Guarantees

A generated pack is a frozen, self-contained snapshot. "View / print" and "Download" render from the stored record only, so a pack you generated in March still shows March's figures no matter what has happened since. Every figure in it is derived, never invented: fees earned and disbursements come from the ledger, unbilled work in progress from time entries not yet billed, funds held in trust from the trust bank balance, the budget figure from the matter, and the key dates from open deadlines. The reading-grade score is computed with the same code Client Desk uses, so the two rooms always report the same number. A decision request cannot be created without a question. The pack will not ask the client the same question twice: if a decision memo recorded on the Client Desk after the request was posed matches the question text, that request is held back from new packs and shown on screen with a green "answered on the Client Desk" note. Generating a pack writes a `portal.pack.generated` audit line and downloading one writes a `portal.pack.delivered` line. The client-facing document carries no Chambers navigation, no forms and no scripts, and is marked noindex, nofollow.

Does not do

There is no client login, and you should not go looking for one. Both the internal page and the client-facing pack page live behind the same session cookie as the rest of Chambers; an unauthenticated visitor to a pack URL is redirected to the Chambers login screen. The pack reaches the client only because you sent it.

It does not deliver anything. The "Download" button writes a file to your own machine, and the audit line it writes is called `portal.pack.delivered` even though nothing has been delivered to anyone. Chambers has no record of whether the client ever received or read the pack.

The downloaded HTML file is not encrypted and is not protected once it leaves. Everything inside Chambers is sealed under the matter key; the file you hand out is a plain HTML document with the client's budget, trust balance and next deadlines in it. Treat it with the care you would treat any client correspondence.

It does not curate what the client sees. Every open deadline with a real date is eligible for "What is coming up" — there is no internal-only flag — so a purely internal step will be shown to the client if it is one of the three soonest, together with its rule citation under a "Reference:" label.

It is not a bill and the figures are not an invoice. "Fees and costs charged so far" is what the ledger has recognised plus disbursements posted, and "Work done, not yet billed" is raw unbilled time at entered rates, before any write-down, tax or fee-model adjustment. A contingency matter will show unbilled hourly work that will never be billed at all.

It does not capture the client's answer. There is no reply mechanism; a decision comes back to you outside the system and you record it in Client Desk.

It does not write a status update. If no client update has been recorded in Client Desk, the pack simply says "No status update has been recorded yet."

Feeds into

This room is a consumer, not a producer, for every figure it shows: client updates and the budget figure come from Client Desk (room 05), fee income, disbursements and the trust balance from the ledger written by Trust & Books (28) and Billing (34), unbilled work in progress from time entries created in Trust & Books, and key dates from the open deadlines written by Intake (01), Discovery (12), Experts (15), Calendar (21) and ADR (23). What it writes — decision requests and the recorded packs — is read only here; the decision memos that close the loop are written in Client Desk (room 05), and the pack you deliver leaves the system as a printed page or a downloaded HTML file.

Watch out

The pack shows what you press the button on. "Generate & record client pack" freezes the preview as it stands at that instant — check the preview, especially the budget tags and the decisions list, before pressing it. There is no edit and no delete for a generated pack.

The answered-question matching is literal. It compares the decision memo's question text against the request's question text after lower-casing, collapsing whitespace and stripping trailing punctuation, and requires the memo to have been recorded after the request was posed. The Client Desk memo form does not pre-fill the question from the request, so if you paraphrase when recording the answer the match fails and the next pack asks the client again. Copy the question verbatim.

A question re-posed after an earlier answer is asked again by design — the memo must post-date the request — so posing the same wording twice is a deliberate second ask, not a bug.

"Mark answered" closes the request but does nothing else; it does not create a decision memo. Recording the client's authority on the Client Desk is a separate act, and it is the one that matters if the instruction is ever disputed.

A pack page can only be opened while its own matter is the open matter. Following a pack link with a different matter selected gives you "That client pack is not available."

Only deadlines whose due date starts with a full YYYY-MM-DD reach the pack; anything with a blank or malformed due date is silently skipped, so a pack showing "No key dates are scheduled right now" is not proof that no key date exists.

Disbursements are included in the client-facing line "Fees and costs charged so far" from the moment they are posted to the ledger, whether or not they have been billed.

Opening "View / print" is not audited; only generating and downloading are.
